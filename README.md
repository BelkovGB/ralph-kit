# Ralph Kit

Ralph выполняет задачи из GitHub, пока вы не за компьютером: берёт issue,
отдаёт её CLI агента, проверяет результат и открывает pull request. Набор
рассчитан на установку в чужой репозиторий: в нём нет кода продукта, только
цикл, пульт, правила сессии и шаблоны настройки.

## Что делать по порядку

1. [Скопировать файлы набора в репозиторий](#что-скопировать-в-проект).
2. [Разложить беклог в GitHub](#что-подготовить-в-github): фаза плана — это
   один milestone (папка задач в GitHub) и одна ветка, issues складывайте в
   milestone в порядке плана.
3. [Настроить конфиг в пульте](#что-настроить-руками): проверки, фазы, модели.
   Пульт — страница настроек на этой же машине, её поднимает команда
   `node scripts/ralph/ralph-gui.mjs`.
4. Закоммитить скопированные файлы набора и заполненный конфиг: прогон стартует
   только на чистом рабочем дереве.
5. [Проверить копию и настройку](#проверить-что-копия-цела) командой `--check`,
   затем запустить прогон командой `--run`.

## Как это работает

1. Вы пишете issues и складываете их в milestone GitHub.
2. Ralph берёт открытую issue этого milestone с наименьшим номером и отдаёт её
   CLI агента вместе с правилами автономной сессии.
3. Агент пишет код, но не коммитит: коммит делает Ralph.
4. Перед коммитом ваши команды проверок работают на хосте или в контейнере
   Docker без сети — режим задаёт конфиг.
5. Вторая сессия модели ревьюит этот коммит, не видя рассуждений первой.
   Замечания возвращают issue агенту, чистое ревью её закрывает.
6. Когда открытых issues в milestone не осталось, Ralph открывает pull request
   черновиком и ревьюит milestone целиком. Снять черновик и слить — ваша
   работа.

## Что нужно на машине

- **Git** — цикл работает ветками и коммитами.
- **GitHub CLI (`gh`)**, вошедший в аккаунт: `gh auth status` должен отвечать
  успехом. Через него идут issues, milestones и pull requests, поэтому аккаунту
  нужно право записи в репозиторий.
- **Node.js 22 или новее** — на нём написаны цикл и пульт, поэтому Node нужен и
  проекту на Python или Go. Набор проверен на Node.js 24.
- **Docker** — нужен только для `validationMode: "container"`. В host-режиме
  Ralph запускает проверки в рабочей папке проекта: код, который написала
  сессия, выполняется на вашей машине до ревью, поэтому host выбирают для
  проекта, которому доверяют.
- **CLI агента: `claude` или `codex`** — он пишет код и делает ревью. Сессия
  запускается с изолированным HOME, и обычный вход CLI ей не виден. Для
  `claude` задайте переменную окружения `CLAUDE_CODE_OAUTH_TOKEN` (её выдаёт
  `claude setup-token`, работает по оплаченной подписке) или `ANTHROPIC_API_KEY`
  (тарифицируется отдельно). Для `codex` выполните `codex login`: Ralph сам
  скопирует `auth.json` в песочницу сессии.

## Что скопировать в проект

В корень репозитория, сохраняя пути:

- `scripts/ralph/` — цикл, пульт, Dockerfile проверок, тесты, файл одобренных
  issues `approved-issues.json` и справку `README.md` о контейнере проверок.
- `.agents/` — конфиг `ralph.config.json`, правила автономной сессии
  `ralph-rules.md`, схема ревью `review.schema.json`, операторская документация
  `RALPH.md` и тексты четырёх команд чата `skills/`: `prd`, `plan-phase`,
  `issues`, `review-all`.
- `.claude/skills/` — ссылки на те же четыре команды. Копируйте `.agents/skills/`
  и `.claude/skills/` вместе: текст каждой команды лежит в `.agents/skills/`, а
  `.claude/skills/` держит ссылку на него, потому что Codex ищет команды в
  `.agents/skills`, а Claude Code — в `.claude/skills`. Без первого каталога
  команды в Claude Code открывают пустую ссылку.
- `.claude/agents/` — три ревьюера команды `/review-all`: `security-reviewer`,
  `correctness-reviewer` и `test-coverage-reviewer`. В каждом файле лежит своя
  перспектива ревью. Есть у CLI субагенты — команда отдаёт перспективы им
  параллельно; нет — читает те же файлы по одному и проходит перспективы по
  очереди, поэтому каталог нужен любому CLI. Прогон ревьюеров не вызывает: их
  запускает `/review-all`, когда вы ревьюите изменения руками.
- `.gitattributes` — одна строка `scripts/ralph/** text eol=lf`: она закрепляет
  перевод строк LF на файлах набора. Без неё Git на Windows подставит CRLF при
  клоне, sha256 файла одобренных issues разойдётся с суммой в конфиге, и не
  запустятся ни `--check`, ни `--run`. Если свой `.gitattributes` в проекте уже
  есть, допишите эту строку в него, а файл набора не копируйте.
- `.gitignore` — четыре строки: два файла результата ревью, которые пишет Ralph,
  и два файла, которые Claude Code пишет себе сам. Прогон стартует только на
  чистом рабочем дереве, а `git status` считает грязным и неотслеживаемый файл.
  Свой `.gitignore` не заменяйте — допишите эти строки в него.
- `templates/AGENTS.md` → `AGENTS.md` и `templates/CLAUDE.md` → `CLAUDE.md`.
- `LICENSE` — рядом со скопированными файлами, например `scripts/ralph/LICENSE`:
  MIT требует сохранять текст лицензии в копиях.

Не переносите в проект: каталог `templates/` целиком, `README.md`,
`CHANGELOG.md`, каталоги `docs/` и `.github/` — они описывают сам набор и его
разработку и остаются в его репозитории. В `.github/` лежат автопроверка тестов
и шаблон pull request: GitHub читает и то и другое только из репозитория.

### Переводы строк набора

Правило `scripts/ralph/** text eol=lf` защищает файлы Ralph и файлы проекта не
трогает: набор не навязывает проекту общее правило переводов строк. Что делать,
если из-за CRLF на Windows у вас сыплется проверка формата, — в
[docs/tips.md](docs/tips.md).

## Что подготовить в GitHub

Разложить беклог — работа человека: Ralph не придумывает задачи и не дробит
крупные.

- **Milestone на каждую фазу.** Название в GitHub и в конфиге совпадают
  посимвольно.
- **Issues.** Ralph берёт их по возрастанию номера, поэтому создавайте в
  порядке плана. Одна issue — одна задача с критерием готовности, который
  проверяется изменениями только этой задачи.
- **Автор issue** — владелец репозитория или логин из поля «Доверенные авторы
  issues». Чужую issue прогон отклонит.
- **Текст issue после старта не правьте.** Ralph запоминает заголовок и тело в
  момент, когда берёт задачу в работу; расхождение останавливает прогон.
- **Метки заведите заранее:** `gh issue create` падает на несуществующей метке.
  Метку `ralph-deferred` Ralph создаёт сам.

Помогают команды в чате: `/prd` пишет требования, `/plan-phase` режет их на
фазы, `/issues` сверяет план с PRD и кодом, проверяет зависимости, затем создаёт
milestones и issues и печатает блок `phases` для конфига. При конфликте GitHub
не меняется.

## Что настроить руками

Значения конфига правьте в пульте: он подписывает каждое поле и проверяет ввод
теми же правилами, что и запуск прогона. Всё остальное правится только в файлах.

1. **`AGENTS.md` в корне.** Впишите стек, где лежит какая часть кода и точные
   команды сборки, линта и тестов. Агент читает этот файл в каждой сессии.
   Готово, когда постороннему человеку хватит одного этого файла, чтобы собрать
   проект.
2. **Режим проверок** — вкладка «Проверки», поле «Режим проверок». Выберите
   `host`, если доверяете проекту и хотите использовать уже установленные
   зависимости и запущенные рядом службы. Выберите `container`, если нужна изоляция и
   воспроизводимая среда.
3. **Контейнер проверок.** Для `container` настройте
   `scripts/ralph/Dockerfile.validation`: замените базовый образ и поставьте
   зависимости в помеченном слоте. Во время проверок сети нет, поэтому базу
   данных и браузер образ получает при сборке. `COPY` берёт только пути из
   `validationDependencyPaths` и скрипты Ralph. Готово, когда первый `--run`
   дошёл до контейнера. Для `host` этот шаг пропустите.
4. **Команды проверок** — вкладка «Проверки», поля «Команды проверок» и
   «Команды подготовки» (в файле — `validationScripts` и `preflightScripts`).
   Пишите готовые команды оболочки (`npm run lint`, `pytest -q`), по одной на
   строку. В «Файлы зависимостей образа» перечислите манифесты и lock-файлы: без
   записи в этом поле `COPY` в Dockerfile файл не найдёт, а их правка
   пересобирает образ. Готово, когда те же команды проходят у вас в терминале на
   чистой ветке.
5. **Фазы** — вкладка «Фазы». Одна фаза — один milestone и своя ветка. Название
   milestone скопируйте из GitHub посимвольно: неточное название или два
   одноимённых milestone останавливают прогон.
6. **Основное** — агент (`claude` или `codex`), GitHub-аккаунт и базовая ветка.
   Поле GitHub-аккаунта принимает login, уже сохранённый командой
   `gh auth login`. Пустое поле оставляет активный аккаунт GitHub CLI. На первый прогон
   включите «Остановиться после первой issue»: Ralph сделает одну задачу,
   отправит ветку и pull request создавать не станет. **Разработка и ревью** —
   модели и effort для разработки, ревью issue и ревью milestone. Effort — это
   глубина рассуждения модели: выше значение, дороже и дольше сессия.
   Поставляемый конфиг заполнен под `claude`; для `codex` меняется сразу пять
   полей, см. [рабочий комплект](#рабочий-комплект-для-codex).
7. **`.gitignore`.** Проверьте, что исключены все четыре пути из файла набора:
   `.agents/last-review.json` и `.agents/last-milestone-review.json` — туда
   Ralph пишет результат ревью; `.claude/settings.local.json` и
   `.claude/scheduled_tasks.lock` — их Claude Code пишет себе сам. Прогон
   стартует только на чистом рабочем дереве, и любой из четырёх останавливает
   запуск. Тем же файлом вы задаёте содержимое контейнера проверок:
   Ralph кладёт в него копию рабочего дерева без того, что исключено
   `.gitignore`, поэтому каталоги сборки и зависимостей держите исключёнными.
8. **Включите Ralph** — «Ralph включён», в файле `active: true`. Пока выключен,
   обе команды печатают одну строку и выходят.

Необязательный шаг: правила ревью своего проекта положите в
`.agents/review-rules.md` — этот файл читает команда `/review-all` и передаёт
правила всем трём ревьюерам, а они дополняют универсальные классы дефектов, а не
заменяют их. В наборе файла нет; без него команда так и говорит ревьюерам, и они
работают по универсальным классам.

Ещё одно необязательное поле — «Файлы без diff в ревью» на вкладке «Разработка
и ревью» (в файле — `reviewDiffExcludedPaths`). Построчный diff этих путей
ревьюер issue не получает: сгенерированный файл вроде lock-файла меняется на
сотни строк от одной зависимости и вытесняет из бюджета продуктовый код. Файл
остаётся в списке изменений и в статистике, исчезает только его diff. По
умолчанию список пуст. На ревью milestone поле не действует: там по тем же
соображениям исключён control plane.

## Рабочий комплект для Codex

Поставляемый конфиг заполнен под `claude`. При переходе на Codex смените агент
и три модели. Значения effort в поставляемом конфиге подходят обоим CLI.

Вместе меняются четыре поля:

| Поле                    | claude          | codex           |
| ----------------------- | --------------- | --------------- |
| `agentCli`              | `claude`        | `codex`         |
| `developmentModel`      | `claude-opus-5` | `gpt-5.6-terra` |
| `review.model`          | `claude-opus-5` | `gpt-5.6-terra` |
| `milestoneReview.model` | `claude-opus-5` | `gpt-5.6-sol`   |

Полный набор effort задаёт CLI: у Codex — `minimal`, `low`, `medium`, `high`,
`xhigh`, `max`, `ultra`; у Claude — `low`, `medium`, `high`, `xhigh`, `max`.

Имена моделей код ни с каким списком не сверяет, он проверяет только безопасные
символы, поэтому имя из таблицы замените на то, к которому у вас есть доступ.
Пульт после смены агента перерисовывает списки и отмечает поле effort с
недопустимым значением, а поле модели не отмечает: своё имя модели там
разрешено. Три имени моделей меняйте сами.

## Проверить, что копия цела

Закоммитьте скопированные файлы набора и заполненный конфиг: `--check` грязное
дерево терпит и печатает «Рабочее дерево: есть изменения», а `--run` на нём
останавливается словами «Рабочее дерево не чистое».

Создайте ветку первой фазы от базовой
(`git switch -c ralph/phase-1 origin/main`) и выполните из неё

```
node scripts/ralph/ralph-loop.mjs --check
```

Команда печатает версию набора, репозиторий, milestone, число открытых issues,
ветку, состояние рабочего дерева, остаток итераций и выбранные модели. Ветки она
не переключает: с чужой ветки команда падает. При `active: false` она печатает
одну строку о выключении и выходит, ничего не проверив. Что изменилось между
версиями набора — `CHANGELOG.md` в его корне.

`--check` не трогает рабочее дерево, ветки, issues и pull requests, но берёт
блокировку прогона и начинает новый `.git/ralph-loop/run.log`: лог предыдущего
прогона уезжает в архив рядом, и таких архивов хранится пять. Упавший прогон
разбирайте до того, как запускать `--check`.

Что команда доказывает: на месте модули цикла, оба `.sh`, конфиг, файл правил
сессии, схема ревью, страница `.agents/RALPH.md`, файл одобренных issues и — в
контейнерном режиме — Dockerfile проверок — без любого из них загрузка останавливается. Ещё она
разбирает каждый найденный `SKILL.md` из `.agents/skills/` и `.claude/skills/`:
заголовок файла без строк `---` или без полей `name` и `description`
останавливает и `--check`, и `--run`. Чего она не проверяет: есть ли сами
каталоги `.claude/skills/` и `.claude/agents/`. Прогон без них идёт как обычно,
но без первого в чате Claude Code не находится ни одной команды, а без второго
команде `/review-all` нечего читать, поэтому оба каталога сверьте глазами по
списку копирования.

Тесты набора запускаются из корня репозитория одной командой:

```
node --test --test-concurrency=1 "scripts/ralph/*.test.mjs"
```

Проходят 283 теста, падать не должен ни один. Ключ `--test-concurrency=1`
обязателен: пять тестов пишут в файлы самого репозитория — журнал одобренных
issues `scripts/ralph/approved-issues.json`, пробный файл в `.claude` и
`scripts/ralph/ralph-validation-entrypoint.sh` — и возвращают их на место за
собой, а параллельный тестовый файл считает контрольные суммы тех же файлов
ровно в этот момент и падает. Без ключа падает часть тестов. Прогон по каталогу
(`node --test scripts/ralph/`) не работает вовсе: Node принимает путь за модуль
и отвечает `Cannot find module`.

Настройки проекта на результат не влияют: тесты разбирают конфигурацию в памяти
и проверяют поведение кода, а не значения из `.agents/ralph.config.json`. Один
тест сверяет снимок зависимостей с закоммиченными байтами, и пока набор в
проекте не закоммичен, он отмечается пропущенным — сравнивать не с чем. Второй
пропуск в чужом проекте штатный: `CHANGELOG.md` в проект не копируют, а тест
версии сверяется с ним. В таком проекте счёт выглядит как 281 пройденный и два
пропущенных.

Пока идёт `--run`, тесты не запускайте: те же пять тестов подменяют файлы, за
которыми прогон следит как за подделкой.

Прогон запускает команда `node scripts/ralph/ralph-loop.mjs --run`. Что делает
каждый её шаг и как чинить остановку, описывает `.agents/RALPH.md`.

## На что обратить внимание при внедрении

- **Автодеплой.** Ralph отправляет ветку после каждой issue и открывает pull
  request черновиком, но не мержит. Проверьте, не запускает ли push или
  открытый pull request деплой и платные сборки.
- **Второй бот-ревьюер на pull request.** Ревью станет два: замечания чужого
  бота Ralph не читает, а его собственные тот продублирует.
- **Правила репозитория.** Ralph коммитит и пушит от вашего имени. Защита
  ветки, обязательная подпись коммитов, CODEOWNERS или запрет прямого push
  останавливают цикл.
- **Вес файлов инструкций.** `.agents/ralph-rules.md` уходит в prompt каждой
  issue целиком, `AGENTS.md` агент читает в каждой сессии. Лишняя страница
  оплачивается на каждой задаче.
- **Один прогон за раз.** Пока идёт `--run`, не запускайте второго Ralph, не
  работайте в этом репозитории второй сессией Claude Code и не запускайте тесты
  набора: и сессия, и тесты пишут в файлы из защищённого списка, а такая правка
  выглядит как подделка.
- **Порог важности замечаний.** `reviewSeverityFloor` решает, какое замечание
  останавливает работу; P0 — самое важное замечание, P3 — самое мелкое. `P1`
  блокирует P0 и P1, остальное уезжает отдельными issues с меткой
  `ralph-deferred`. `P3` блокирует всё: любое мелкое замечание
  возвращает issue агенту и добавляет попытку, поэтому прогон обходится заметно
  дороже. Набор поставляется с порогом `P1`, хотя умолчание кода — `P3`: в
  свежей установке P2 и P3 сразу уходят в отложенные issues.
- **Имя образа проверок.** В поставляемом конфиге `validationContainer.image`
  задан явно — `ralph-validation:latest`. Это только начало имени: Ralph
  дописывает к нему отпечаток Dockerfile и файлов зависимостей, поэтому образы
  двух проектов не перезаписывают друг друга, но стоят в `docker images` под
  одинаковым началом. Уберите ключ `image`, и Ralph выведет начало из имени
  каталога репозитория: `<имя-каталога>-ralph-validation:latest`.

## Пульт

`node scripts/ralph/ralph-gui.mjs` поднимает страницу на этой же машине и
открывает её в браузере. Тема одна, тёмная. Слева панель с тремя разделами:
расход, настройки и команды; кнопка внизу сворачивает её до иконок, на узком
экране панель сворачивается сама. Над содержимым стоит заголовок раздела и
строка о том, что в нём видно; справа в той же шапке — состояние прогона.
Раздел «Команды» разделён на две вкладки по месту набора: «Команды Ralph-loop»
и «Работа со скиллами в чате». У каждой записи заголовок словами, под ним сама команда —
строкой терминала с приглашением и раскраской: путь к файлу основным цветом,
ключ акцентом. Ниже три карточки — «Делает», «Когда звать» и «Не делает»;
открыта первая, две другие раскрываются знаком плюс. Иконка справа копирует
команду в буфер; приглашение в буфер не попадает.

Расход берётся из журнала `.git/ralph-loop/issue-metrics.json`: токены и время
по задачам, число попыток и исход последней, разбивка попытки на код, проверки
и ревью. Ревью milestone стоит отдельной строкой без номера issue — его
оплачивает прогон, а не задача. Журнал хранит последние 200 попыток. Ручное
ревью командой `/review-all` в журнал не попадает: оно идёт в вашей сессии CLI и
на её модели, своей модели ревьюеры не задают.

Над расходом стоит ход прогона. Пока прогон идёт, счёт относится к текущей
фазе: номер фазы из плана, закрытые и отложенные задачи, число открытых issues,
баги ревью отдельной парой. В открытые входит и та задача, что идёт сейчас, —
это то же число, которое цикл печатает в журнал. Ниже строка о том, что идёт
прямо сейчас: задача, этап, итерация, шаг сессии, круг проверок и круг ревью —
каждый со своим лимитом из конфигурации. Прогона нет — счёт идёт по всему
журналу, и страница об этом говорит.

Живой шаг и число открытых issues пульт читает из хвоста
`.git/ralph-loop/run.log`: в состоянии этих чисел нет, а цикл их печатает.
Считаются только строки с отметкой журнала, поэтому вывод инструментов, попавший
в тот же файл, за строки цикла не сойдёт. Если проверка залила журнал так, что
строки цикла ушли из хвоста, счётчик пропадает до следующей итерации: пустое
место честнее устаревшего числа.

Таблица сгруппирована по фазам в порядке плана; заголовок фазы называет её
задачи, закрытые, отложенные, баги и общий счёт. Внутри фазы строки идут по ходу
работы, переключатель «по объёму» ставит сверху самые дорогие.

Ключи, которых пульт не знает, он показывает на вкладке «Настройки» блоком «Не
распознано»: кнопка «Удалить» вычёркивает ключ из черновика, кнопка «Сохранить»
убирает его из файла.

Чего пульт не умеет: запускать и останавливать прогон — он только показывает
его состояние; править что-либо, кроме `.agents/ralph.config.json`; показать
токены под Codex — тот не присылает счётчики, и остаются только время и число
попыток. Пока идёт прогон, форма заблокирована: правка конфига во время работы
обрывает текущую задачу. Пульт слушает только `127.0.0.1` и требует разовый
ключ из адресной строки, так что с другого устройства его не открыть.

Одна шероховатость: пульт записывает конфиг стандартным отступом JSON. Если
`.agents/ralph.config.json` попадает под `prettier`, после сохранения прогоните
форматирование, иначе проверка формата покраснеет.

## Чего в наборе сознательно нет

- Выбора проверок по изменённым файлам — выполняются все проверки.
- Дешёвой дорожки для правок в комментариях — они проходят полную валидацию.
- Заранее заданных направлений аудита для ревьюера — он разбирает каждый
  изменённый файл и каждый критерий готовности.

Каждая из этих настроек зависит от стека. Задать её под свой проект дешевле,
чем разбирать и чинить готовое правило, написанное под чужой.

## Как обновить набор

Обновление — это повторное копирование файлов из репозитория набора
(`https://github.com/BelkovGB/ralph-kit`) поверх установленной копии. Сам
репозиторий держите рядом: `README.md` и `CHANGELOG.md` в проект не копируются,
и читать их вы будете там.

Перезаписывайте целиком:

- `scripts/ralph/` — все `*.mjs`, `*.sh` и тесты;
- `.agents/RALPH.md`, `.agents/ralph-rules.md`, `.agents/review.schema.json`,
  `.agents/skills/`;
- `.claude/agents/`, `.claude/skills/`;
- `.gitattributes`, если он пришёл из набора и своих правил в нём нет.

Не трогайте никогда:

- `.agents/ralph.config.json` — ваша настройка;
- `.agents/review-rules.md` — правила ревью вашего проекта; в наборе такого
  файла нет, и обновление его не приносит;
- `scripts/ralph/Dockerfile.validation` — ваш стек;
- `scripts/ralph/approved-issues.json` — журнал одобренных issues вашего
  проекта;
- `.gitignore` — он ваш: новые строки набора сверьте по списку копирования и
  допишите руками;
- `AGENTS.md` и `CLAUDE.md` — они описывают ваш проект. Что изменилось в
  `templates/AGENTS.md` и `templates/CLAUDE.md`, переносите руками.

Контрольная сумма журнала одобренных issues обновление переживает: эталон лежит
ключом `approvedIssueSnapshotsHash` в `.agents/ralph.config.json`, а этот файл
обновление не трогает. Журнал и его сумма остаются вашими вместе.

Правите журнал — тем же коммитом впишите в этот ключ новую сумму, иначе
следующий запуск остановится на сверке. Считать её руками не нужно: сообщение об
остановке называет файл журнала, имя ключа и вычисленную сумму.

После обновления сверьте `.agents/ralph.config.json` с разделом CHANGELOG за
новую версию. Незнакомый ключ верхнего уровня и незнакомый ключ внутри `runtime`
останавливают загрузку конфига и печатают список допустимых. Внутри `review`,
`milestoneReview` и `validationContainer` незнакомый ключ проходит молча.
Пропавший ключ останавливает загрузку с именем поля, если умолчания у него нет:
это `approvedIssueSnapshotsHash`, `enabled`, `schemaFile` и `outputFile` у обеих
ролей ревью и `milestoneReview.model`. Остальные Ralph подставляет сам:
`review.model` — `gpt-5.6-terra`, `review.effort` — `medium`,
`milestoneReview.effort` — `high`,
`milestoneReview.maxTurns` — значение `maxTurns`, `milestoneReview.maxFindings`
— 10, `milestoneReview.incremental` — `true`, `validationContainer.image` — имя
из имени каталога репозитория, `validationContainer.dockerfile` — путь к
Dockerfile набора, `validationContainer.writableVolumes` — пустой список,
`validationMode` — `container`, `validationEnvironment` — пустой список,
`githubAccount` — активный аккаунт GitHub CLI. Умолчание `review.model` — модель Codex, поэтому в конфиге
под `claude` пропавший ключ загрузку не остановит, а молча подставит чужую
модель.
