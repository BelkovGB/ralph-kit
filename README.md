# Ralph Kit

Ralph выполняет задачи из GitHub, пока вы не за компьютером: берёт issue,
отдаёт её CLI агента, проверяет результат и открывает pull request. Набор
рассчитан на установку в чужой репозиторий: код прежнего проекта из него
удалён, а не спрятан под настройку.

## Что делать по порядку

1. [Скопировать файлы набора в репозиторий](#что-скопировать-в-проект).
2. [Разложить беклог в GitHub](#что-подготовить-в-github): milestone на каждую
   фазу, issues в порядке плана.
3. [Настроить конфиг в пульте](#что-настроить-руками): проверки, фазы, модели.
4. Проверить настройку командой `--check` и запустить прогон командой `--run`.

## Как это работает

1. Вы пишете issues и складываете их в milestone GitHub.
2. Ralph берёт открытую issue этого milestone с наименьшим номером и отдаёт её
   CLI агента вместе с правилами автономной сессии.
3. Агент пишет код, но не коммитит: коммит делает Ralph.
4. Перед коммитом ваши команды проверок отрабатывают в контейнере Docker без
   доступа к сети.
5. Вторая сессия модели ревьюит этот коммит, не видя рассуждений первой.
   Замечания возвращают issue агенту, чистое ревью её закрывает.
6. Когда открытых issues в milestone не осталось, Ralph открывает pull request
   черновиком и ревьюит milestone целиком. Снять черновик и слить — ваша
   работа.

## Что нужно на машине

- **Git** — цикл работает ветками и коммитами.
- **GitHub CLI (`gh`)**, вошедший в аккаунт: `gh auth status` должен отвечать
  успехом. Через него идут issues, milestones и pull requests, поэтому аккаунту
  нужно право записи в репозиторий.
- **Node.js** — на нём написаны цикл и пульт, поэтому Node нужен и проекту на
  Python или Go.
- **Docker** — внутри контейнера идут проверки. Ralph требует работающий демон,
  только если вы задали хотя бы одну команду проверок.
- **CLI агента: `claude` или `codex`** — он пишет код и делает ревью. Сессия
  запускается с изолированным HOME, и обычный вход CLI ей не виден. Для
  `claude` задайте переменную окружения `CLAUDE_CODE_OAUTH_TOKEN` (её выдаёт
  `claude setup-token`, работает по оплаченной подписке) или `ANTHROPIC_API_KEY`
  (тарифицируется отдельно). Для `codex` выполните `codex login`: Ralph сам
  скопирует `auth.json` в песочницу сессии.

## Что скопировать в проект

В корень репозитория, сохраняя пути:

- `scripts/ralph/` — цикл, пульт, Dockerfile проверок, тесты.
- `.agents/` — конфиг `ralph.config.json`, правила автономной сессии
  `ralph-rules.md`, схема ревью `review.schema.json`, операторская документация
  `RALPH.md`.
- `.claude/agents/` и `.claude/skills/` — три субагента ревью и скиллы
  планирования. Прогон субагентов не вызывает: их запускает скилл `/revew-all`
  в чате, когда вы ревьюите изменения руками.
- `templates/AGENTS.md` → `AGENTS.md` и `templates/CLAUDE.md` → `CLAUDE.md`.
- `templates/pre-commit` → `.git/hooks/pre-commit`,
  `templates/lint-staged.config.mjs` → в корень, если хотите хук перед своим
  ручным коммитом. Свой коммит Ralph делает мимо хуков.

Каталог `templates/` и этот файл в проект не переносите.

## Что подготовить в GitHub

Разложить беклог — работа человека, и она больше всей технической настройки:
Ralph не придумывает задачи и не дробит крупные.

- **Milestone на каждую фазу.** Название в GitHub и в конфиге совпадают
  посимвольно.
- **Issues.** Ralph берёт их по возрастанию номера, поэтому создавайте в
  порядке плана. Одна issue — одна задача с критерием готовности, который
  проверяется изменениями только этой задачи.
- **Автор issue** — владелец репозитория или логин из поля «Доверенные авторы
  issues». Чужую issue прогон отклонит.
- **Текст issue после старта не правьте.** Ralph запоминает заголовок и тело в
  момент, когда берёт задачу в работу; расхождение останавливает прогон.
- **Метки заведите заранее:** `gh issue create` падает на несуществующей метке.
  Метку `ralph-deferred` Ralph создаёт сам.

Помогают скиллы в чате: `/prd` пишет требования, `/plan_phase` режет их на
фазы, `/issues` создаёт milestones и issues из плана и печатает готовый блок
`phases` для конфига.

## Что настроить руками

Значения конфига удобнее править в пульте: он подписывает каждое поле и
проверяет ввод теми же правилами, что и запуск прогона. Всё остальное правится
только в файлах.

1. **`AGENTS.md` в корне.** Впишите стек, где лежит какая часть кода и точные
   команды сборки, линта и тестов. Агент читает этот файл в каждой сессии.
   Готово, когда постороннему человеку хватит одного этого файла, чтобы собрать
   проект.
2. **`scripts/ralph/Dockerfile.validation`.** Замените базовый образ и поставьте
   зависимости в помеченном слоте. Во время проверок сети нет, поэтому базу
   данных и браузер образ получает при сборке. Готово, когда проходит
   `docker build -f scripts/ralph/Dockerfile.validation .`.
3. **Команды проверок** — вкладка «Проверки», поля «Команды проверок» и
   «Команды подготовки» (в файле — `validationScripts` и `preflightScripts`).
   Пишите готовые команды оболочки (`npm run lint`, `pytest -q`), по одной на
   строку. В «Файлы зависимостей образа» перечислите манифесты и lock-файлы:
   их правка пересобирает образ. Готово, когда те же команды проходят у вас в
   терминале на чистой ветке.
4. **Фазы** — вкладка «Фазы». Одна фаза — один milestone и своя ветка. Название
   milestone скопируйте из GitHub посимвольно: неточное название или два
   одноимённых milestone останавливают прогон.
5. **Основное** — агент (`claude` или `codex`), базовая ветка, модели и effort
   для разработки и ревью. На первый прогон включите «Остановиться после первой
   issue»: Ralph сделает одну задачу, отправит ветку и pull request создавать не
   станет.
6. **`.gitignore`.** Добавьте `.agents/last-review.json` и
   `.agents/last-milestone-review.json`. Ralph пишет туда результат ревью, а
   прогон стартует только на чистом рабочем дереве: оставшийся файл остановит
   следующий запуск.
7. **Включите Ralph** — «Ralph включён», в файле `active: true`. Пока выключен,
   обе команды печатают одну строку и выходят.

Проверьте настройку так: создайте ветку первой фазы от базовой
(`git switch -c ralph/phase-1 origin/main`) и выполните из неё

```
node scripts/ralph/ralph-loop.mjs --check
```

`--check` ничего не меняет и печатает репозиторий, milestone, число открытых
issues, ветку, состояние рабочего дерева, остаток итераций и выбранные модели.
Ветки он не переключает: с чужой ветки команда падает. Прогон запускает вторая
и последняя команда — `node scripts/ralph/ralph-loop.mjs --run`. Что делает
каждый её шаг и как чинить остановку, описывает `.agents/RALPH.md`.

Необязательный шаг: правила безопасности своего проекта положите в
`.agents/security-rules.md` или в `.claude/skills/security-review/SKILL.md`. В
наборе этих файлов нет; субагент `security-reviewer` работает без них по
универсальным классам уязвимостей и сам говорит, что правил проекта не нашёл.

## На что обратить внимание при внедрении

- **Автодеплой.** Ralph отправляет ветку после каждой issue и открывает pull
  request черновиком, но не мержит. Проверьте, не запускает ли push или
  открытый pull request деплой и платные сборки.
- **Второй бот-ревьюер на pull request.** Ревью станет два: замечания чужого
  бота Ralph не читает, а его собственные тот продублирует.
- **Правила репозитория.** Ralph коммитит и пушит от вашего имени. Защита
  ветки, обязательная подпись коммитов, CODEOWNERS или запрет прямого push
  останавливают цикл.
- **Вес файлов инструкций.** `.agents/ralph-rules.md` уходит в prompt каждой
  issue целиком, `AGENTS.md` агент читает в каждой сессии. Лишняя страница
  оплачивается на каждой задаче.
- **Один прогон за раз.** Пока идёт `--run`, не запускайте второго Ralph и не
  работайте в этом репозитории второй сессией Claude Code: она пишет в
  `.claude/**`, а этот каталог входит в защищённый список файлов, и правка
  выглядит как подделка.
- **Порог важности замечаний.** `reviewSeverityFloor` решает, какое замечание
  останавливает работу. `P1` блокирует P0 и P1, остальное уезжает отдельными
  issues с меткой `ralph-deferred`. `P3` блокирует всё и делает прогон заметно
  дороже: на исходном проекте 25 задач заняли 83 попытки, и 40 из них отклонило
  ревью.

## Пульт

`node scripts/ralph/ralph-gui.mjs` поднимает страницу на этой же машине и
открывает её в браузере. Три вкладки: расход, настройки и команды. Вкладка
«Команды» перечисляет обе команды прогона, пульт и скиллы чата: что делает
каждая, когда её звать и чего она не делает; кнопка рядом с командой копирует
её в буфер.

Расход берётся из журнала `.git/ralph-loop/issue-metrics.json`: токены и время
по задачам, число попыток и исход последней, разбивка попытки на код, проверки
и ревью. Ревью milestone стоит отдельной строкой без номера issue — его
оплачивает прогон, а не задача. Журнал хранит последние 200 попыток.

Чего пульт не умеет: запускать и останавливать прогон — он только показывает
его состояние; править что-либо, кроме `.agents/ralph.config.json`; показать
токены под Codex — тот не присылает счётчики, и остаются только время и число
попыток. Пока идёт прогон, форма заблокирована: правка конфига во время работы
обрывает текущую задачу. Пульт слушает только `127.0.0.1` и требует разовый
ключ из адресной строки, так что с другого устройства его не открыть.

Одна шероховатость: пульт записывает конфиг стандартным отступом JSON. Если
`.agents/ralph.config.json` попадает под `prettier`, после сохранения прогоните
форматирование, иначе проверка формата покраснеет.

## Чего в наборе сознательно нет

- Выбора проверок по изменённым файлам — выполняются все проверки.
- Дешёвой дорожки для правок в комментариях — они проходят полную валидацию.
- Заранее заданных направлений аудита для ревьюера — он разбирает каждый
  изменённый файл и каждый критерий готовности.

Всё это было написано под конкретный стек. Настроить заново под свой проект
дешевле, чем разбирать и чинить чужие правила.
