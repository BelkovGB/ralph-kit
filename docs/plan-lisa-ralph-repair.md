# Plan: Lisa исправляет Ralph и возобновляет его цикл

**PRD**: [prd-lisa-ralph-repair.md](prd-lisa-ralph-repair.md)
**Дата**: 2026-11-04

## Основание плана

План опирается на PRD из PR #70 и код `main` на коммите `587b442`.
Открытый PR #68 не считается частью действующего контракта.
Реализация в этом документе не выполнена.

Фазы идут последовательно. Первая разрешает ремонт скриптов до коммита текущей
issue, вторая добавляет конфиг и инструкции, третья охватывает опубликованную
работу. До сдачи очередной фазы неподдерживаемый ремонт заканчивается помощью
оператора с сохранённой работой; прежний ремонт обычного кода проекта сохраняется.

## Общие контракты

- Команда `node scripts/ralph/ralph-loop.mjs --run` остаётся пользовательской
  точкой входа. Новый `runRalphLifecycle` в `scripts/ralph/ralph-lifecycle.mjs`
  владеет блокировкой всего прогона, журналом, остановкой дочерних процессов
  и передачей управления между Ralph и Lisa.
- Основной цикл исполняется дочерним процессом. Он передаёт управляющему процессу
  `RalphRunOutcome` с `kind: completed | paused | repair-needed | needs-human`.
  Только `repair-needed` вызывает Lisa; аварийное завершение без проверяемого
  контекста требует оператора. Контракт принадлежит `ralph-lifecycle.mjs`.
- Для ремонта используется `LisaRepairContext`: `repairId`, `runId`, `phaseIndex`,
  `issueNumber`, `branch`, `head`, `failureStep`, `failureFingerprint`,
  `baselineTreeHash`, `baselineControlHashes`, `policy`. Идентификаторы связывают
  ответ Lisa с конкретной остановкой, а не с произвольным новым запуском.
- Политика `policy` фиксирует исходные критерии задачи, обязательные проверки,
  настройки ревью, доверенные источники, пределы вмешательств, полномочия.
  Исправленный конфиг не может переопределить политику текущего восстановления.
- `captureLisaRepairContext`, `assessLisaRepair` и `acceptLisaRepair` принадлежат
  новому `scripts/ralph/ralph-lisa-repair.mjs`. Приёмка работает на доверенной
  версии до ремонта; изменённый код не принимает собственные правки.
  Исходная политика остаётся в памяти управляющего процесса; файлы ответа Lisa
  не могут её переопределять. Перед каждым использованием доверенной копии
  её содержимое сверяется с исходными хешами в памяти; несовпадение требует оператора.
  Управляющий процесс загружает доверенный граф модулей до ремонта; его повторные
  импорты не загружают исправляемые файлы. Проверяемая копия исходных байтов
  содержит зависимости внешних helpers и схему ревью; prompt хранится в загруженном
  коде. Так пути проекта не меняются из-за переноса модулей во временный каталог.
  Это проверка целостности, а не изоляция ОС от произвольного процесса того же
  пользователя; новые ограничения системных прав в эту реализацию не входят.
- `assessLisaRepair` проверяет происхождение diff, сохранность работы, границы
  политики, результаты проверок. Семантическое ослабление тестов или инструкций
  оценивается отдельным read-only вызовом `runReviewSession` из
  `ralph-agent-backends.mjs` с исходной политикой; недоступный, неполный
  или сомнительный вердикт требует оператора.
  Заявления самой Lisa о готовности недостаточно.
  Ревью снижает риск, но не доказывает эквивалентность произвольного кода.
- Сохранённое поле `lisaRepair` в `ralph-state-store.mjs` хранит `repairId`,
  `status`, `failureStep`, `failureFingerprint`, `acceptedTreeHash`.
  Статусы: `repairing`, `checking`, `accepted`, `resuming`, `needs-human`.
  Поле не заменяет `issue.phase`, `supervisorCalls`, `supervisorExtraIterations`.
  Старый state без поля читается как отсутствие ремонта.
- Успешное прохождение ранее падавшего шага завершает ремонт. Новый текст ошибки,
  правка файла или смена PID не считаются прогрессом. Отпечаток причины строится
  из этапа, кода отказа, нормализованных признаков ошибки без времени и PID.
- Принятые изменения образуют новый доверенный слепок только для проверенного
  дерева. Любая следующая незаявленная правка снова блокирует исполнение.
  Ручной запуск не вправе превращать незавершённый ремонт в доверенную базу.

Новых сервисов, библиотек и моделей нет. Проверка ремонта использует уже
настроенный backend Lisa; её отказ не заменяется молчаливым разрешением.
Временная доверенная копия механизма восстановления не является второй установкой
набора и удаляется по завершении прогона без удаления пользовательского diff.

## Фазы реализации

### Фаза 1: Ремонт скрипта Ralph с автоматическим перезапуском

**Цель** Пользователь получает продолжение незавершённой issue после ремонта
скрипта Ralph без ручного запуска процесса.

**Зависит от** Ничего.

**Затрагивает** `ralph-loop.mjs`, `ralph-supervisor.mjs`, `ralph-runtime.mjs`,
`ralph-state-store.mjs`, `ralph-validation-runner.mjs`, `ralph-process-runner.mjs`,
новые `ralph-lifecycle.mjs` и `ralph-lisa-repair.mjs`, журнал, терминал, пульт.
Все пути модулей в плане относятся к `scripts/ralph/`.

**Критерии PRD** 1–3, 5–8, 10–16 для ремонта скриптов до коммита; критерий 9
для сохранения текущей issue и фазы. Полное покрытие 4 и 9 дают фазы 2 и 3.

**Задачи**

- [ ] **1.1** Ввести `RalphRunOutcome` в `ralph-lifecycle.mjs` рядом с прежним результатом `runWithSupervisor`.
  Контракт разбирает завершение, предусмотренную паузу, запрос ремонта, запрос
  оператора; неизвестный результат не запускает Lisa; текущий CLI пока не меняется.
- [ ] **1.2** Ввести приёмку `LisaRepairContext` в `ralph-lisa-repair.mjs`.
  `captureLisaRepairContext`, `assessLisaRepair`, `acceptLisaRepair` работают
  на исходной доверенной версии с проверкой целостности копии, проверяют политику, добавленные, удалённые,
  неотслеживаемые файлы, ссылки, ветку, HEAD, исходный diff; правка конфига
  или инструкций пока отклоняется; отказ ревью запрещает принятие ремонта.
- [ ] **1.3** Добавить сохранённый переход `lisaRepair` в `ralph-state-store.mjs`.
  Переход связывается с `runId` и фазой; запись атомарна; старый state читается;
  несовпадение контекста требует оператора; счётчик вмешательств резервируется
  до вызова Lisa; повторный старт не обнуляет бюджет.
- [ ] **1.4** Подключить `runRalphLifecycle` к существующему CLI `--run`.
  Один управляющий процесс удерживает `acquireRunLock`, исходную политику,
  доверенный механизм приёмки на весь цикл; основной процесс использует проверяемую
  передачу владения без второго захвата; `--check` сохраняет прежний контракт;
  закрытие процесса ожидается до запуска следующего; SIGINT завершает дерево
  процессов на Windows и Linux без автоматического перезапуска.
- [ ] **1.5** Перевести вызов Lisa на `RalphRunOutcome` внутри `runRalphLifecycle`.
  `requestLisa` выдаёт предложение ремонта, приёмку выполняет `assessLisaRepair`;
  `acceptLisaRepair` разрешает новый процесс только для проверенного дерева;
  `prepareLisaResume` инвалидирует устаревшие результаты для этапов до коммита;
  ошибки загрузки исправленного процесса сохраняют контекст ремонта;
  повтор прежнего отказа без прогресса завершает автоматические попытки.
- [ ] **1.6** Удалить прежнее управление повторными запусками из `runWithSupervisor`.
  Удаление выполняется после перевода всех вызывающих мест на `runRalphLifecycle`;
  остаётся единственный владелец вызовов Lisa, бюджета, блокировки, остановки;
  ошибки доступа, недоверенная issue, внешняя правка control plane не обходят защиту.
- [ ] **1.7** Передать события `lisaRepair` в существующие средства наблюдения.
  `ralph-live-status.mjs`, `ralph-terminal.mjs`, `ralph-gui-data.mjs` получают
  этап, список файлов, результаты проверок, исход ремонта; `initializePersistentLog`
  открывает один журнал на весь пользовательский прогон без ротации при перезапуске.
- [ ] **1.8** Обновить инструкции для ремонта скриптов Ralph.
  `supervisorPrompt`, `.agents/RALPH.md`, `scripts/ralph/README.md` описывают
  доступные этапы, ограничения, Stop, журнал; версия и CHANGELOG отражают
  поставленную возможность, без обещаний следующих фаз.

**Когда готова** В установленном наборе на Windows и Linux ошибка скрипта во время
валидации незакоммиченной issue вызывает Lisa; проверенный ремонт загружается
новым процессом, та же issue проходит упавший шаг. Пульт сохраняет историю.
Параллельный запуск отклоняется. Stop, повтор ошибки, исчерпанный бюджет,
ослабление теста, внешний diff управляющего файла завершаются без нового Ralph.
Правка конфига или ремонт этапа после коммита пока возвращают управление человеку.

### Фаза 2: Ремонт конфига и инструкций Ralph

**Цель** Пользователь получает продолжение при ошибочной команде проверки
или противоречии инструкции без ручной правки управляющих файлов.

**Зависит от** Фазы 1.

**Затрагивает** `ralph-lisa-repair.mjs`, `ralph-config.mjs`,
`ralph-validation-runner.mjs`, `ralph-supervisor.mjs`, инструкции.

**Критерии PRD** 4–8, 10–11, 13–14 для конфига и инструкций.

**Задачи**

- [ ] **2.1** Расширить `assessLisaRepair` на изменения конфигурации Ralph.
  Исправленные команды подготовки или проверки сохраняют проверяемые требования;
  идентичность плана, ветка, milestone, критерии, доверие, ревью, пределы бюджета
  сравниваются с исходной `policy`; удаление проверки или расширение прав отклоняется;
  новая конфигурация разбирается без принятия её хешей до решения приёмки.
- [ ] **2.2** Расширить `assessLisaRepair` на инструкции из `agentInstructionFiles`.
  Принимается исправление команды или противоречия без ослабления исходной задачи;
  семантическое ревью читает исходную политику, полный diff, исходные инструкции;
  новые указания внутри ремонтируемого текста не становятся инструкциями ревьюера;
  неопределённость заканчивается помощью оператора.
- [ ] **2.3** Применять принятый слепок через `acceptLisaRepair` при возобновлении.
  `controlPlaneSnapshot` и `assertTrustedControlFilesUnchanged` получают только
  принятые хеши; повторная проверка дерева предшествует старту;
  исправленный конфиг загружается заново; затронутые проверки подготовки,
  валидации, ревью повторяются; незаявленные изменения остаются ошибкой.
- [ ] **2.4** Обновить инструкции для ремонта конфига и правил.
  `supervisorPrompt`, `.agents/RALPH.md`, `scripts/ralph/README.md` называют
  разрешённые изменения, причины отказа, неизменяемую политику;
  версия и CHANGELOG описывают расширение прав.

**Когда готова** Lisa исправляет ошибочную команду проверки либо противоречивую
инструкцию, после чего Ralph продолжает незавершённую issue с новым конфигом.
Попытка удалить проверку, повысить бюджет, заменить критерий задачи или принять
постороннюю правку приводит к помощи оператора с сохранённым diff.

### Фаза 3: Восстановление после коммита и публикации

**Цель** Пользователь получает завершение уже начатой публикации без потери
ремонта, дублирования PR или повторного закрытия issue.

**Зависит от** Фазы 2.

**Затрагивает** `ralph-recovery.mjs`, `prepareLisaResume` в `ralph-supervisor.mjs`,
`ralph-state-store.mjs`, `ralph-loop.mjs`, `ralph-lifecycle.mjs`, инструкции.

**Критерии PRD** 1–4, 7–14 для `committed`, `pushed`, `reviewing`, `closing`;
регресс 5–6, 15–16 обязателен.

**Задачи**

- [ ] **3.1** Расширить `prepareLisaResume` на принятый ремонт после коммита.
  `analyzeRecovery` проверяет `commit`, `recoveryHead`, `pushedHead`, `reviewedCommit`,
  ожидаемое дерево; изменившиеся файлы возвращают работу на нужные проверки;
  созданные коммиты остаются в истории; несовместимость состояния блокирует продолжение.
- [ ] **3.2** Согласовать внешние действия при повторном входе в `runPhasePlan`.
  Для `pushed`, `reviewing`, `closing` система сверяет сохранённые идентификаторы
  с GitHub перед повтором действия; потерянный ответ после успешной публикации
  не создаёт новый PR; закрытая issue не закрывается снова; недоступный GitHub
  сохраняет этап для восстановления без заявления об успехе.
- [ ] **3.3** Завершать `lisaRepair` по результату восстановленного шага.
  Учёт лимитов продолжается в той же фазе; переход к следующей фазе использует
  штатный сброс только после завершения текущей; финальный журнал показывает
  принятый ремонт, повторённые проверки, исход публикации без повторного расхода.
- [ ] **3.4** Обновить инструкции полного цикла восстановления.
  `.agents/RALPH.md`, `scripts/ralph/README.md`, версия, CHANGELOG описывают
  поддержанные этапы, ручной выход при несогласованном state, сохранение внешних действий.

**Когда готова** При сбоях после commit, push, ревью или успешного внешнего действия
с потерянным ответом Lisa ремонтирует причину, Ralph завершает ту же issue через
существующий PR. Изменённый код проходит повторную проверку. Чужая работа сохранена;
конфликт ветки или недоступное подтверждение внешнего действия не выдаются за успех.

## Проверка каждой задачи и фазы

Изменение поведения начинается с падающего теста внутри соответствующей задачи.
Тест использует код этой задачи и предыдущих; последующая фаза не нужна для его
прохождения. Для документов отдельные тесты не добавляются.

После задачи проверяются изменённый контракт и его потребители; в конце фазы —
её сквозные сценарии на Windows и Linux. Полный регресс репозитория запускается
отдельно от Ralph: `node --test --test-concurrency=1 "scripts/ralph/*.test.mjs"`.
Для приёмки используются управляемые ответы агента и GitHub, воспроизводимые
сбои процессов, живой путь CLI → Lisa → новый Ralph; тест одного helper не
заменяет проверку передачи управления.

Каждая фаза сдаётся отдельным PR с актуальными инструкциями, версией и CHANGELOG.
Слияние выполняется только после явного одобрения владельца.
