# Plan: Исправления Ralph Kit по итогам аудита

**PRD** [prd-ralph-audit-remediation.md](prd-ralph-audit-remediation.md)

**Дата** 2026-11-07

## База и исполнение

- План опирается на `d31b6e3` из открытого [PR
  №81](https://github.com/BelkovGB/ralph-kit/pull/81). Ветки реализации должны содержать
  этот набор изменений. После слияния PR сверить итоговый `main` с базой плана.
- Фаза 1 проверяет сквозной путь. Независимую защиту `.git` из фазы 3 можно поставить
  отдельным исправлением раньше.
- Фазы меняют управляющий код и скиллы самого Ralph. Их выполняют обычные инженерные
  сессии. Текущие `/issues` и `--run` исключают такие задачи из продуктовой очереди.
- Пути модулей и тестов ниже относятся к `scripts/ralph/` . Поведение закреплять падающим
  тестом в той же задаче. Затронутые инструкции, версию и `CHANGELOG.md` обновлять вместе
  с изменением. Полный регресс перед поставкой фазы выполняется отдельно командой
  `node --test --test-concurrency=1 "scripts/ralph/*.test.mjs"` на Windows и Linux.

## Фазы реализации

### Фаза 1: Публикация проверенного коммита

**Цель** Оператор получает сквозной результат одной issue. Ralph отправляет проверенный
локальный HEAD, затем закрывает задачу.

**Зависит от** Ничего.

**Затрагивает** `ralph-loop.mjs` , `ralph-git.mjs` , `ralph-state-store.mjs` ,
`ralph-recovery.mjs` , интеграцию с Lisa.

**Критерии PRD** 1–4, 6–7.

**Задачи**

- [ ] Ввести необязательную запись `issue.reviewReceipt` в `ralph-state-store.mjs`.
  Контракт записи — `{ head, result }` , где `head` обозначает фактически проверенный
  локальный HEAD, а `result` содержит вердикт и замечания. Запись отделена от
  `issue.phase` , `issue.commit` с трейлером и подтверждённого `issue.pushedHead` . В
  `ralph-recovery.mjs` поддержать старое состояние. Старый `PASS` переиспользовать только
  при однозначном совпадении вердикта и проверенного HEAD. Проверить чтение старого
  `closing` , неоднозначного `pushed` и смену HEAD в `ralph-state.test.mjs` и
  `ralph-recovery.test.mjs` .
- [ ] Перевести `reviewAndCloseCommittedIssue` на публикацию по `issue.reviewReceipt`.
  Записывать `PASS` или `FAIL` до первой внешней записи. Перед публикацией сверять
  состояние issue, её принадлежность к фазе и принятые условия. После `PASS` передавать
  точный SHA в `pushBranchAndVerify(config, { expectedHead })` , сверять ветку на сервере
  перед закрытием. При отключённом ревью использовать SHA проверенного локального дерева.
  При исчерпании попыток на неопубликованном `FAIL` сохранить задачу и остановить
  продвижение ветки до исправления, включая push следующей issue и PR фазы. Сигнал об
  устранении сбоя ревью для Lisa оставить после сверки опубликованного HEAD. Покрыть
  обычный путь с обоими адаптерами, `FAIL` , технический сбой, `stopAfterFirstIssue` ,
  потерянный ответ push, повторный отказ закрытия и недоступную запись замечаний.
  Использовать `ralph-lifecycle.test.mjs` и `ralph-repair-completion.test.mjs` . Обновить
  `.agents/RALPH.md` и `scripts/ralph/README.md` .

**Когда готова** При `PASS` журнал показывает локальное ревью перед первым push и закрытие
после сверки SHA. При `FAIL` удалённая ветка сохраняет прежний HEAD, в том числе при
пустой очереди и наличии следующей задачи. После двух отказов закрытия Ralph закрывает
issue на третьей попытке с одним ревью этого SHA.

### Фаза 2: Продолжение работы при недоступном GitHub

**Цель** Оператор сохраняет локальный результат при сбое GitHub и видит, какой внешний шаг
ждёт. Для диагностики достаточно прав чтения.

**Зависит от** Фаза 1.

**Затрагивает** запуск и восстановление в `ralph-loop.mjs` , `ralph-lifecycle-host.mjs` ,
`ralph-recovery.mjs` , `ralph-github-client.mjs` , `ralph-git.mjs` .

**Критерии PRD** 5, 8–9, 14, 20.

**Задачи**

- [ ] Продолжать работу по принятой issue при обрыве связи.
  Вызывать `resumeAcceptedIssue` из `runContinuousLoop` для уже принятой issue с
  проверенным локальным контекстом. Этот путь использует доверенный снимок, локальную
  ветку и `issue.reviewReceipt` . В `commitAndCompleteIssue` убрать ранний запрос статуса
  после работы агента. Проверка перед внешней записью принадлежит маршруту публикации фазы
  1. При отмене, смене условий или несовпадении SHA сохранять локальный результат и
  показывать причину остановки. На фикстуре с успешным стартом проверить обрыв после
  принятия issue, отмену задачи и несовпадение SHA в `ralph-lifecycle.test.mjs` .
- [ ] Подготовить локальный запуск до сетевых проверок в `main`.
  Вызывать `resumeAcceptedIssue` при холодном запуске с подходящим состоянием. Новые
  задачи по-прежнему брать из актуальной очереди. `--check` выводит локальную диагностику
  и доступную очередь отдельно от статуса права записи. `--accept-manual-commit` при
  достаточном контексте проходит через локальный `prepareRecovery` . Для сетевой части
  старта собрать один снимок через `githubPagedArray` , разрешить из него все milestones с
  проверкой отсутствующих и неоднозначных имён. Использовать в `verifyBaseHistory` базу,
  которую уже загрузила `syncPhaseBranchWithBase` ; для `createPullRequest` оставить
  свежую проверку. Покрыть холодный запуск со старым состоянием, read-only доступ,
  недоступную очередь, ручное принятие, пагинацию и число fetch в
  `ralph-github-client.test.mjs` и `ralph-repair-published-cli.test.mjs` . Обновить
  руководство команд.

**Когда готова** При обрыве GitHub после принятия issue Ralph сохраняет локальный коммит и
`PASS` , показывает ожидающий шаг, затем возобновляет публикацию с него. Read-only
`--check` показывает очередь. При старте двух фаз один проход API читает общий список
milestones, синхронизация базы делает один fetch.
