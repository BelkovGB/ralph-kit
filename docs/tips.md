# Подсказки

Сюда собраны приёмы, которые упрощают установку и работу с набором, но самим
набором не являются: это знание об инструментах вашего стека, а не поведение
Ralph. Документация набора — `README.md` и `.agents/RALPH.md` — описывает только
то, что Ralph делает; здесь лежит то, что помогает подготовить под него проект.

Файл живёт в репозитории набора и в проект не копируется. Проверяйте команды на
своём стеке: примеры написаны для распространённых инструментов, а не для всех.

## Переводы строк на Windows

Набор закрепляет LF только за своими файлами — `scripts/ralph/** text eol=lf` в
`.gitattributes`. Это узкое правило: оно защищает контрольную сумму журнала
одобренных issues и не трогает файлы проекта. Общее правило переводов строк
проекту приходится задавать самому.

Форматтер или CI перечисляют много файлов, которых вы не трогали, — проверьте
переводы строк:

```
git config --get core.autocrlf
git ls-files --eol
```

Вывод `w/crlf` при `core.autocrlf=true` означает, что Git записал в рабочую
копию CRLF. Если проект требует LF, добавьте в его `.gitattributes`:

```
* text=auto eol=lf
```

Дальше важен порядок, и начинать нужно с чистого рабочего дерева. Сначала
пересчитайте индекс под новое правило и посмотрите, что в него попало:

```
git add --renormalize .
git diff --cached --stat
```

Закоммитьте нормализацию отдельно от изменений продукта. Затем обновите рабочую
копию: правка `.gitattributes` сама файлы на диске не переписывает, и до этого
шага `git ls-files --eol` продолжает показывать `w/crlf`.

```
git rm --cached -r .
git reset --hard
```

Форматтер запускайте последним. Запущенный раньше, он видит на диске прежние
CRLF и переписывает весь проект — ровно тот огромный diff, из-за которого
проверка формата и падала.

## Быстрый хук перед своим коммитом

Свой commit Ralph делает мимо хуков — локальные проверки не входят в его
доказательство. Для ручного коммита хук полезен: он ловит опечатку до того, как
её увидит прогон. Держите его быстрым, полный набор всё равно выполняется
проверками Ralph.

`.git/hooks/pre-commit` для проекта на npm:

```sh
#!/bin/sh
npx lint-staged
```

и `lint-staged.config.mjs` в корне:

```js
export default {
  '*.{cjs,css,js,json,jsx,md,mjs,ts,tsx,yaml,yml}': 'prettier --write',
};
```

Для другого стека подставьте свой инструмент: `ruff format`, `gofmt -w`,
`cargo fmt`. Набор такой хук не поставляет: он принадлежит стеку проекта.

## Отчёты проверок ломают следующую проверку

Проверки идут в рабочей папке, поэтому файл, созданный одной
командой, попадает под следующую: отчёт браузерного набора — под линтер, и тот
падает на сгенерированном коде, которого вы не писали.

Лечится с двух сторон, и обе нужны.

Со стороны проекта — исключите каталог отчётов из линтера и форматтера. Это
полезно и без Ralph: тот же отчёт ломает проверку, запущенную руками.

```text
# пример для ESLint: каталог отчётов не проверяется
output/**
```

Со стороны набора — назовите этот каталог в поле «Артефакты проверок»
(`validationArtifactPaths`). Ralph удалит его перед прогоном, и старый отчёт не
доживёт до следующей итерации.

```json
"validationArtifactPaths": ["apps/web/output", "coverage"]
```

Ralph удаляет только то, чего нет в Git. Путь, который git отслеживает, он не
трогает, а останавливает прогон: там работа, а не мусор.

## Форматирование после каждой правки агента

Проверка формата — самый дешёвый способ потерять итерацию: агент сделал работу,
а прогон вернул задачу из-за отступов. По журналу одного проекта такой отказ
случился дважды на 83 попытки.

Если ваш агент — Claude Code, повесьте форматтер на хук `PostToolUse` в
`.claude/settings.json` проекта: он прогоняется после каждой записи файла, и до
проверок доходит уже отформатированный код.

```json
"hooks": {
  "PostToolUse": [
    {
      "matcher": "Write|Edit",
      "hooks": [
        {
          "type": "command",
          "command": "jq -r '.tool_input.file_path' | { read -r f; npx prettier --write \"$f\"; } 2>/dev/null || true"
        }
      ]
    }
  ]
}
```

Команду замените на форматтер своего стека. У Codex такого хука нет — там
остаётся команда формата в `validationScripts` и итерация на исправление.
