# Подсказки

Сюда собраны приёмы, которые упрощают установку и работу с набором, но самим
набором не являются: это знание об инструментах вашего стека, а не поведение
Ralph. Документация набора — `README.md` и `.agents/RALPH.md` — описывает только
то, что Ralph делает; здесь лежит то, что помогает подготовить под него проект.

Файл живёт в репозитории набора и в проект не копируется. Проверяйте команды на
своём стеке: примеры написаны для распространённых инструментов, а не для всех.

## Переводы строк на Windows

Набор закрепляет LF только за своими файлами — `scripts/ralph/** text eol=lf` в
`.gitattributes`. Это узкое правило: оно защищает контрольную сумму журнала
одобренных issues и не трогает файлы проекта. Общее правило переводов строк
проекту приходится задавать самому.

Форматтер или CI перечисляют много файлов, которых вы не трогали, — проверьте
переводы строк:

```
git config --get core.autocrlf
git ls-files --eol
```

Вывод `w/crlf` при `core.autocrlf=true` означает, что Git записал в рабочую
копию CRLF. Если проект требует LF, добавьте в его `.gitattributes`:

```
* text=auto eol=lf
```

Дальше важен порядок, и начинать нужно с чистого рабочего дерева. Сначала
пересчитайте индекс под новое правило и посмотрите, что в него попало:

```
git add --renormalize .
git diff --cached --stat
```

Закоммитьте нормализацию отдельно от изменений продукта. Затем обновите рабочую
копию: правка `.gitattributes` сама файлы на диске не переписывает, и до этого
шага `git ls-files --eol` продолжает показывать `w/crlf`.

```
git rm --cached -r .
git reset --hard
```

Форматтер запускайте последним. Запущенный раньше, он видит на диске прежние
CRLF и переписывает весь проект — ровно тот огромный diff, из-за которого
проверка формата и падала.

## Обрыв загрузки при сборке образа проверок

Сборка образа — единственный шаг прогона с сетью и единственное место, где
дерево зависимостей скачивается целиком. Обрыв связи ломает именно его: Ralph
повторит сборку, но каждый повтор начинает упавший слой с начала.

Цикл повторов внутри одного `RUN` сохраняет уже скачанное, потому что кэш
пакетного менеджера лежит в том же слое, и каждый заход продвигается дальше.
Пример для npm:

```
RUN ok=""; for attempt in 1 2 3 4 5; do \
      npm ci --prefer-offline && ok=1 && break \
      || echo "npm ci: attempt $attempt failed, retrying"; \
    done; test -n "$ok"
```

## База данных внутри контейнера проверок

Контейнер поднимается заново на каждый прогон, а корневая файловая система в нём
только для чтения, поэтому сервис с состоянием на диске в образ не запекается:
его каталог данных оказался бы недоступен для записи. Такую службу инициализирует
и запускает команда из `preflightScripts`, а каталог данных кладёт в `/tmp`.

Кластеру PostgreSQL задавайте локаль UTF-8 явно, например `C.UTF-8`: локаль `C`
по умолчанию не приводит регистр ничего за пределами ASCII, и проект, чьи тесты
сравнивают неанглийские строки, падает на сравнениях, которые везде проходят.

## Записываемые каталоги при read-only корне

Пакетный менеджер, которому нужно обновлять свой store во время проверки,
получает временный том через `validationContainer.writableVolumes` — например
`/opt/pnpm-store`. Зависимости, установленные при сборке, лежат вне рабочего
каталога, обычно в `/opt`, а команда из `preflightScripts` копирует их туда, где
их ждут команды проверок:

```
"preflightScripts": ["cp -R /opt/deps/node_modules node_modules"]
```

Копируйте, а не связывайте ссылкой: тест-раннеры пишут внутрь собственного
дерева зависимостей, и ссылка в каталог только для чтения ломает прогон.

## Быстрый хук перед своим коммитом

Свой commit Ralph делает мимо хуков — локальные проверки не входят в его
доказательство. Для ручного коммита хук полезен: он ловит опечатку до того, как
её увидит прогон. Держите его быстрым, полный набор всё равно выполняется
проверками Ralph.

`.git/hooks/pre-commit` для проекта на npm:

```sh
#!/bin/sh
npx lint-staged
```

и `lint-staged.config.mjs` в корне:

```js
export default {
  '*.{cjs,css,js,json,jsx,md,mjs,ts,tsx,yaml,yml}': 'prettier --write',
};
```

Для другого стека подставьте свой инструмент: `ruff format`, `gofmt -w`,
`cargo fmt`. Набор такой хук не поставляет: он принадлежит стеку проекта.

## pnpm и Corepack в образе проверок

Задайте `COREPACK_HOME` и store вне `HOME`. В слое сборки выполните
`corepack enable`, затем `corepack install`, установите зависимости и отдайте
каталоги uid 65532. Store добавьте в `validationContainer.writableVolumes`,
например `/opt/pnpm-store`. Так проверка берёт pnpm из образа и не скачивает его
перед прогоном.

BuildKit cache mounts подойдут для архива Corepack и store: повтор сборки
продолжит загрузку после сетевого обрыва.
