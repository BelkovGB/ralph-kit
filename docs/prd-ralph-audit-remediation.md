# PRD — исправления Ralph Kit по итогам аудита

**Дата** 2026-11-07

**База** Ralph Kit `2.21.2`, коммит `d31b6e3`, [PR №81](https://github.com/BelkovGB/ralph-kit/pull/81).

## Цель

Оператор получает проверенный локальный коммит, который Ralph отправляет в GitHub и связывает с задачей. Сбой публикации сохраняет результат локальной работы. Ralph защищает данные Git и инструкции агентов, а скиллы показывают оператору полную и точную картину работы.

## Подтверждённые решения

- Ralph реализует задачу и запускает тесты в локальной ветке Git. GitHub хранит код и задачи.
- Для обычной задачи с включённым независимым ревью оператор выбрал порядок «локальные тесты и ревью → push → закрытие issue». Ревью проверяет локальный коммит. Ralph публикует именно проверенный SHA и сверяет его на сервере перед закрытием задачи.
- `stopAfterFirstIssue` ограничивает прогон одной задачей. Публикация этой задачи остаётся частью завершения.

## Пользовательские сценарии

| Сценарий | Результат для оператора |
| --- | --- |
| S1. Реализовать и опубликовать одну задачу | Ralph проверяет локальный коммит, отправляет его в GitHub и закрывает issue после сверки опубликованного SHA. |
| S2. Продолжить после сбоя или отказа ревью | Оператор видит сохранённый результат и незавершённый шаг. Ralph продолжает с этого шага. |
| S3. Защитить рабочую копию и инструкции | Ralph сохраняет служебные данные Git и чужие изменения, распознаёт точные пути и останавливается при подмене управляющих файлов. |
| S4. Проверить готовность и взять задачу | Диагностика работает с правами чтения. Автоодобрение доверенной задачи работает без пустого ручного журнала. |
| S5. Поставить задачи, проверить ветку и принять фазу | Скиллы соблюдают границы команды, берут верный diff и показывают неполный прогон приёмки. |
| S6. Избежать повторной передачи данных | Ralph загружает общий список фаз один раз и передаёт ревьюеру исправление в пределах доступного контекста. |

## Вне объёма

- Отдельный локальный режим без публикации, новые команды и изменения политики слияния PR.
- Возврат отдельной команды PR-ревью. Ручное `review-all`, режим issue `review` и встроенное ревью сохраняют свои назначения.
- Общий рефакторинг по размеру файлов, кэш пульта, смена агентских CLI, таймаутов и способа изоляции процессов.
- Отмена требования чистого дерева при смене ветки или слиянии. Проверка производительности на реальных сессиях провайдеров и численные цели по токенам и задержке.

## Технические ограничения

- Ralph использует локальный Git, GitHub и действующие адаптеры Codex и Claude Code. Дополнительные сервисы и зависимости для этих сценариев не требуются.
- Установленные конфиги, сохранённые прогоны и старые отчёты приёмки должны читаться после обновления. Результат старого ревью можно переиспользовать, если состояние однозначно подтверждает вердикт и проверенный SHA.
- Снимок активной issue, защита ветки, индекса и управляющих файлов, изоляция учётных данных и границы полномочий сохраняются. Исключение для разрешённого ремонта Lisa подчиняется действующему контракту ремонта.
- Режимы issue с обязательным ревью, проверка отчётов `research` и `review`, отдельные проверки `ui-change` и итоговое ревью фазы сохраняют свои условия. Одноимённые проверки с разными входами или областью проверки учитываются отдельно.
- Сценарии с GitHub, Codex и Claude Code можно воспроизводить на фикстурах. Прогон набора использует `node --test --test-concurrency=1 "scripts/ralph/*.test.mjs"` на Windows и Linux.

## Допущения

- Локальное продолжение при сбое GitHub начинается после принятия issue и сохранения её условий. Выбор новой задачи по-прежнему требует актуальной очереди.
- После технического сбоя Ralph показывает оператору состояние, SHA сохранённого коммита, ожидающий шаг и причину остановки. Для этого достаточно существующих точек входа.
- Для оптимизаций достаточно наблюдаемого сокращения повторов в одинаковом сценарии. Замеры аудита служат исходной точкой без порога в миллисекундах или байтах.

## Критерии готовности

### S1. Реализация и публикация

1. При штатном запуске новой issue с включённым независимым ревью Ralph проходит локальные тесты, создаёт локальный коммит и получает `PASS` для его SHA до первого push кода задачи. После push Ralph сверяет этот SHA на сервере и закрывает issue. Критерий проверяется с обоими поддерживаемыми адаптерами ревью.
2. При `FAIL` проверенный коммит и замечания доступны следующей попытке. Удалённая ветка сохраняет прежний HEAD, а issue остаётся открытой. Технический сбой ревью отображается отдельно от `FAIL` и сохраняет локальный коммит.
3. При разрешённом отключении независимого ревью Ralph публикует коммит после локальной валидации. Перед закрытием issue действует та же сверка опубликованного SHA.
4. При `stopAfterFirstIssue: true` Ralph доводит выбранную задачу до завершения или показывает незавершённый шаг. Следующая задача и завершение фазы остаются для отдельного прогона.

### S2. Возобновление и сетевые сбои

5. Если GitHub перестал отвечать после принятия задачи, а локальная валидация и ревью доступны и проходят, Ralph сохраняет коммит и `PASS`. В выводе видны SHA, результат и причина, по которой публикация ждёт. После восстановления доступа Ralph продолжает с внешней операции, используя действующий вердикт.
6. Если GitHub дважды отказывает в закрытии, а третья попытка успешна, для того же SHA с действующим `PASS` наблюдается одна сессия ревью и одно успешное закрытие. Потеря ответа на уже выполненный push или закрытие распознаётся по состоянию GitHub.
7. Если после `FAIL` GitHub отказывает в записи замечаний, следующий запуск получает сохранённые замечания для исправления. Для восстановления замечаний Ralph использует уже полученный вердикт. Изменённый коммит проходит своё ревью.
8. Если до публикации оператор закрыл issue, вывел её из очереди или изменил утверждённые условия, Ralph сохраняет локальный результат и сообщает, почему публикация остановилась. При несовпадении проверенного и опубликованного SHA автоматическое закрытие останавливается с указанием обоих SHA.
9. После обновления сохранённый прогон продолжает ту же issue с её коммита без переписывания уже опубликованной истории. Подтверждённый старый `PASS` используется для того же SHA, а неоднозначное состояние требует новой проверки. Сбой GitHub при продолжении оставляет локальный результат доступным.

### S3. Целостность Git и инструкций

10. При попытке указать `.GIT` или другой регистровый вариант служебного пути на Windows Ralph останавливает уборку до удаления, указывает путь и сохраняет данные Git. Проверка действует в обычном checkout и linked worktree. Допустимый артефакт в каталоге проекта удаляется по прежним правилам.
11. Если после начала работы обычная агентская сессия добавляет или меняет `AGENTS.override.md`, Ralph отклоняет изменения до коммита и публикации и называет файл. Существующий файл из доверенного снимка проходит проверку при совпадении содержимого.
12. При путях с пробелами, ведущим пробелом, Unicode и переименованиях Ralph коммитит предназначенные задаче файлы по точным именам. Если в индексе есть чужие изменения, Ralph сохраняет их и сообщает об отказе, когда безопасно продолжить нельзя.
13. Если команда валидации перезаписывает уже изменённый или неотслеживаемый файл с ведущим пробелом, Ralph сообщает его точное имя и останавливает коммит. Команда, которая сохраняет содержимое дерева, проходит этот контроль.

### S4. Диагностика и одобрение

14. С доступом на чтение Ralph через `--check` показывает доступную очередь и отдельно сообщает о недоступности публикации. Если очередь недоступна, вывод указывает причину и показывает доступные результаты локальной диагностики. Ручное принятие коммита при достаточном сохранённом контексте проверяет локальную историю и состояние без права записи в GitHub.
15. При автоодобрении и отсутствии явной настройки журнала доверенная задача принимается без пустого файла и его SHA. Недоверенный автор и подмена условий активной issue приводят к отказу с объяснением. Ручной режим и явно настроенный журнал проходят действующие проверки целостности.

### S5. Скиллы

16. По `/issues` Ralph создаёт или переиспользует задачи и завершает вызов списком задач и блоком `phases`. Изменение конфига, его коммит и запуск `--run` происходят по отдельному поручению оператора.
17. Повтор `/issues` на частично созданном беклоге с несколькими страницами находит совпадающие записи, включая закрытые milestones. При расхождении Ralph показывает конфликт до создания дубля. Совпадающая закрытая фаза сохраняет свой статус.
18. Для зависимой фазы `review-all` использует её базовую ветку. Исключённые lock-файлы остаются в перечне изменений, а построчный diff применяет одинаковые исключения к коммитам и рабочей копии. При недоступной базе скилл сообщает, что нужно уточнить.
19. Если в отчёте с полем `Кейсы` пропущен назначенный ID или появился лишний, `acceptance status` сообщает расхождение и не показывает прогон как принятый. Полный отчёт и старый отчёт без этого поля читаются по своим правилам.

### S6. Повторные вызовы и объём ревью

20. При старте с двумя фазами Ralph читает общий список milestones одним проходом с учётом страниц. При включённой синхронизации одной базы на старте фазы она загружается один раз. Свежая сверка, нужная перед публикацией PR, выполняется отдельно.
21. Если у Ralph есть подтверждённая база предыдущего ревью, следующее ревью получает новые изменения той же issue и прежние замечания. В фикстуре с большим первым diff и коротким исправлением исправление присутствует в фактическом промпте. При недостоверной базе ревью получает полный инвентарь по действующим правилам.
