# Ralph Loop для Codex и Claude Code

> **Это операторская документация.** Она описывает настройку, запуск,
> восстановление и устройство изоляции. Контракт автономной сессии — отдельный
> файл `.agents/ralph-rules.md`, который оркестратор целиком подставляет в
> prompt. AFK-агент не должен читать этот файл: он не содержит требований к
> реализации, но стоит сотни строк входного контекста на каждую issue.

Циклом управляет `scripts/ralph/ralph-loop.mjs`; `.agents/ralph-loop.mjs` —
совместимый launcher старой команды, запускающий ту же реализацию. Оба файла
вместе с `.agents/**` и всеми `AGENTS.md` образуют защищённый control plane:
продуктовый AFK-цикл никогда их не изменяет, Ralph настраивается оператором
вручную вне продуктового цикла.

## Перед запуском

1. В `.agents/ralph.config.json` заполнить массив `phases` в порядке выполнения.
   Для каждой фазы указать **точное** название GitHub milestone и отдельную
   рабочую ветку `branch`.
   При `autoApproveConfiguredIssues=true` закоммиченный план автоматически
   фиксирует точные title/body доверенных issues в локальном AFK state перед
   запуском Terra; последующие изменения GitHub будут отклонены.
2. Проверить глобальный `baseBranch`. При необходимости конкретная фаза может
   переопределить его своим `phases[].baseBranch`.
3. Убедиться, что история каждой рабочей ветки совместима с её базой PR.
4. Каждая issue milestone должна быть самостоятельно завершаемым зелёным
   срезом. Зависимые test-only и implementation-only задачи объединяйте в одну
   фазовую issue, иначе строгий per-issue commit/review намеренно остановится.
5. Проверить `docker version`, авторизацию `gh auth status` и версию выбранного
   агента. Агента задаёт поле `agentCli`: `codex` (по умолчанию) или `claude`.
   Роли настраиваются одними и теми же полями `developmentModel`,
   `developmentEffort`, `review.model`, `milestoneReview.model`; словарь
   `effort` у CLI разный — Codex принимает minimal/low/medium/high, Claude
   low/medium/high/xhigh/max, и конфиг проверяется под выбранный CLI.

   Claude-сессия запускается с изолированным HOME, куда OAuth-состояние CLI не
   переносится, поэтому для `agentCli: "claude"` в окружении оператора должна
   быть одна из двух переменных, и они не равнозначны по деньгам:
   `CLAUDE_CODE_OAUTH_TOKEN` от `claude setup-token` работает по уже оплаченной
   подписке, `ANTHROPIC_API_KEY` тарифицируется отдельно. Ralph останавливается
   до запуска процесса, если нет ни одной.

   `maxTurns` не переносится между CLI числом: Codex считает каждый item, включая
   выполненные команды, Claude — ответы модели. Одно и то же значение ограничит
   разный объём работы.
6. Убедиться, что рабочее дерево чистое либо содержит только незавершённую
   работу, сохранённую самим Ralph для восстановления.

`--check` дополнительно проверяет frontmatter всех project-local
`.agents/skills/*/SKILL.md` и печатает эффективные модель и reasoning effort для
каждой роли, а также израсходованный бюджет итераций из сохранённого state.

В режиме `--run` скрипт сам перейдёт на ветку текущей фазы. Если её
нет локально, он подключит удалённую ветку или создаст новую от её
`origin/baseBranch`. При грязном рабочем дереве это запрещено. `--check` ничего
не переключает и не создаёт.

## Изоляция проверок

Весь набор `preflightScripts` + `validationScripts` выполняется в **одном**
непривилегированном контейнере без сети и host credentials: он один раз
поднимает временный PostgreSQL, применяет migrations, разворачивает snapshot и
выполняет scripts по очереди, останавливаясь на первой ошибке. Перед каждым
script печатается маркер `RALPH_VALIDATION_SCRIPT=<name>`, поэтому упавший
script назван в отчёте. Web E2E идёт в Playwright CI-режиме с одним worker.

Успешный прогон пишет attestation в
`.git/ralph-loop/validation-attestations.json` с ключом из байтов source, списка
scripts и digest образа. Повторная валидация того же дерева пропускается; любое
изменение входов, обнаруженная подделка control-файла или неразрешимый digest
образа делают запись непригодной, и проверки выполняются заново.

## Несколько фаз

`phases` — упорядоченный массив независимых фаз:

```json
"phases": [
  { "milestone": "Phase 1: Core Profile API", "branch": "features/profile-phase-1" },
  { "milestone": "Phase 2: Profile UI", "branch": "features/profile-phase-2", "baseBranch": "master" }
]
```

В режиме `--run` Ralph полностью завершает текущую фазу: закрывает её issues,
создаёт отдельный PR, получает чистый milestone-review и закрывает milestone.
Только после этого он сохраняет следующий `phaseIndex`, обнуляет счётчик
`maxIterations` для новой фазы, переключает ветку и продолжает работу. После
сбоя следующий запуск возобновляет сохранённую фазу, а не начинает план заново.

Фазы считаются независимыми и по умолчанию создаются от глобального
`baseBranch`. Если следующая фаза действительно зависит от ещё не смерженной
предыдущей ветки, её `baseBranch` нужно задать явно; Ralph не выполняет merge PR
автоматически. Названия milestone и веток в массиве должны быть уникальными.
Верхнеуровневые `milestone` и `branch` больше не читаются: одна фаза
записывается массивом из одного элемента. Конфиг без `phases` отклоняется при
загрузке.

## Актуальность базы

Разработка всегда идёт на актуальной базе. В начале фазы Ralph вливает
`origin/baseBranch` в её рабочую ветку и проверяет результат **полным** набором
`validationScripts`. Порядок важен: слияние выполняется после переключения на
ветку и до снятия слепка control plane, иначе принесённые базой правки
`.agents/**` или `scripts/ralph/**` выглядели бы подделкой доверенных файлов.

Ветка фазы создаётся от базы один раз, а дальше база живёт своей жизнью:
родительская фаза дорабатывается по замечаниям своего ревью, база принимает
чужие merge. Без слияния агент строит поверх устаревшего кода и не знает об
этом — на фазе 6 это стоило второй реализации того, что фаза 5 уже сделала:
обе ветки независимо получили meeting-scoped идентификатор аватара загрузчика,
и свести их пришлось вручную. `verifyBaseHistory` такое не ловит: общий предок
у разошедшихся веток остаётся, и проверка проходит молча.

Слияние пропускается, когда в дереве лежит незавершённая работа: это
восстановление после сбоя, и чужие изменения поверх незаконченного diff смешали
бы две работы в одном коммите. База подождёт до чистого дерева.

Конфликт с базой останавливает прогон: слияние отменяется через `merge --abort`,
дерево остаётся нетронутым, и разрешает конфликт человек. Автоматическое
разрешение выбирало бы между двумя реализациями вслепую, а именно этот выбор и
есть содержание конфликта. Упавшая после слияния валидация останавливает прогон
так же — но слияние при этом уже в истории ветки, и разбирать его нужно вручную.

Выключается полем `"syncBaseBranch": false`. Имеет смысл только там, где базу
двигают намеренно и ветка обязана остаться на прежней. Учтите цену: каждое
слияние добавляет в ветку merge-коммит, а он сбрасывает инкрементальное
milestone-ревью на полный аудит.

## Что происходит в одной итерации

1. Скрипт получает title, body и URL следующей issue.
2. В prompt подставляются issue, branch, milestone, лимит попыток и содержимое
   `.agents/ralph-rules.md`. Операторская документация в prompt не попадает.
3. Агент на модели из `developmentModel` запускается с полным доступом к
   файловой системе (`danger-full-access` у Codex, `bypassPermissions` у Claude):
   может редактировать и создавать файлы во всём рабочем дереве, реализует
   задачу по TDD, запускает только затронутые тесты, делает self-review. GitHub
   credentials ему не передаются, а изменения доверенных control-файлов Ralph и
   `AGENTS.md` оркестратор отклоняет до commit. Оркестратор считает уникальные
   шаги сессии и принудительно завершает агента при попытке превысить `maxTurns`.
   Полный доступ выбран намеренно: с ограниченной песочницей сессии циклически
   падали на записи вне рабочего дерева. Изоляцию даёт временный HOME без
   пользовательского конфига, скиллов и credentials, а не флаг песочницы.
4. Скрипт проверяет ветку и изменения, запускает полный набор проверок вне
   development sandbox в изолированном validation-контейнере, создаёт ровно один
   commit и отправляет его в удалённую ветку. Orchestrated commit использует
   временный пустой `core.hooksPath`: пользовательский host hook не дублирует уже
   пройденную canonical validation и не зависит от схемы локальной dev-БД. Ручные
   commit по-прежнему используют обычные Git hooks.
5. Только для уже опубликованного commit отдельная read-only сессия агента на
   модели `review.model` проверяет его и пишет структурированный результат в
   `.agents/last-review.json`.
6. Только после успешного review оркестратор закрывает issue через GitHub CLI.
7. При замечаниях issue остаётся открытой, в неё добавляется комментарий, и
   `--run` передаёт её Terra на следующей итерации. Техническая ошибка review
   повторяется согласно `runtime.reviewRetryAttempts`; если попытки исчерпаны,
   commit сохраняется в состоянии issue, и следующий `--run` повторит проверки и
   review без повторной реализации. Служебная отметка в issue не считается
   доказательством успеха и удаляется перед закрытием.

Каждый созданный Ralph commit содержит trailer `Ralph-Issue: #<number>`. Если
процесс был остановлен, а готовый commit появился отдельно, следующий запуск
свяжет его с issue и сразу перейдёт к проверкам и review без повторной
Terra-сессии. Автоматически принимается только commit новее последнего изменения
issue: старый trailer после нового review или ручного reopen не переиспользуется.

## Что происходит после завершения milestone

1. Когда открытых issues больше нет, скрипт выполняет финальные проверки,
   отправляет ветку и создаёт draft PR (либо находит уже открытый PR этой ветки).
2. Модель из `milestoneReview.model` проверяет целостность всей текущей фазы.
   Diff относительно `baseBranch` используется как доказательство, но границы
   review задаются title и description текущего milestone: накопленные изменения
   других фаз не должны превращаться в его issues.
3. В review учитываются архитектура, взаимодействие изменений из разных issues,
   безопасность, производительность, масштабирование, тесты и соответствие PRD.
4. Sol возвращает структурированный JSON в `.agents/last-milestone-review.json`;
   только оркестратор публикует его в PR через GitHub CLI.
5. При FAIL оркестратор создаёт по одной issue на каждый **продуктовый** finding.
   Повторный finding не создаёт дубликат: открытая issue используется снова,
   закрытая переоткрывается. Новые issues сразу попадают во внутреннюю очередь,
   поэтому цикл не зависит от задержки GitHub API. За один review создаётся не
   больше `milestoneReview.maxFindings` задач. Findings по `.agents/**`,
   `scripts/ralph/**` и любым `AGENTS.md` исключаются из продуктовой очереди и
   разбираются вручную в чате настройки Ralph.
6. Terra последовательно исправляет review-issues, ветка отправляется заново, Sol
   проверяет новый SHA. Со второго круга ревью инкрементально: оркестратор
   находит последнее опубликованное milestone-ревью этого PR по маркеру,
   передаёт его текст дословно и сужает инвентарь изменений до коммитов после
   уже проверенного head; ревьюеру предписано проверить закрытие прежних
   findings, полностью проверить только новые изменения и не переаудировать
   признанное чистым. Полный аудит остаётся на первом круге, при
   `"milestoneReview": {"incremental": false}` и в каждом случае, когда сузить
   круг небезопасно: прежний head не предок текущего (force-push), в диапазоне
   есть merge из базы («Update branch» на PR затянул бы чужую работу в
   инвентарь), прежнее ревью обрезано лимитом `maxFindings` (отрезанные findings
   живут только в обещании «deferred to the next full review») или сделано
   другой моделью либо effort — их смена остаётся способом заказать свежий
   полный аудит. Плата за инкремент: интеграция между старыми и новыми срезами
   проверяется одним ограниченным проходом, а полнота реализации требований
   milestone — только на первом круге. Цикл продолжается до PASS либо
   до достижения `maxIterations`/`maxTurns`.
7. После чистого PASS оркестратор закрывает GitHub milestone. PR остаётся draft:
   решение о merge принимает человек. Если в `phases` есть следующий элемент,
   Ralph сохраняет переход и запускает его в отдельной ветке.
8. Повторный `--run` не расходует токены на уже опубликованный PASS того же SHA:
   скрипт ищет в PR скрытый маркер с моделью, effort и SHA. После нового commit
   SHA изменится, и Sol выполнит review заново.

## Команды

```powershell
# Только проверить конфиг, GitHub, milestone, ветку, skills и бюджет
node scripts/ralph/ralph-loop.mjs --check

# Выполнить issues, создать draft PR и запустить итоговый Sol-review
node scripts/ralph/ralph-loop.mjs --run

# Ровно одна issue и остановка: то же --run с "stopAfterFirstIssue": true
# в .agents/ralph.config.json. PR и milestone-review при этом не создаются.
```

Для первого тренировочного запуска включить `stopAfterFirstIssue` и вручную проверить
изменения и commit. Для AFK запускайте `--run` из чистой консоли в корне
репозитория. Один процесс сам проходит очереди всех настроенных фаз, циклы
исправлений, итоговые review и закрытие milestones; параллельно второй Ralph не
запускайте.

## Восстановление AFK-запуска

Ralph хранит lock в `.git/ralph-loop/run.lock`, состояние в
`.git/ralph-loop/state.json`, журнал в `.git/ralph-loop/run.log` и attestations в
`.git/ralph-loop/validation-attestations.json`. Они не попадают в commit и
остаются локально между запусками. Lock не позволяет двум процессам одновременно
менять одну ветку; устаревший lock снимается только после проверки, что
записанный процесс уже завершён.

State фиксирует `phaseIndex`, лимит итераций текущей фазы, issue, commit и стадию
pipeline. Если процесс завершился после реализации, commit, push или во время
review, следующий `--run` продолжает с подтверждённой стадии, а не реализует
задачу повторно. Оставленный Ralph dirty tree восстанавливается только при
совпадении с сохранённым состоянием. Любые посторонние незакоммиченные изменения
считаются небезопасными и останавливают запуск — не очищайте их автоматически
через `reset`/`restore`.

При сбое проверки в state сохраняется ограниченная сводка (команда, exit code,
упавшие проверки, основная ошибка, значимые строки, артефакты), и именно она
уходит в recovery prompt. Полный вывод остаётся только в `run.log`.

Все внешние команды имеют wall-clock timeout из секции `runtime`: обычные
команды — `commandTimeoutMs`, сборка validation-образа — `validationTimeoutMs`,
весь прогон проверок в контейнере — `validationRunTimeoutMs`, сессии агента —
`agentTimeoutMs`. На Windows отдельный command-runner завершает всё дерево
зависшей команды, чтобы после timeout не оставались фоновые `npm`/тестовые
процессы. Временные сетевые ошибки GitHub/Git повторяются `networkRetryAttempts`
раз с экспоненциальной задержкой от `networkRetryBaseDelayMs`; число повторов
review задаёт `reviewRetryAttempts`. `maxPages` ограничивает безопасную
постраничную выборку GitHub, не обрезая очередь первой страницей.

## Защита от ошибок

Скрипт останавливается с явным сообщением при любом нарушении своих инвариантов:
некорректная конфигурация, несовпадение ветки, незакоммиченная работа перед
`--run`, отсутствие изменений или превышение `maxTurns` у агента,
самовольная смена ветки/commit/issue, невозможность создать ровно один commit,
техническая ошибка review, FAIL milestone-review без findings, исчерпание
`maxIterations`, wall-clock timeout, ошибка GitHub/Git/агента. Диагностику берите
из самого сообщения и `run.log`, а не из этого списка. `run.log` содержит только
текущий прогон: при старте предыдущий переименовывается в `run-<время>.log`, и
рядом хранятся последние пять.

Пока идёт `--run`, не работайте с этим репозиторием второй сессией Claude Code и
не запускайте `npm run test:ralph` на хосте. Обе вещи трогают контрольный контур:
Claude Code пишет в `.claude/**` (например `settings.local.json` после
подтверждения доступа), а часть тестов Ralph временно перезаписывает
`.agents/ralph.config.json` и настоящие `AGENTS.md`. Набор доверенных файлов
снимается один раз при старте, и `assertTrustedControlFilesUnchanged` сверяет с
ним живое дерево перед каждым прогоном проверок — появившийся файл выглядит как
подделка. Сообщение при этом обвиняет AFK-сессию, хотя изменение внесли вы, а
починить его сама сессия не может: это её же контрольный контур.

Исключение — файлы, которые Claude Code ведёт сам и переписывает без участия
человека: они перечислены в `toolManagedClaudeFiles`
(`scripts/ralph/ralph-config.mjs`) и в доверенный набор не входят, потому что
инструкцией не являются, а их обновление посреди прогона останавливало бы Ralph
от постороннего события. Список закрытый: всё, что способно нести инструкцию —
агенты, скиллы, настройки, хуки, — остаётся доверенным, и добавлять туда файл
можно только доказав, что поведение будущей сессии он не меняет.

Git при этом видит меньше, чем контрольный контур: `.claude/agents/**`
версионируется, потому что задаёт, как и что ревьюится, а установленные скиллы
(`.claude/skills/**`, восстанавливаются из `skills-lock.json`), локальные
разрешения и lock планировщика игнорируются. Это разные механизмы: `.gitignore`
управляет содержимым репозитория, а доверенный набор собирается обходом
файловой системы и об игнорировании ничего не знает.

Тот же снимок объясняет отдельную ловушку: `.claude/**` лежит не на всех ветках.
Если запустить Ralph, когда HEAD на `master`, набор снимется без `.claude`, а
`verifyRepository` затем переключится на ветку фазы и материализует эти файлы —
прогон упадёт на «изменила набор доверенных файлов инструкций» ещё до контейнера.
Держите каталог на базовой ветке либо стартуйте с ветки фазы.

Перед закрытием issue, push и PR выполняются npm scripts из `validationScripts`.
В AFK-конфигурации обязательны `format:check`, `lint`, `build`, unit-тесты Ralph
и API/web E2E.

На отдельной issue набор сокращается до проверок, применимых к изменённым
файлам: правка Markdown проходит только `format:check` и не поднимает базу,
браузерная спека не запускает E2E API. Карта областей лежит в
`scripts/ralph/ralph-scope.mjs`; путь, которого в ней нет, возвращает полный
набор. Перед созданием PR полный набор выполняется всегда — сокращение
покрывает каждую issue по отдельности, а ветку целиком проверяет он.
Выключается полем `"scopedValidation": false`.

Поверх карты областей действует дешёвая дорожка для правок, не тронувших ни
одного токена кода: если изменение затрагивает только комментарии в исходниках
и Markdown, выполняются лишь `format:check`, `lint` и `build` — без тестов и без
базы. Сравниваются потоки токенов компилятора TypeScript, а не строки diff,
поэтому текст вида `// комментарий` внутри template literal распознаётся как
данные и дорожку не включает. Любая неуверенность — новый или удалённый файл,
незнакомое расширение — возвращает полный набор. Выключается полем
`"commentOnlyValidation": false`. Если хотя бы одна проверка не прошла, issue не закрывается и PR не
создаётся. Host pre-commit hooks не являются частью AFK proof: они могут
обращаться к локальной БД, отличающейся от проверяемого snapshot. Ralph отключает
их только для собственного commit после успешной изолированной validation;
проверенный staged tree затем обязан точно совпасть с tree созданного commit.

`--run` создаёт draft PR по умолчанию. Для обычного PR укажите
`"draftPullRequest": false`.

Лимит исправлений красных тестов задаётся полем `maxTestFixAttempts` (по
умолчанию 5). После лимита агент должен оставить диагностику в финальном
сообщении; issue остаётся открытой.

`maxTurns` применяется отдельно к сессии реализации и локальному review issue.
Для итогового review используется `milestoneReview.maxTurns`. `maxIterations`
ограничивает суммарное количество сессий реализации обычных и автоматически
созданных review-issues **в одной фазе**, включая перезапуски `--run`. Счётчик
обнуляется только после чистого PASS и сохранённого перехода к следующей фазе.
Это защита от обхода лимита перезапуском, роста контекста и бесконечного
fix-review цикла.

## Порог важности и отложенные замечания

Поле `reviewSeverityFloor` задаёт минимальную важность, при которой замечание
ревью блокирует работу. `"P3"` (умолчание кода) блокирует всё; `"P1"` — только
P0 и P1, а P2/P3 перестают отклонять issue, создавать milestone-задачи и мешать
закрытию milestone. Порог действует и на per-issue ревью, и на milestone-ревью;
управление критичностью — одно это поле в `.agents/ralph.config.json`.

Замечания ниже порога не теряются: каждое записывается отдельной GitHub issue с
label `ralph-deferred` и **без milestone**, поэтому в очередь Ralph оно не
попадает. Дубликаты не создаются: отпечаток замечания (важность, файл,
нормализованный title — без привязки к PR и кругу ревью) ищется в существующих
issues с этим label; закрытую человеком issue повторная находка не
переоткрывает. Соседние находки одного файла и одной полосы важности
группируются в одну issue тем же правилом, что и milestone-задачи.

Разбор отложенных issues — ручной: закрыть как wontfix, объединить с другой или
назначить milestone — после этого задачу берёт обычный цикл. Отказ GitHub при
записи отложенной issue не прерывает прогон: текст замечания уже опубликован в
комментарии ревью.

## Объём итогового PR

Milestone-review использует весь накопительный diff `branch` относительно
`baseBranch` как контекст, но создаёт findings только по требованиям title и
description текущего milestone и необходимым им интеграциям. Это защищает
накопительную ветку от задач чужих фаз. Новую фазу всё равно рекомендуется
вести в отдельной ветке от корректной базы: prompt-ограничение не переписывает
историю и не делает накопительный PR удобным для ручного merge-review.
