# Ralph Loop — операторская документация

Ralph берёт issues одной вехи (milestone) GitHub, реализует их автономными
сессиями агента, прогоняет проверки в изолированном контейнере, коммитит,
отправляет ветку и получает ревью. Здесь — настройка, запуск и восстановление.

> Контракт автономной сессии — отдельный файл `.agents/ralph-rules.md`, который
> оркестратор целиком подставляет в prompt. AFK-агент не должен читать эту
> страницу: требований к реализации в ней нет, а стоит она сотни строк входного
> контекста на каждую issue.

Циклом управляет `scripts/ralph/ralph-loop.mjs`. Он вместе с `.agents/**`,
`.claude/**` и всеми `AGENTS.md` и `CLAUDE.md` образует защищённый control
plane: продуктовый AFK-цикл никогда их не изменяет, Ralph настраивает оператор
вручную.

## Что нужно на машине

- Node.js — на нём работают скрипты цикла.
- Git и `gh` с выполненным `gh auth status`.
- Docker: `docker version` должен отвечать.
- CLI выбранного агента. Поле `agentCli`: `codex` (по умолчанию) или `claude`.
  Claude-сессия запускается с изолированным HOME, куда OAuth-состояние CLI не
  переносится, поэтому в окружении оператора должна быть одна из двух
  переменных, и по деньгам они не равнозначны: `CLAUDE_CODE_OAUTH_TOKEN` от
  `claude setup-token` работает по уже оплаченной подписке, `ANTHROPIC_API_KEY`
  тарифицируется отдельно. Без обеих Ralph останавливается до запуска процесса.

## Настройка под проект

1. **Проверки.** `preflightScripts` и `validationScripts` в
   `.agents/ralph.config.json` — готовые однострочные команды оболочки, а не
   имена скриптов пакетного менеджера. Контейнер выполняет каждую строку как
   есть из корня репозитория и останавливается на первой ошибке:
   `npm run lint`, `pytest -q`, `go test ./...`. Preflight готовит окружение,
   validation доказывает работоспособность изменения.
2. **Образ проверок.** `validationContainer` задаёт имя образа и путь к
   Dockerfile; по умолчанию это `scripts/ralph/Dockerfile.validation`. Кит
   ставит туда только git, дальше — слот проекта: базовый образ, зависимости,
   при необходимости база данных или браузер. Сеть внутри прогона выключена,
   поэтому всё нужное образ должен получить при сборке.
3. **Инструкции проекту.** Положите в корень `AGENTS.md` и `CLAUDE.md` из
   `templates/`: агент читает их как контракт задачи. Оттуда же —
   `templates/pre-commit` и `templates/lint-staged.config.mjs`, если нужен хук
   перед ручным коммитом.
4. **Фазы.** `phases` — упорядоченный массив; для каждой фазы **точное** имя
   вехи GitHub и отдельная рабочая ветка:

   ```json
   "phases": [
     { "milestone": "Phase 1: API", "branch": "ralph/phase-1" },
     { "milestone": "Phase 2: UI", "branch": "ralph/phase-2", "baseBranch": "main" }
   ]
   ```

   Фазы независимы и создаются от глобального `baseBranch`. Если следующая
   зависит от ещё не смерженной предыдущей, задайте её `baseBranch` явно: merge
   PR Ralph не делает. Имена вех и веток уникальны, конфиг без `phases`
   отклоняется при загрузке.
5. **Модели.** `developmentModel`, `developmentEffort`, `review.model`,
   `milestoneReview.model`. Словарь `effort` у CLI разный: Codex принимает
   minimal/low/medium/high, Claude — low/medium/high/xhigh/max. `maxTurns` между
   CLI тоже не переносится числом: Codex считает каждый item, включая
   выполненные команды, Claude — ответы модели.
6. **Issues.** Каждая issue вехи должна быть самостоятельно завершаемым зелёным
   срезом: зависимые test-only и implementation-only задачи объединяйте в одну,
   иначе строгий per-issue commit/review намеренно остановится. При
   `autoApproveConfiguredIssues=true` закоммиченный план фиксирует точные
   title/body issues доверенных авторов (`trustedIssueAuthors`) в локальном
   состоянии до старта; последующие правки в GitHub прогон остановят. При
   `false` каждую issue добавляют вручную в `approvedIssueSnapshotsFile`.

## Команды

```powershell
# Проверить конфиг, GitHub, веху, ветку, скиллы и остаток бюджета итераций
node scripts/ralph/ralph-loop.mjs --check

# Выполнить issues, создать draft PR и запустить итоговое ревью вехи
node scripts/ralph/ralph-loop.mjs --run
```

`--check` ничего не переключает и не создаёт. `--run` сам перейдёт на ветку
текущей фазы, подключит удалённую или создаст новую от `origin/baseBranch` —
при чистом рабочем дереве. Для первого запуска включите
`"stopAfterFirstIssue": true` и проверьте изменения и commit руками: PR и ревью
вехи при этом не создаются. Обычный PR вместо draft —
`"draftPullRequest": false`. Параллельно второй Ralph не запускайте.

## Изоляция проверок

Весь набор preflight + validation выполняется в **одном** непривилегированном
контейнере без сети, без Docker-сокета и без host credentials, на read-only
образе с примонтированным снимком только отслеживаемых файлов. Перед каждой
командой печатается маркер `RALPH_VALIDATION_SCRIPT=<команда>`, поэтому упавшая
команда названа в отчёте без разбора её вывода.

Успешный прогон пишет attestation в
`.git/ralph-loop/validation-attestations.json` с ключом из байтов исходников,
списка команд и digest образа. Повторная валидация того же дерева пропускается;
любое изменение входов, обнаруженная подделка control-файла или неразрешимый
digest делают запись непригодной, и проверки выполняются заново.

Host pre-commit hooks частью доказательства не являются: они ходят в локальное
окружение, отличное от проверенного снимка. Для собственного commit Ralph
отключает их временным пустым `core.hooksPath` после успешной изолированной
валидации, и проверенный staged tree обязан совпасть с tree созданного commit.
Ручные commit по-прежнему используют обычные Git hooks.

## Актуальность базы

В начале фазы Ralph вливает `origin/baseBranch` в рабочую ветку и проверяет
результат **полным** набором. Слияние идёт после переключения на ветку и до
снятия снимка control plane, иначе принесённые базой правки control-файлов
выглядели бы подделкой. Без слияния агент строит поверх устаревшего кода и не
знает об этом: две ветки независимо реализуют одно и то же, а проверка истории
базы такое не ловит — общий предок у разошедшихся веток остаётся.

Слияние пропускается, когда в дереве лежит незавершённая работа: это
восстановление после сбоя, и чужие изменения смешали бы две работы в одном
коммите. Конфликт останавливает прогон: `merge --abort`, дерево нетронуто,
разрешает человек — автоматическое разрешение выбирало бы между двумя
реализациями вслепую. Упавшая после слияния валидация останавливает прогон так
же, но слияние уже в истории ветки.

Выключается полем `"syncBaseBranch": false`. Цена слияния: merge-коммит
сбрасывает инкрементальное ревью вехи на полный аудит.

## Одна итерация

1. Скрипт получает title, body и URL следующей issue.
2. В prompt подставляются issue, ветка, веха, лимиты и содержимое
   `.agents/ralph-rules.md`. Эта страница в prompt не попадает.
3. Агент на `developmentModel` работает с полным доступом к файловой системе
   (`danger-full-access` у Codex, `bypassPermissions` у Claude). Полный доступ
   выбран намеренно: с ограниченной песочницей сессии циклически падали на
   записи вне рабочего дерева. Изоляцию даёт временный HOME без
   пользовательского конфига, скиллов и credentials, а не флаг песочницы.
   GitHub credentials агенту не передаются, правки control-файлов оркестратор
   отклоняет до commit, а при попытке превысить `maxTurns` сессия завершается.
4. Оркестратор проверяет ветку и изменения, запускает полный набор проверок в
   контейнере, создаёт ровно один commit и отправляет его.
5. Отдельная read-only сессия на `review.model` проверяет уже опубликованный
   commit и пишет результат в `.agents/last-review.json`.
6. Только после чистого ревью issue закрывается через GitHub CLI.
7. При замечаниях issue остаётся открытой с комментарием и вернётся на следующей
   итерации. Техническая ошибка ревью повторяется `runtime.reviewRetryAttempts`
   раз; после исчерпания commit сохраняется в состоянии issue, и следующий
   `--run` повторит проверки и ревью без повторной реализации.

Если ревью отклонило работу по одной issue `maxReviewFixAttempts` раз подряд,
issue откладывается до конца прогона: работа остаётся в ветке, замечания — в её
теле. Бюджет итераций общий на фазу, и без этого предела одна issue съедает его
целиком, ни разу не дойдя до нуля замечаний.

Каждый commit Ralph содержит trailer `Ralph-Issue: #<number>`. Если процесс
остановили, а готовый commit появился отдельно, следующий запуск свяжет его с
issue и перейдёт сразу к проверкам. Принимается только commit новее последнего
изменения issue.

## Завершение вехи

1. Когда открытых issues не осталось, выполняются финальные проверки, ветка
   отправляется и создаётся draft PR (либо находится уже открытый).
2. Модель `milestoneReview.model` проверяет целостность фазы: архитектуру,
   взаимодействие изменений разных issues, безопасность, производительность,
   тесты, соответствие требованиям. Diff относительно `baseBranch` — контекст,
   но границы ревью задают title и description вехи, чтобы накопленные изменения
   других фаз не превращались в её findings.
3. Результат уходит в `.agents/last-milestone-review.json`; публикует его в PR
   только оркестратор.
4. При FAIL создаётся по одной issue на каждый **продуктовый** finding, не
   больше `milestoneReview.maxFindings` за круг. Повторный finding переиспользует
   открытую issue или переоткрывает закрытую. Findings по путям control plane в
   продуктовую очередь не попадают и разбираются вручную.
5. Со второго круга ревью инкрементально: прежний текст передаётся дословно, а
   инвентарь сужается до коммитов после проверенного head. Полный аудит остаётся
   на первом круге, при `"milestoneReview": {"incremental": false}` и там, где
   сузить круг небезопасно: force-push, merge из базы в диапазоне, обрезка
   прежнего ревью лимитом findings, смена модели или effort.
6. После чистого PASS веха закрывается, PR остаётся draft — решение о merge
   принимает человек. Затем Ralph переходит к следующей фазе в её ветке.

## Восстановление

Lock, состояние, журнал и attestations лежат в `.git/ralph-loop/` и в commit не
попадают. Lock не даёт двум процессам менять одну ветку; устаревший снимается
после проверки, что записанный процесс завершён.

Состояние фиксирует номер фазы, лимит итераций, issue, commit и стадию цикла:
следующий `--run` продолжает с подтверждённой стадии, а не реализует задачу
заново. Оставленное Ralph грязное дерево восстанавливается только при совпадении
с сохранённым состоянием; посторонние незакоммиченные изменения останавливают
запуск — не чистите их через `reset`/`restore`.

При сбое проверки сохраняется ограниченная сводка (команда, код возврата,
упавшие проверки, основная ошибка, артефакты), и в recovery prompt уходит она.
Полный вывод остаётся в `run.log`, который содержит только текущий прогон:
предыдущий переименовывается в `run-<время>.log`, рядом хранятся последние пять.

Все внешние команды имеют wall-clock timeout из секции `runtime`: обычные
команды — `commandTimeoutMs`, сборка образа — `validationTimeoutMs`, прогон
проверок в контейнере — `validationRunTimeoutMs`, сессии агента —
`agentTimeoutMs`. На Windows отдельный command-runner завершает всё дерево
зависшей команды. Сетевые ошибки GitHub и Git повторяются `networkRetryAttempts`
раз с экспоненциальной задержкой от `networkRetryBaseDelayMs`; `maxPages`
ограничивает постраничную выборку GitHub, не обрезая очередь первой страницей.

## Защита от ошибок

Скрипт останавливается с явным сообщением при нарушении своих инвариантов:
некорректная конфигурация, несовпадение ветки, незакоммиченная работа перед
`--run`, отсутствие изменений или превышение `maxTurns`, самовольная смена
ветки, commit или issue, невозможность создать ровно один commit, техническая
ошибка ревью, FAIL ревью вехи без findings, исчерпание `maxIterations`, timeout,
ошибка GitHub, Git или агента. Диагностику берите из самого сообщения и
`run.log`.

Пока идёт `--run`, не работайте с репозиторием второй сессией Claude Code и не
запускайте на хосте тесты самого Ralph. Обе вещи трогают контрольный контур:
Claude Code пишет в `.claude/**` (например `settings.local.json`), а тесты
временно перезаписывают `.agents/ralph.config.json` и настоящие `AGENTS.md`.
Набор доверенных файлов снимается один раз при старте и сверяется с живым
деревом перед каждым прогоном проверок: появившийся файл выглядит как подделка,
сообщение обвиняет AFK-сессию, а починить это она не может — это её же
контрольный контур.

Исключение — файлы, которые Claude Code ведёт сам и переписывает без участия
человека: они перечислены в `toolManagedClaudeFiles`
(`scripts/ralph/ralph-config.mjs`) и в доверенный набор не входят, потому что
инструкцией не являются. Список закрытый: всё, что способно нести инструкцию —
агенты, скиллы, настройки, хуки, — остаётся доверенным, и добавлять туда файл
можно, только доказав, что поведение будущей сессии он не меняет.

Отсюда отдельная ловушка: `.claude/**` лежит не на всех ветках. Если запустить
Ralph с HEAD на базовой ветке без этого каталога, набор снимется без него, а
переключение на ветку фазы материализует файлы — прогон упадёт на «изменила
набор доверенных файлов инструкций» ещё до контейнера. Держите каталог на
базовой ветке либо стартуйте с ветки фазы.

## Порог важности и отложенные замечания

`reviewSeverityFloor` задаёт минимальную важность, при которой замечание
блокирует работу. `"P3"` блокирует всё; `"P1"` — только P0 и P1, а P2 и P3
перестают отклонять issue, создавать задачи вехи и мешать её закрытию. Порог
действует и на ревью issue, и на ревью вехи.

Замечания ниже порога не теряются: каждое записывается отдельной GitHub issue с
label `ralph-deferred` и **без вехи**, поэтому в очередь Ralph не попадает.
Дубликаты не создаются: отпечаток замечания (важность, файл, нормализованный
заголовок) ищется среди issues с этим label, закрытую человеком issue повторная
находка не переоткрывает. Соседние находки одного файла и одной полосы важности
группируются в одну issue.

Разбор отложенных issues ручной: закрыть как wontfix, объединить или назначить
веху — после этого задачу берёт обычный цикл. Отказ GitHub при записи отложенной
issue прогон не прерывает: текст замечания уже опубликован в комментарии ревью.
