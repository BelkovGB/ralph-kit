# Ralph Loop — операторская документация

Ralph берёт issues одного milestone GitHub, реализует их автономными сессиями
агента, прогоняет проверки в изолированном контейнере, коммитит, отправляет
ветку и получает ревью. Здесь — запуск, наблюдение и восстановление.

Что копировать в проект, что переписать под свой стек и что решить до первого
прогона — в `README.md` набора Ralph. Там же список программ, которые нужны
на машине.

> Контракт автономной сессии лежит в `.agents/ralph-rules.md`: оркестратор
> подставляет его в prompt целиком. AFK-агент эту страницу не читает —
> требований к реализации в ней нет, а стоит она сотни строк входного контекста
> на каждую issue.

Циклом управляет `scripts/ralph/ralph-loop.mjs`. Вместе с ним защищён весь
control plane — файлы, которые задают поведение будущей сессии агента:

- все модули и оба `.sh` из `scripts/ralph/` и Dockerfile проверок;
- из `.agents/` — `ralph.config.json`, `ralph-rules.md`, файл одобренных issues,
  схемы ревью включённых ролей и эта страница;
- `.claude/**` целиком;
- все `AGENTS.md` и `CLAUDE.md` репозитория.

AFK-цикл эти файлы не изменяет, Ralph настраивает оператор вручную. Файлы
`.agents/` перечислены поимённо, поэтому новый файл в этом каталоге в список не
попадёт: сканирование каталога приняло бы за доверенный любой подложенный.

## Настройка под проект

README перечисляет, что переписать. Ниже — то, что легко задать неправильно.

1. **Выключатель.** `"active": false` останавливает оба режима первой же
   строкой: скрипт печатает «Ralph Loop выключен: active=false» и выходит. В
   примере конфига стоит `false`, поэтому первый `--run` без правки этого поля
   не делает ничего.
2. **Проверки.** `preflightScripts` и `validationScripts` — готовые однострочные
   команды оболочки, а не имена скриптов пакетного менеджера. Контейнер
   выполняет каждую строку как есть из корня репозитория и останавливается на
   первой ошибке: `npm run lint`, `pytest -q`, `go test ./...`. Preflight
   готовит окружение, validation доказывает работоспособность изменения. Оба
   списка пустые — контейнер не поднимается вовсе, и Docker не нужен.
3. **Фазы.** `phases` — упорядоченный массив; для каждой фазы **точное** имя
   milestone GitHub и отдельная рабочая ветка:

   ```json
   "phases": [
     { "milestone": "Phase 1: API", "branch": "ralph/phase-1" },
     { "milestone": "Phase 2: UI", "branch": "ralph/phase-2", "baseBranch": "main" }
   ]
   ```

   Фазы независимы и создаются от глобального `baseBranch`. Если следующая
   зависит от ещё не смерженной предыдущей, задайте её `baseBranch` явно: merge
   pull request Ralph не делает. Имена milestone и веток уникальны, конфиг без
   `phases` отклоняется при загрузке.
4. **Модели.** `developmentModel`, `developmentEffort`, `review.model`,
   `milestoneReview.model`. Словарь effort у CLI разный: Codex принимает
   minimal/low/medium/high, Claude — low/medium/high/xhigh/max. `maxTurns` между
   CLI тоже не переносится числом: Codex считает каждый item, включая
   выполненные команды, Claude — ответы модели.
5. **Issues.** Одна issue — одна задача, которую можно завершить целиком: после
   неё проверки проходят. Не делите задачу на «написать тесты» и «написать
   код»: Ralph коммитит и ревьюит каждую issue отдельно и остановится на той,
   что сама по себе не работает. При `autoApproveConfiguredIssues=true` Ralph
   снимает снимок заголовка и тела issue доверенного автора
   (`trustedIssueAuthors`) в тот момент, когда берёт её в работу, и хранит его
   в локальном состоянии: правка issue в GitHub после этого момента
   останавливает прогон. При `false` каждую issue добавляют вручную в
   `approvedIssueSnapshotsFile`.

## Команды

Что делает каждая команда, когда её звать и чего она не делает — вкладка
«Команды» в пульте. Здесь то, чего на ней нет.

`--check` печатает номер фазы, репозиторий, milestone и число открытых issues,
текущую ветку и чистоту дерева, бюджет итераций, лимиты шагов и исправлений,
модели разработки и обоих ревью, путь к файлу правил и заголовок следующей
issue.

`--run` сам перейдёт на ветку текущей фазы, подключит удалённую или создаст новую
от `origin/baseBranch` — при чистом рабочем дереве. Для первого запуска включите
`"stopAfterFirstIssue": true`: Ralph выполнит одну issue целиком — commit, push,
ревью и закрытие issue, — но pull request и ревью milestone не создаст. Обычный
pull request вместо draft — `"draftPullRequest": false`. Параллельно второй Ralph
не запускайте.

## Пульт

Вкладок три: «Расход», «Настройки» и «Команды»; что показывает каждая и чего
пульт не умеет — в `README.md`. Здесь операторское.

- Страница поднимается на `127.0.0.1`, порт — первый свободный начиная с 4599.
  Ctrl+C останавливает пульт.
- Адрес несёт разовый ключ, новый на каждый запуск: из старой вкладки и с
  другого устройства страница не работает.
- Пульт меняет один файл — `.agents/ralph.config.json`. Резервная копия и
  временный файл записи ложатся в `.git/ralph-loop`, чтобы не остаться мусором
  в рабочем дереве.
- `state.json` и лок пульт не трогает, issues не создаёт.
- Пока прогон идёт, форма заблокирована, а POST настроек отклоняется. Конфиг
  Ralph читает один раз при старте прогона, но хеш этого файла входит в список
  доверенных и сверяется перед каждым прогоном проверок: правка под ногами
  выглядит как подделка control plane и обрывает текущую задачу. Изменения
  вступают в силу со следующего прогона.

## Изоляция проверок

Ralph поднимает один контейнер и выполняет в нём подготовку и проверки. У
контейнера нет сети, нет доступа к Docker и к вашим ключам. Образ он не меняет,
а внутрь кладёт копию только тех файлов, которые лежат в Git. Перед каждой
командой печатается маркер `RALPH_VALIDATION_SCRIPT=<команда>`, поэтому упавшая
команда названа в отчёте без разбора её вывода.

Успешный прогон пишет в `.git/ralph-loop/validation-attestations.json`
attestation — отметку об успешной проверке: по ней Ralph не гоняет проверки
второй раз для того же дерева. Ключ отметки собран из байтов исходников, списка
команд и digest образа, то есть отпечатка той сборки, на которой проверки
прошли. Отметка становится непригодной, и проверки идут заново, когда изменился
любой из этих входов, когда обнаружена подделка control-файла и когда digest не
удалось получить.

Host pre-commit hooks частью доказательства не являются: они ходят в локальное
окружение, отличное от проверенного снимка. Для собственного commit Ralph
отключает их временным пустым `core.hooksPath` после успешной изолированной
валидации, и проверенный staged tree обязан совпасть с tree созданного commit.
Ручные commit по-прежнему используют обычные Git hooks.

## Актуальность базы

В начале фазы Ralph вливает `origin/baseBranch` в рабочую ветку и проверяет
результат **всеми** проверками. Слияние идёт после переключения на ветку и до
снятия снимка control plane, иначе принесённые базой правки control-файлов
выглядели бы подделкой. Без слияния агент строит поверх устаревшего кода и не
знает об этом: две ветки независимо реализуют одно и то же, а проверка истории
базы такое не ловит — общий предок у разошедшихся веток остаётся.

Слияние пропускается, когда база не ушла вперёд и когда в дереве лежит
незавершённая работа: последнее — восстановление после сбоя, и чужие изменения
смешали бы две работы в одном коммите. Конфликт останавливает прогон:
`merge --abort`, дерево нетронуто, разрешает человек — автоматическое разрешение
выбирало бы между двумя реализациями вслепую. Упавшая после слияния валидация
останавливает прогон так же, но слияние уже в истории ветки.

Выключается полем `"syncBaseBranch": false`. Цена слияния: merge-коммит
сбрасывает инкрементальное ревью milestone на полный аудит.

## Одна итерация

1. Скрипт получает title, body и URL следующей issue.
2. В prompt подставляются issue, ветка, milestone, лимиты и содержимое
   `.agents/ralph-rules.md`. Эта страница в prompt не попадает.
3. Агент на `developmentModel` работает с полным доступом к файловой системе
   (`danger-full-access` у Codex, `bypassPermissions` у Claude). Полный доступ
   выбран намеренно: с ограниченной песочницей сессии циклически падали на
   записи вне рабочего дерева. Изоляцию даёт временный HOME без
   пользовательского конфига, скиллов и credentials, а не флаг песочницы.
   GitHub credentials агенту не передаются, правки control-файлов оркестратор
   отклоняет до commit, а при попытке превысить `maxTurns` сессия завершается.
4. Оркестратор проверяет ветку и изменения, запускает все проверки в
   контейнере, создаёт ровно один commit и отправляет его.
5. Отдельная read-only сессия на `review.model` проверяет уже опубликованный
   commit и пишет результат в `.agents/last-review.json`.
6. Только после чистого ревью issue закрывается через GitHub CLI.
7. При замечаниях issue остаётся открытой с комментарием и вернётся на следующей
   итерации. Техническая ошибка ревью повторяется `runtime.reviewRetryAttempts`
   раз; после исчерпания commit сохраняется в состоянии issue, и следующий
   `--run` повторит проверки и ревью без повторной реализации.

Если ревью отклонило работу по одной issue `maxReviewFixAttempts` раз подряд,
issue откладывается до конца прогона: работа остаётся в ветке, замечания — в её
теле. Бюджет итераций общий на фазу, и без этого предела одна issue съедает его
целиком, ни разу не дойдя до нуля замечаний.

Бюджет кончился — Ralph останавливается **до** начала следующей issue, пишет в
журнал расхода строку с итогом `iteration-limit` и печатает, сколько issues
осталось открытыми. Pull request в этот момент не создаётся и не трогается: он
открывается только когда открытых issues не остаётся. Состояние сохранено,
поэтому достаточно увеличить `maxIterations` в конфиге — следующий `--run`
продолжит с того же места.

Каждый commit Ralph содержит trailer `Ralph-Issue: #<number>`. Если процесс
остановили, а готовый commit появился отдельно, следующий запуск свяжет его с
issue и перейдёт сразу к проверкам. Принимается только commit новее последнего
изменения issue.

## Завершение milestone

1. Когда открытых issues не осталось, выполняются финальные проверки, ветка
   отправляется и создаётся draft pull request (либо находится уже открытый).
2. Модель `milestoneReview.model` проверяет целостность фазы: архитектуру,
   взаимодействие изменений разных issues, безопасность, производительность,
   тесты, соответствие требованиям. Diff относительно `baseBranch` — контекст,
   но границы ревью задают title и description milestone, чтобы накопленные
   изменения других фаз не превращались в его findings.
3. Результат уходит в `.agents/last-milestone-review.json`; публикует его в
   pull request только оркестратор.
4. При FAIL создаётся по одной issue на каждый **продуктовый** finding, не
   больше `milestoneReview.maxFindings` за круг. Повторный finding переиспользует
   открытую issue или переоткрывает закрытую. Findings по путям control plane в
   продуктовую очередь не попадают и разбираются вручную.
5. Со второго круга ревью инкрементально: прежний текст передаётся дословно, а
   инвентарь сужается до коммитов после проверенного head. Полный аудит остаётся
   на первом круге, при `"milestoneReview": {"incremental": false}` и там, где
   сузить круг небезопасно: force-push, merge из базы в диапазоне, обрезка
   прежнего ревью лимитом findings, смена модели или effort.
6. После чистого PASS Ralph сверяет head pull request с отревьюенным коммитом и
   закрывает milestone. Pull request он не мержит и из черновика не выводит —
   решение принимает человек. Затем Ralph переходит к следующей фазе в её ветке.

Отложенные issues закрыть milestone не дают: Ralph печатает их номера, оставляет
milestone открытым и завершает прогон. Разберите замечания в теле этих issues и
запустите цикл снова.

## Журнал расхода

Каждая попытка пишет строку в `.git/ralph-loop/issue-metrics.json` и в консоль:
номер и заголовок issue, время по стадиям, число сессий, шагов и вызовов
инструментов, объём токенов и итог. Журнал хранит последние 200 записей и живёт
отдельно от `state.json`, который удаляется на успешном завершении.

Расход считается в токенах, а не в деньгах: на подписке доллары условны, а
прогон ограничивает пятичасовое окно, которое расходуется токенами. Сырые
счётчики складывать нельзя — чтение кэша даёт большинство токенов и малую часть
цены, — поэтому строка называет «базовые токены»: взвешенную сумму с разбивкой
на вход вне кэша, запись и чтение кэша, рассуждения и ответ. Цена от CLI
остаётся в записи, когда CLI её присылает; Codex её не отдаёт, и тогда строка
говорит, сколько сессий из скольких прислали телеметрию.

Итог попытки — одно из: `completed`, `review-failed`, `review-parked` (issue
отложена после отказов ревью подряд), `iteration-limit`, `validation-failed`,
`agent-failed`, `milestone-review` или код ошибки прогона. Ревью milestone идёт
отдельной записью без номера issue: его оплачивает прогон, а не последняя
задача.

## Восстановление

Lock, состояние, журналы и attestations лежат в `.git/ralph-loop/` и в commit не
попадают. Lock не даёт запустить второй Ralph в этом репозитории; устаревший
снимается после проверки, что записанный процесс завершён.

Состояние фиксирует номер фазы, лимит итераций, issue, commit и стадию цикла:
следующий `--run` продолжает с подтверждённой стадии, а не реализует задачу
заново. Оставленное Ralph грязное дерево восстанавливается только при совпадении
с сохранённым состоянием; посторонние незакоммиченные изменения останавливают
запуск — не чистите их через `reset`/`restore`.

При сбое проверки сохраняется ограниченная сводка (команда, код возврата,
упавшие проверки, основная ошибка, артефакты), и в recovery prompt уходит она.
Полный вывод остаётся в `run.log`, который содержит только текущий прогон:
предыдущий переименовывается с меткой времени в имени, рядом хранятся последние
пять.

Все внешние команды имеют wall-clock timeout из секции `runtime`: обычные
команды — `commandTimeoutMs`, сборка образа — `validationTimeoutMs`, прогон
проверок в контейнере — `validationRunTimeoutMs`, сессии агента —
`agentTimeoutMs`. На Windows отдельный command-runner завершает всё дерево
зависшей команды. Сетевые ошибки GitHub и Git повторяются `networkRetryAttempts`
раз с экспоненциальной задержкой от `networkRetryBaseDelayMs`; `maxPages`
ограничивает постраничную выборку GitHub, не обрезая очередь первой страницей.

## Защита от ошибок

Ralph останавливается и называет причину, когда:

- конфиг не проходит проверку;
- текущая ветка не совпадает с веткой фазы;
- перед `--run` в дереве лежит незакоммиченная работа;
- агент ничего не изменил или упёрся в `maxTurns`;
- агент сам сменил ветку, commit или issue;
- создать ровно один commit не удалось;
- ревью упало с технической ошибкой;
- ревью milestone вернуло FAIL без findings;
- бюджет `maxIterations` исчерпан;
- команда не уложилась в timeout;
- GitHub, Git или агент ответили ошибкой.

Диагностику берите из самого сообщения и `run.log`.

Пока идёт `--run`, не работайте с репозиторием второй сессией Claude Code и не
запускайте на хосте тесты самого Ralph. Обе вещи трогают контрольный контур:
Claude Code пишет в `.claude/**` (например `settings.local.json`), а тесты
временно перезаписывают `.agents/ralph.config.json` и настоящие `AGENTS.md`.
Список доверенных файлов снимается один раз при старте и сверяется с живым
деревом перед каждым прогоном проверок: появившийся файл выглядит как подделка,
сообщение обвиняет AFK-сессию, а починить это она не может — это её же
контрольный контур.

Исключение — файлы, которые Claude Code ведёт сам и переписывает без участия
человека: они перечислены в `toolManagedClaudeFiles`
(`scripts/ralph/ralph-config.mjs`) и доверенными не считаются, потому что
инструкцией не являются. Список закрытый: всё, что способно нести инструкцию —
агенты, скиллы, настройки, хуки, — остаётся доверенным, и добавлять туда файл
можно, только доказав, что поведение будущей сессии он не меняет.

Отсюда отдельная ловушка: `.claude/**` лежит не на всех ветках. Если запустить
Ralph с HEAD на базовой ветке без этого каталога, список снимется без него, а
переключение на ветку фазы материализует файлы — прогон упадёт на «изменила
набор доверенных файлов инструкций» ещё до контейнера. Держите каталог на
базовой ветке либо стартуйте с ветки фазы.

## Порог важности и отложенные замечания

`reviewSeverityFloor` задаёт минимальную важность, при которой замечание
блокирует работу. `"P3"` блокирует всё; `"P1"` — только P0 и P1, а P2 и P3
перестают отклонять issue, создавать задачи milestone и мешать его закрытию.
Порог действует и на ревью issue, и на ревью milestone.

Замечания ниже порога не теряются: каждое записывается отдельной GitHub issue с
label `ralph-deferred` и **без milestone**, поэтому в очередь Ralph не попадает.
Дубликаты не создаются: отпечаток замечания (важность, файл, нормализованный
заголовок) ищется среди issues с этим label, закрытую человеком issue повторная
находка не переоткрывает. Соседние находки одного файла и одной полосы важности
группируются в одну issue.
