# Ralph Loop — правила автономной сессии

## Как брать issue

- Прочитай title, body и все критерии готовности issue; сверь их с кодом,
  документацией и AGENTS.md.
- Работай только над issue #{issue_number}. Не включай в commit посторонние
  изменения.
- Не изменяй и не создавай `.agents/**`, `.claude/**`, `scripts/ralph/**` и любые
  `AGENTS.md`: это control plane Ralph, его настраивает оператор вручную вне
  продуктового цикла. `.claude/**` входит сюда потому, что Claude Code читает
  оттуда агентов, скиллы, настройки и хуки, то есть файл там управляет
  следующей сессией. Оркестратор отклонит такое изменение перед валидацией, и
  вся работа сессии пропадёт. Если issue требует таких изменений, остановись и
  сообщи блокер.
- Если требования противоречивы или небезопасны, не угадывай: остановись и
  опиши блокер.

## Границы полномочий

- Целевая ветка `{branch}` уже проверена оркестратором. Не переключай ветки и не
  создавай новых.
- Не выполняй команды, изменяющие Git: `git add`, `git commit`, `git restore`,
  `git stash`, merge, rebase, reset, force-push. Commit создаёт оркестратор.
- Не запускай `gh`, не изменяй issue и не создавай PR: GitHub — зона
  оркестратора, он работает с ним после проверок и независимого review.

## Реализация

- Лимит сессии — `{max_turns}` наблюдаемых шагов; при попытке превысить его
  оркестратор принудительно остановит сессию. Не расширяй объём задачи.
- Для изменений поведения используй TDD: сначала тест, падающий по ожидаемой
  причине, затем минимальная реализация. Для документации, конфигурации и
  рефакторинга без изменения поведения искусственный тест не создавай.
- После каждого финального изменения перезапускай затронутые тесты.
- Не ослабляй и не удаляй тесты ради зелёного результата.
- Если после `{max_test_fix_attempts}` осмысленных попыток тесты остаются
  красными, остановись. В финальном сообщении укажи, какая команда падает,
  ключевой фрагмент ошибки, что пробовалось и какой следующий шаг предлагается.

## Проверки внутри sandbox

- Запускай только минимальный релевантный набор тестов. Полный
  `validationScripts`, `test:ralph`, API и Web E2E оркестратор выполнит снаружи
  sandbox перед commit и review — не дублируй его.
- Исключение — форматирование: перед финальным сообщением из корня репозитория
  выполни `npx prettier --write` по изменённым тобой файлам. Это одна секунда у
  тебя, а для оркестратора несформатированный файл стоит полного прогона
  контейнера с PostgreSQL и миграциями, который падает на первом же скрипте.
- На Windows вызывай npm через `npm.cmd`: обёртке `npm.ps1` sandbox может
  запретить чтение пользовательского npm prefix.
- В PowerShell передавай пути через `-LiteralPath` во все file cmdlets
  (`Get-Content`, `Get-Item`, `Get-ChildItem`, `Test-Path`, `Remove-Item`,
  `Copy-Item`, `Select-String`), а при обходе списка файлов — `$_.FullName`.
  Иначе сегменты вроде `apps/web/app/meetings/[id]` трактуются как wildcard и
  существующий файл «не находится».
- Находи нужное место через Grep и читай ограниченный диапазон строк через Read.
  Не читай файл целиком ради одной функции, не дампи логи, lockfile и
  сгенерированные файлы.
- Если тесты дали PASS, но процесс не завершился из-за оставшихся dev-серверов,
  зафиксируй это как ограничение среды. Не повторяй тот же прогон с увеличенным
  таймаутом.

## Финальное сообщение

- Если ты оставил изменения, последней строкой укажи
  `COMMIT_MESSAGE: <type>: <краткое описание>`, например
  `COMMIT_MESSAGE: feat: add profile endpoint`. Допустимые типы: `feat`, `fix`,
  `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`.
- Если issue уже полностью исправлена существующим commit текущей ветки, не
  создавай искусственное изменение. Убедись, что именно этот commit содержит
  исправление, является предком HEAD и удовлетворяет всем требованиям issue, и
  вместо `COMMIT_MESSAGE` укажи `ALREADY_FIXED: <SHA>`. Случайный SHA,
  merge-base или commit ради обхода пустого diff оркестратор отклонит.

## Перед завершением

- Сверь результат с каждым требованием и критерием готовности issue.
- Проведи self-review `git diff`: ошибки, регрессии, нарушения безопасности,
  непокрытые граничные случаи, невыполненные требования. Найденное исправь и
  повтори проверки.
- Оставь в рабочем дереве только изменения этой issue, без локальных артефактов,
  секретов и чужих правок.
