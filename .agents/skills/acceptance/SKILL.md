# Приёмка фазы и регресс

## Контракт

Выбери режим по запросу пользователя.

- `/acceptance <название milestone>` — приёмка по запросу после закрытия
  milestone. Допиши недостающие кейсы фазы, пройди её сценарии на стенде,
  сохрани отчёт и обнови `status.md`. После `impact` предложи регресс по
  задетым модулям с кейсами.
- `/acceptance regress <модуль|all>` — регресс по прямому запросу или после
  согласия на предложенный объём. Пройди живые кейсы выбранных модулей,
  сохрани отдельный отчёт и обнови `status.md`.
- `/acceptance status` — запрос сводки. Выполни `status` и покажи счёт,
  вердикт последнего прогона и текущие `FAIL` с датами. Для этого режима
  достаточно реестра и файлов приёмки.

Если режим или цель не указаны, покажи milestone репозитория и известные
модули, затем уточни выбор.

В приёмке и регрессе зафиксируй ID назначенных кейсов до браузера. По
завершении сверь отчёт со списком и выполни проверку перед сдачей. Выдай путь
к отчёту, вердикт, счёт по статусам и границы проверки.

Скилл заканчивается отчётом. Найденное не чини, issues не заводи.

## Где всё лежит

Каталог документов проекта — по умолчанию `docs`, если файл инструкций проекта
называет другой, бери его. Внутри `acceptance/`:

- `modules.md` — реестр модулей: имя, файл кейсов, пути в коде. Ведёт проект.
- `cases/<модуль>.md` — кейсы модуля, ID вида `CART-012`.
- `runs/<дата>-<тип>[-<модуль>].md` — прогоны.
- `evidence/<имя прогона>/<ID>.png` — снимки экрана.
- `status.md` — сводка; её пишет скрипт, руками не правь.

Форматы файлов и команды скрипта — в `scripts/ralph/README.md`, раздел
«Приёмка». Скрипт:

```
node scripts/ralph/ralph-acceptance.mjs status
node scripts/ralph/ralph-acceptance.mjs impact <база>...<ветка>
```

Каталог не `docs/acceptance` — добавляй `--dir <путь>` к обеим командам.

## Входы для приёмки и регресса

Сначала сверь критерии issue, спецификацию и инструкции проекта. Бери из них
принятые решения о пользователе, стенде и ожидаемом результате. Спрашивай
только о пробеле или противоречии, от которого зависит сценарий, объём
прогона или вердикт. Вопрос формулируй через действие и ожидаемый результат
пользователя. Если выбор за владельцем, назови варианты и их последствия
для приёмки.

1. Адрес работающего тестового стенда и версия приложения на нём.
2. Учётные данные тестового пользователя, если сценарии требуют входа.
3. Инструмент, которым ты управляешь браузером. Годится любой: Playwright MCP,
   Chrome DevTools MCP, встроенный браузер CLI. Playwright поднимает свой чистый
   контекст: вход выполняется тестовыми данными и повторяется одинаково.
   Инструмент во вкладке человека входа не требует, но тащит в прогон его куки
   и расширения — отказ, который на чистом браузере не воспроизводится, ищи
   здесь.

До прогона подтверди версию на стенде по данным проекта и запиши коммит
или идентификатор сборки. Если не хватает адреса, версии, необходимых
тестовых данных или доступа к браузеру, назови пробел и остановись.
Приложение не поднимай и не гаси.

## Реестр модулей

Нет `modules.md` — собери черновик для приёмки фазы и жди подтверждения. В
режиме `status` или `regress` назови путь к недостающему реестру и остановись.
Имена модулей возьми из строк «Затрагивает»
закрытых issue, пути — из diff фазы (`git diff --name-only <база>...<ветка>`),
сгруппировав их по верхним каталогам. Покажи таблицу, попроси поправить и
сохранить. Правильность путей проверит следующий `impact`: изменённые файлы, не
попавшие ни в один модуль, он печатает списком «Пути вне реестра» — это
подсказка расширить реестр, покажи её пользователю.

## Приёмка фазы

### Шаг 1. Собери задачи фазы

Найди milestone по точному названию. Если совпадений несколько,
уточни номер. Если milestone ещё открыт, назови это и остановись. Собери
все закрытые issue milestone по номеру с пагинацией.

```
gh api --paginate "repos/{owner}/{repo}/milestones?state=all&per_page=100" --jq ".[] | {number,title,state}"
gh api --paginate "repos/{owner}/{repo}/issues?milestone=<номер>&state=closed&per_page=100" --jq ".[] | select(.pull_request == null) | {number,title,body,labels:[.labels[].name]}"
```

Исключи PR и issue с меткой `ralph-deferred`. Из тела каждой оставшейся issue
возьми раздел `## Критерий готовности` целиком и строку «Затрагивает».
Если раздел пуст или из критерия и принятых решений нельзя получить
наблюдаемый результат, назови номер issue и уточни критерий до назначения
кейсов.

Инвентарь собирай сам, до запуска субагентов: у них нет ни оболочки, ни `gh`.

### Шаг 2. Составь кейсы субагентами

Раздели issue на пачки по 3–5 и запусти по субагенту на пачку — параллельно:
они только читают текст. В задание вложи тела issue целиком и имя модуля для
каждой — по строке «Затрагивает» и реестру; не сопоставилось — спроси
пользователя до запуска.

Модель здесь дешёвая: работа механическая — переложить критерий в шаги. У Claude
Code это `sonnet`, у Codex — `terra`: номер версии перед именем ступени меняется
вместе с линейкой, бери текущий. Отдельный effort субагенту не задаётся, он
наследует сессию.

Задание субагенту: на каждый критерий готовности — минимум один кейс основного
пути, а на критерий с вводом или внешним вызовом — ещё и кейс отказной ветки.
Формат кейса:

```
## CART-012. Товар с нулевым остатком не кладётся в корзину

**Источник** issue #42, критерий 3 · Фаза 2
**Предусловия** пользователь вошёл; в каталоге есть товар с остатком 0
**Шаги**
1. Открыть карточку товара с нулевым остатком.
2. Нажать «В корзину».
**Ожидается** кнопка неактивна, рядом «Нет в наличии», счётчик корзины не меняется
```

Правило, которое проверяй лично: у каждого кейса стоит номер issue и номер
критерия. Кейс без источника — выдумка модели; удали его, а не переписывай.

Допиши недостающие кейсы в `cases/<модуль>.md`. Номер — наибольший в файле
плюс один и не короче трёх цифр (`001`). Снятые номера тоже учитывай.
При повторной приёмке используй существующие кейсы по тому же источнику и
сценарию. Основной путь и отказную ветку одного критерия веди отдельными
кейсами.
Снятый кейс не удаляют, а помечают строкой `**Снят** <дата> — <причина>`.

### Шаг 3. Прогони кейсы фазы

Возьми живые кейсы по критериям этой фазы. Кейсы других фаз ждут регресса.
Разложи кейсы по прогонам с общими предусловиями. Вход выполняется один раз,
дальше кейсы идут подряд по тому же состоянию. Кейс, который ломает состояние
остальных (очистка данных, выход, смена роли), уводи в конец или в отдельный
прогон. Мелкая фаза целиком помещается в один прогон.

Порядок и правила прогона — в разделе «Как проходит прогон». Файл —
`runs/<дата>-phase-<номер фазы>.md`.

### Шаг 4. Сводка и вопрос о регрессе

Выполни проверку перед сдачей. Затем вызови `impact <база>...<ветка фазы>` и
сложи его вывод со строками «Затрагивает». Если пользователь уже запросил
регресс с понятным объёмом, переходи к нему. Иначе при наличии задетых
модулей с кейсами спроси:
«Фаза задела cart (14 кейсов) и checkout (6). Запустить регресс?» Число в
скобках — все живые кейсы модуля, включая дописанные и прогнанные этой фазой.
Для предложенного регресса дождись согласия. Если задетых модулей с кейсами
нет, сообщи об этом. «Пути вне реестра» покажи пользователю.

## Регресс

`/acceptance regress <модуль>` или `/acceptance regress all`. Модуля нет в
реестре — остановись и назови модули из него.

Возьми живые кейсы модуля или всех модулей, разложи
по прогонам по общим предусловиям и пройди. Файл —
`runs/<дата>-regress-<модуль|all>.md`, в шапке «Повод»: пути diff или слова
пользователя. Прежние статусы кейсов прочитай в `status.md` до прогона: `status`
после прогона их перезаписывает. После прогона выполни проверку перед сдачей.

В отчёте первыми стоят кейсы, у которых до прогона был `PASS`, а теперь `FAIL`:
это находки регресса. Остальные отказы — ниже.

## Как проходит прогон

Зафиксируй точный непустой список ID до браузера и перенеси его в поле
«Кейсы» отчёта. Проводи сценарий пользователя от действия до видимого
результата. При выборе порядка проверь, где сценарий затрагивает деньги,
доступ к чужим данным или необратимое действие. Приоритизация меняет
очерёдность, а согласованный объём сохраняется.

**Прогоны идут по одному.** Ломает параллель не браузер, а приложение: два
прогона, одновременно меняющие корзину того же пользователя, дают отказ, которого
в коде нет. Свой контекст браузера на прогон — Playwright так умеет — этой
причины не убирает. Параллель безопасна только там, где у каждого прогона свой
тестовый пользователь и свои данные; это свойство проекта, и брать его надо из
его документации, а не из предположения.

Прогон отдавай субагенту: контекст у него чистый, а главная сессия не тонет в
шагах браузера. Модель здесь основная, не дешёвая: решить, прошёл ли сценарий,
глядя на страницу, — самая дорогая работа приёмки, и на слабой модели ты
получишь ложные «прошло». У Claude Code это `opus`, у Codex — `sol`. Субагентов
у CLI нет — проходи прогоны сам, по одному, и записывай результат каждого
прогона в файл сразу, а не в конце.

В задании назови адрес, пользователя, кейсы прогона целиком и требование
возвращать результат по каждому кейсу. Статусы одни на всю приёмку:

- `PASS` — наблюдаемый результат совпал с ожидаемым. Запиши, что увидел.
- `FAIL` — разошлось. Обязательны шаг, на котором разошлось, фактический
  результат и доказательство: текст ошибки, запись консоли, адрес страницы, путь
  к снимку экрана.
- `BLOCKED` — до кейса не дошли: не выполнилось предусловие или упал предыдущий
  шаг цепочки.
- `SKIPPED` — кейс не выполняли, и причина названа.

Снимки экрана складывай в `evidence/<имя прогона>/<ID>.png`. Доказательство,
оставшееся только в переписке субагента, до отчёта не доживёт.

Первый `FAIL` прогон не останавливает: следующий кейс проходят, если его
предусловия целы. Остальное помечай `BLOCKED`, а не `FAIL`: непройденный кейс —
не сломанный.

## Файл прогона

```
# Прогон: регресс cart

**Тип** регресс
**Milestone** —
**Коммит** 3f2a9c1 ветки ralph/phase-3
**Стенд** http://localhost:3000
**Дата** 2026-09-15
**Исполнял** claude / opus
**Повод** фаза 3 задела src/cart/total.ts, src/cart/add.ts
**Кейсы** CART-001, CART-007, CART-008

## Итог

Прошло 1 из 3, не прошло 1, заблокировано 1.
Вердикт: не принято.

## Результаты

| Кейс | Статус | Комментарий |
| ---- | ------ | ----------- |
| CART-001 | PASS | счётчик корзины вырос на 1 |
| CART-007 | FAIL | кнопка активна при нулевом остатке |
| CART-008 | BLOCKED | предусловие CART-007 |

## Отказы

### CART-007. Товар с нулевым остатком не кладётся в корзину

**Разошлось на шаге** 2
**Ожидалось** кнопка неактивна, текст «Нет в наличии»
**Фактически** кнопка активна, товар добавлен, счётчик стал 1
**Доказательство** На странице http://localhost:3000/product/17 в консоли
видно `POST /api/cart 200`. Снимок evidence/2026-09-15-regress-cart/CART-007.png

## Границы проверки

Счётчик вырос при добавлении доступного товара. Добавление товара с нулевым
остатком воспроизвело ошибку. За пределами прогона удаление из корзины,
оформление заказа и изменение остатка во время покупки.
```

Таблицу «Результаты» читает скрипт: строка — ID, статус из четырёх, комментарий.
Второй прогон того же имени в тот же день — суффикс `-2`.

Вердикт последней строкой итога:

- Есть хотя бы один `FAIL` — `Вердикт: не принято.`
- Нет `FAIL`, но есть `BLOCKED` или `SKIPPED` — `Вердикт: не завершено.`
- Все назначенные кейсы имеют `PASS` — `Вердикт: принято.`

Называй число `BLOCKED` и `SKIPPED` и причины: пропущенная проверка не доказывает
работоспособность. Исключение кейса из объёма требует решения владельца до
принятия; причина пропуска сама по себе не превращает `SKIPPED` в `PASS`.
Не удаляй назначенный кейс из отчёта ради положительного вердикта.

## Проверка перед сдачей

До сохранения файла в `runs/` проверь четыре условия.

1. У каждого нового кейса стоит issue и номер критерия, а ID — с префиксом
   своего модуля.
2. Поле «Кейсы» и ID таблицы совпадают со списком, зафиксированным до
   браузера. Каждый назначенный ID встречается в таблице один раз. Если
   результат не получен, укажи `BLOCKED` или `SKIPPED` с известной причиной.
3. У каждого `PASS` есть наблюдаемый результат. У каждого `FAIL` есть шаг,
   фактический результат и доказательство. Проверь, что указанные файлы
   доказательств доступны. Назови, что доказывает прогон и что осталось за
   его пределами.
4. Счёт и вердикт совпадают с таблицей.

После записи запусти `status` и сверь вердикт в строке именно этого файла
в `status.md`. Проверь вывод команды на предупреждения по этому отчёту.

`status` сверяет поле `**Кейсы**` с ID в таблице. При расхождении он перечисляет
пропущенные и лишние ID в выводе и в `status.md`. Такой прогон получает «не
завершено», а при наличии `FAIL` — «не принято». Старые отчёты без поля читаются
по таблице. Сверь поле с назначенным списком и проверь доказательства. При
ошибке команды, расхождении ID или недостатке доказательств сообщи, что осталось
проверить. Итог «принято» требует полного набора `PASS` и всех проверок выше.
