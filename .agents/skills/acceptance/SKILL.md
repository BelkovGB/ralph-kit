# Приёмка фазы и регресс

Проверяет продукт так, как проверил бы тестировщик: кейсы собираются из
критериев готовности закрытых issue, копятся в файлах модулей и гоняются в
работающем приложении. Автоматические проверки и ревью цикл уже провёл — здесь
ищут то, что видно только пользователю.

Три формы команды:

- `/acceptance <название milestone>` — приёмка закрытой фазы: новые кейсы фазы
  дописываются в модули и гоняются; затем скилл считает, какие модули фаза
  задела, и **спрашивает**, гнать ли по ним регресс.
- `/acceptance regress <модуль|all>` — регресс накопленных кейсов модуля или
  всех модулей. Новых кейсов не создаёт.
- `/acceptance status` — что сейчас красное. Браузер не трогает.

Без аргумента — покажи список milestone репозитория и модули из реестра и
спроси, что делать.

Скилл заканчивается отчётом. Найденное не чини, issues не заводи, регресс без
прямого «да» не запускай.

## Где всё лежит

Каталог документов проекта — по умолчанию `docs`, если файл инструкций проекта
называет другой, бери его. Внутри `acceptance/`:

- `modules.md` — реестр модулей: имя, файл кейсов, пути в коде. Ведёт проект.
- `cases/<модуль>.md` — кейсы модуля, ID вида `CART-012`.
- `runs/<дата>-<тип>[-<модуль>].md` — прогоны.
- `evidence/<имя прогона>/<ID>.png` — снимки экрана.
- `status.md` — сводка; её пишет скрипт, руками не правь.

Форматы файлов и команды скрипта — в `scripts/ralph/README.md`, раздел
«Приёмка». Скрипт:

```
node scripts/ralph/ralph-acceptance.mjs status
node scripts/ralph/ralph-acceptance.mjs impact <база>...<ветка>
```

Каталог не `docs/acceptance` — добавляй `--dir <путь>` к обеим командам.

## Что нужно от проекта

1. Команда, которая поднимает приложение, и адрес, по которому оно доступно.
2. Учётные данные тестового пользователя, если сценарии требуют входа.
3. Инструмент, которым ты управляешь браузером. Годится любой: Playwright MCP,
   Chrome DevTools MCP, встроенный браузер CLI. Playwright поднимает свой чистый
   контекст: вход выполняется тестовыми данными и повторяется одинаково.
   Инструмент во вкладке человека входа не требует, но тащит в прогон его куки
   и расширения — отказ, который на чистом браузере не воспроизводится, ищи
   здесь.

Первые две ищи в файле инструкций проекта. Не нашёл — спроси у пользователя и
остановись: угаданный адрес даёт прогон по чужому стенду, а угаданный
пользователь портит данные. Приложение не поднимай и не гаси: на том же
экземпляре может идти чужая работа.

## Реестр модулей

Нет `modules.md` — собери черновик и жди подтверждения, дальше не иди: без
реестра кейсы некуда класть. Имена модулей возьми из строк «Затрагивает»
закрытых issue, пути — из diff фазы (`git diff --name-only <база>...<ветка>`),
сгруппировав их по верхним каталогам. Покажи таблицу, попроси поправить и
сохранить. Правильность путей проверит следующий `impact`: изменённые файлы, не
попавшие ни в один модуль, он печатает списком «Пути вне реестра» — это
подсказка расширить реестр, покажи её пользователю.

## Приёмка фазы

### Шаг 1. Собери задачи фазы

```
gh issue list --milestone "<название>" --state closed --json number,title,body,labels
```

Выбрось issue с меткой `ralph-deferred`: их закрыли как отложенные замечания, а
не как сделанную работу. Из тела каждой оставшейся возьми раздел
`## Критерий готовности` целиком и строку «Затрагивает».

Инвентарь собирай сам, до запуска субагентов: у них нет ни оболочки, ни `gh`.

### Шаг 2. Составь кейсы субагентами

Раздели issue на пачки по 3–5 и запусти по субагенту на пачку — параллельно:
они только читают текст. В задание вложи тела issue целиком и имя модуля для
каждой — по строке «Затрагивает» и реестру; не сопоставилось — спроси
пользователя до запуска.

Модель здесь дешёвая: работа механическая — переложить критерий в шаги. У Claude
Code это `sonnet`, у Codex — `terra`: номер версии перед именем ступени меняется
вместе с линейкой, бери текущий. Отдельный effort субагенту не задаётся, он
наследует сессию.

Задание субагенту: на каждый критерий готовности — минимум один кейс основного
пути, а на критерий с вводом или внешним вызовом — ещё и кейс отказной ветки.
Формат кейса:

```
## CART-012. Товар с нулевым остатком не кладётся в корзину

**Источник** issue #42, критерий 3 · Фаза 2
**Предусловия** пользователь вошёл; в каталоге есть товар с остатком 0
**Шаги**
1. Открыть карточку товара с нулевым остатком.
2. Нажать «В корзину».
**Ожидается** кнопка неактивна, рядом «Нет в наличии», счётчик корзины не меняется
```

Правило, которое проверяй лично: у каждого кейса стоит номер issue и номер
критерия. Кейс без источника — выдумка модели; удали его, а не переписывай.

Допиши кейсы в `cases/<модуль>.md`. Номер — наибольший в файле плюс один, снятые
считаются; номера не переиспользуются. Кейс с тем же источником (issue и номер
критерия), что уже есть в файле, пропусти: повторная приёмка не плодит дубли.
Снятый кейс не удаляют, а помечают строкой `**Снят** <дата> — <причина>`.

### Шаг 3. Прогони новые кейсы фазы

Гоняются только кейсы этой фазы — накопленные ждут регресса. Разложи их по
прогонам по общим предусловиям: вход выполняется один раз, дальше кейсы идут
подряд по тому же состоянию. Кейс, который ломает состояние остальных (очистка
данных, выход, смена роли), уводи в конец или в отдельный прогон. Мелкая фаза
целиком помещается в один прогон.

Порядок и правила прогона — в разделе «Как проходит прогон». Файл —
`runs/<дата>-phase-<номер фазы>.md`.

### Шаг 4. Сводка и вопрос о регрессе

Выполни `status`. Затем `impact <база>...<ветка фазы>` и сложи его вывод со
строками «Затрагивает». Есть задетый модуль, в котором лежат кейсы прошлых фаз, —
спроси одной фразой: «Фаза задела cart (14 кейсов) и checkout (6). Запустить
регресс?» Без «да» ничего не делай. Таких модулей нет — так и скажи. «Пути вне
реестра» покажи пользователю.

## Регресс

`/acceptance regress <модуль>` или `/acceptance regress all`. Модуля нет в
реестре — остановись и назови модули из него.

Возьми живые кейсы модуля или всех модулей — снятые в прогон не идут, — разложи
по прогонам по общим предусловиям и пройди. Файл —
`runs/<дата>-regress-<модуль|all>.md`, в шапке «Повод»: пути diff или слова
пользователя. После прогона выполни `status`.

В отчёте первыми стоят кейсы, у которых в `status.md` до прогона был `PASS`, а
теперь `FAIL`: это находки регресса. Остальные отказы — ниже.

## Сводка

`/acceptance status` выполняет `status`, печатает строку счёта и список `FAIL` с
датой последнего прогона из таблицы. Больше ничего не делает.

## Как проходит прогон

**Прогоны идут по одному.** Ломает параллель не браузер, а приложение: два
прогона, одновременно меняющие корзину того же пользователя, дают отказ, которого
в коде нет. Свой контекст браузера на прогон — Playwright так умеет — этой
причины не убирает. Параллель безопасна только там, где у каждого прогона свой
тестовый пользователь и свои данные; это свойство проекта, и брать его надо из
его документации, а не из предположения.

Прогон отдавай субагенту: контекст у него чистый, а главная сессия не тонет в
шагах браузера. Модель здесь основная, не дешёвая: решить, прошёл ли сценарий,
глядя на страницу, — самая дорогая работа приёмки, и на слабой модели ты
получишь ложные «прошло». У Claude Code это `opus`, у Codex — `sol`. Субагентов
у CLI нет — проходи прогоны сам, по одному, и записывай результат каждого
прогона в файл сразу, а не в конце.

В задании назови адрес, пользователя, кейсы прогона целиком и требование
возвращать результат по каждому кейсу. Статусы одни на всю приёмку:

- `PASS` — ожидаемое совпало с фактическим.
- `FAIL` — разошлось. Обязательны шаг, на котором разошлось, фактический
  результат и доказательство: текст ошибки, запись консоли, адрес страницы, путь
  к снимку экрана.
- `BLOCKED` — до кейса не дошли: не выполнилось предусловие или упал предыдущий
  шаг цепочки.
- `SKIPPED` — кейс не выполняли, и причина названа.

Снимки экрана складывай в `evidence/<имя прогона>/<ID>.png`. Доказательство,
оставшееся только в переписке субагента, до отчёта не доживёт.

Первый `FAIL` прогон не останавливает: следующий кейс проходят, если его
предусловия целы. Остальное помечай `BLOCKED`, а не `FAIL`: непройденный кейс —
не сломанный.

## Файл прогона

```
# Прогон: регресс cart

**Тип** регресс
**Milestone** —
**Коммит** 3f2a9c1 ветки ralph/phase-3
**Стенд** http://localhost:3000
**Дата** 2026-09-15
**Исполнял** claude / opus
**Повод** фаза 3 задела src/cart/total.ts, src/cart/add.ts
**Кейсы** cases/cart.md, CART-001…CART-014

## Итог

Прошло 12 из 14, не прошло 1, заблокировано 1.
Вердикт: не принято.

## Результаты

| Кейс | Статус | Комментарий |
| ---- | ------ | ----------- |
| CART-001 | PASS | |
| CART-007 | FAIL | кнопка активна при нулевом остатке |
| CART-008 | BLOCKED | предусловие CART-007 |

## Отказы

### CART-007. Товар с нулевым остатком не кладётся в корзину

**Разошлось на шаге** 2
**Ожидалось** кнопка неактивна, текст «Нет в наличии»
**Фактически** кнопка активна, товар добавлен, счётчик стал 1
**Доказательство** http://localhost:3000/product/17; в консоли
`POST /api/cart 200`; снимок evidence/2026-09-15-regress-cart/CART-007.png
```

Таблицу «Результаты» читает скрипт: строка — ID, статус из четырёх, комментарий.
Второй прогон того же имени в тот же день — суффикс `-2`.

Вердикт последней строкой итога: есть хотя бы один `FAIL` — «не принято», иначе
«принято». `BLOCKED` вердикт не решает, но в итоге называется числом: прогон, где
проверена половина кейсов, приёмкой не является.

## Проверка перед сдачей

1. У каждого нового кейса стоит issue и номер критерия, а ID — с префиксом
   своего модуля.
2. У каждого `FAIL` есть шаг, фактический результат и доказательство.
3. Числа итога сходятся с таблицей результатов.
4. Ни один кейс прогона не остался без статуса.
5. `status` выполнен после прогона и завершился без остановки.
