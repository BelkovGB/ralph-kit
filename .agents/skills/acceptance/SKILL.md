# Приёмка фазы

Проверяет закрытую фазу так, как проверил бы тестировщик: собирает кейсы из
критериев готовности закрытых issue, режет их на прогоны и проходит каждый
прогон в работающем приложении. Автоматические проверки и ревью цикл уже
провёл — здесь ищут то, что видно только пользователю.

Аргумент команды — название milestone. Аргумента нет — покажи список milestone
репозитория и спроси, какой принимать.

Скилл заканчивается отчётом. Найденное не чини и issues не заводи.

## Что нужно от проекта

Три вещи, без которых прогон невозможен:

1. Команда, которая поднимает приложение, и адрес, по которому оно доступно.
2. Учётные данные тестового пользователя, если сценарии требуют входа.
3. Инструмент, которым ты управляешь браузером.

Первые две ищи в файле инструкций проекта. Не нашёл — спроси у пользователя и
остановись: угаданный адрес даёт прогон по чужому стенду, а угаданный
пользователь портит данные.

Приложение поднимает пользователь или проект своей командой. Сам его не
перезапускай и не гаси: на том же экземпляре может идти чужая работа.

## Шаг 1. Собери задачи фазы

```
gh issue list --milestone "<название>" --state closed --json number,title,body,labels
```

Выбрось issue с меткой `ralph-deferred`: их закрыли как отложенные замечания, а
не как сделанную работу. Кейсы по ним — проверка того, чего в коде нет.

Из тела каждой оставшейся issue возьми раздел `## Критерий готовности` целиком.
Он и есть источник кейсов: `/issues` пишет критерии в форме «при <условии>
система <результат>», проверяемой снаружи без чтения кода.

Инвентарь собирай сам, до запуска субагентов: у них нет ни оболочки, ни `gh`, и
без готового текста они либо угадывают по именам, либо читают весь проект.

## Шаг 2. Составь кейсы субагентами

Раздели issue на пачки по 3–5 штук и запусти по субагенту на пачку —
параллельно: они только читают текст и ничего не делят. В задание каждого вложи
тела его issue целиком.

Модель здесь дешёвая: работа механическая — переложить критерий в шаги. У Claude
Code — `sonnet`, у Codex — `gpt-5.6-terra`. Отдельный effort субагенту не
задаётся, он наследует сессию.

Задание субагенту: на каждый критерий готовности — минимум один кейс основного
пути, а на критерий с вводом или внешним вызовом — ещё и кейс отказной ветки.
Формат кейса:

```
### TC-7. Товар с нулевым остатком не кладётся в корзину

**Источник** issue #42, критерий 3
**Предусловия** пользователь вошёл; в каталоге есть товар с остатком 0
**Шаги**
1. Открыть карточку товара с нулевым остатком.
2. Нажать «В корзину».
**Ожидается** кнопка неактивна, рядом текст «Нет в наличии», счётчик корзины не меняется.
```

Правило, которое проверяй лично: у каждого кейса стоит номер issue и номер
критерия. Кейс без источника — выдумка модели; удали его, а не переписывай.

Сведи ответы субагентов в один файл `docs/acceptance/cases-<слаг>.md`, пронумеруй
кейсы сквозной нумерацией `TC-1`…`TC-N` и выкинь дубли: соседние issue часто
закрывают один и тот же критерий с разных сторон. Каталог документов задаёт
проект: по умолчанию `docs`, но если файл инструкций называет другой — бери его.

## Шаг 3. Разложи кейсы по прогонам

Прогон — это пачка кейсов, которые проходят одной цепочкой в одной сессии
браузера. Собирай пачку по общим предусловиям: вход выполняется один раз,
корзина наполняется один раз, а дальше кейсы идут подряд по тому же состоянию.
Кейс, который ломает состояние остальных (очистка данных, выход, смена роли),
уводи в конец пачки или в отдельный прогон.

Мелкая фаза целиком помещается в один прогон — так и делай. Дели, когда пачка
перестаёт помещаться в одну сессию или когда предусловия расходятся.

## Шаг 4. Проведи прогоны

**Прогоны идут по одному, никогда параллельно.** Браузер один на всю сессию, а у
приложения общее состояние: два агента, одновременно меняющие ту же корзину,
ломают проверки друг друга и дают отказ, которого в коде нет.

Прогон отдавай субагенту: контекст у него чистый, а главная сессия не тонет в
шагах браузера. Модель здесь основная, не дешёвая: решить, прошёл ли сценарий,
глядя на страницу, — самая дорогая работа приёмки, и на слабой модели ты
получишь ложные «прошло». У Claude Code — `opus`, у Codex — `gpt-5.6-sol`.
Субагентов у CLI нет — проходи прогоны сам, по одному, и записывай результат
каждого прогона в файл сразу, а не в конце.

В задании назови адрес, пользователя, кейсы прогона целиком и требование
возвращать результат по каждому кейсу. Статусы одни на всю приёмку:

- `PASS` — ожидаемое совпало с фактическим.
- `FAIL` — разошлось. Обязательны шаг, на котором разошлось, фактический
  результат и доказательство: текст ошибки, запись консоли, адрес страницы, путь
  к снимку экрана.
- `BLOCKED` — до кейса не дошли: не выполнилось предусловие или упал предыдущий
  шаг цепочки.
- `SKIPPED` — кейс не выполняли, и причина названа.

Первый `FAIL` прогон не останавливает: следующий кейс проходят, если его
предусловия целы. Остальное помечай `BLOCKED`, а не `FAIL`: непройденный кейс —
не сломанный.

## Шаг 5. Напиши отчёт

Файл `docs/acceptance/run-<слаг>-<ГГГГ-ММ-ДД>.md`; такой уже есть — добавь `-2`.

```
# Приёмка: Фаза 2. Корзина

**Milestone** Фаза 2. Корзина
**Коммит** <SHA> ветки <ветка>
**Стенд** http://localhost:3000
**Дата** 2026-09-07
**Исполнял** claude / opus
**Кейсы** docs/acceptance/cases-cart.md, TC-1…TC-9

## Итог

Прошло 7 из 9, не прошло 2, заблокировано 0.
Вердикт: не принято.

## Результаты

| Кейс  | Статус | Комментарий                                  |
| ----- | ------ | -------------------------------------------- |
| TC-1  | PASS   |                                              |
| TC-7  | FAIL   | кнопка активна при нулевом остатке           |

## Отказы

### TC-7. Товар с нулевым остатком не кладётся в корзину

**Источник** issue #42, критерий 3
**Разошлось на шаге** 2
**Ожидалось** кнопка неактивна, текст «Нет в наличии»
**Фактически** кнопка активна, товар добавлен, счётчик стал 1
**Доказательство** http://localhost:3000/product/17; в консоли
`POST /api/cart 200`; снимок `docs/acceptance/tc-7.png`
```

Вердикт последней строкой итога: есть хотя бы один `FAIL` — «не принято», иначе
«принято». `BLOCKED` вердикт не решает, но в итоге называется числом: прогон, где
проверена половина кейсов, приёмкой не является.

## Проверка перед сдачей

1. У каждого кейса в файле кейсов стоит issue и номер критерия.
2. У каждого `FAIL` есть шаг, фактический результат и доказательство.
3. Числа итога сходятся с таблицей результатов.
4. Ни один кейс не остался без статуса.
