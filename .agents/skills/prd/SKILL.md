# PRD генератор

Опиши требования к фиче, названной в аргументе команды.

## Перед написанием

- Прочитай файл инструкций проекта и документ действующего контракта, если
  проект его называет. Технические ограничения берутся из текущего кода и
  контрактов, а не из общих соображений.
- Если описание короткое или допускает разные прочтения, задавай уточняющие
  вопросы и не создавай файл до полного понимания.

## Куда сохранить

`docs/prd-<слаг>.md`, где `<слаг>` — два-четыре латинских слова в kebab-case,
описывающих фичу, например `user-profile`. План и issues берут
тот же слаг, поэтому после создания он не меняется.

Каталог документов задаёт проект: по умолчанию `docs`, но если файл инструкций
проекта называет другой — бери его.

Если каталога нет — создай.

## Структура документа

# PRD: {Название фичи}

**Дата**: {текущая дата}
**Статус**: Draft

## Цель

Одно-два предложения: что получает пользователь и зачем.

## Пользовательские сценарии

- Пользователь {действие} -> {результат}

## Не в скоупе

Что явно не делаем в этой итерации.

## Технические ограничения

Известное ограничение текущего кода, которое придётся учесть.

## Критерии готовности

1. Критерий
2. Критерий

## Правила

- Пиши конкретно, без воды.
- По каждому критерию готовности видно, чем подтверждается выполнение.
- Критерии нумеруются: план ссылается на них номерами.
- Не описывай, как реализовывать: только что и зачем.
