# PRD генератор

Опиши требования к фиче, названной в аргументе команды.

## Перед написанием

Прочитай файл инструкций проекта и документ действующего контракта, если проект
его называет. Технические ограничения берутся из текущего кода и контрактов, а
не из общих соображений.

## Уточняющие вопросы

Спрашивай только о том, что меняет объём фичи или критерии готовности.
Остальное решай сам и записывай в «Допущения».

Порядок важности: объём > доступ и данные > поведение при отказе > детали
интерфейса.

Задавай по одному вопросу за раз. К каждому давай пронумерованные варианты
ответа и помечай рекомендуемый, чтобы пользователь ответил короткой строкой.

Если решение меняет объём или критерии, а в документах проекта его нет —
остановись и спроси. За пользователя такое решение не принимай и в «Допущения»
не прячь.

## Куда сохранить

`docs/prd-<слаг>.md`, где `<слаг>` — два-четыре латинских слова в kebab-case,
описывающих фичу, например `user-profile`. План и issues берут
тот же слаг, поэтому после создания он не меняется.

Каталог документов задаёт проект: по умолчанию `docs`, но если файл инструкций
проекта называет другой — бери его.

Если каталога нет — создай.

## Структура документа

# PRD: {Название фичи}

**Дата**: {текущая дата}

## Цель

Одно-два предложения: что получает пользователь и зачем.

## Пользовательские сценарии

- Пользователь {действие} -> {результат}

Сценарии идут по важности. Первый сценарий сам по себе даёт работающий продукт:
план делает из него первую фазу. Если ролей больше одной, называй роль вместо
слова «пользователь».

## Не в скоупе

Что явно не делаем в этой итерации.

## Технические ограничения

Известное ограничение текущего кода, которое придётся учесть. Назови новую
внешнюю зависимость, сервис или модель, если фича их требует: план заводит на
неё отдельную первую задачу фазы.

## Допущения

Решение, принятое за пользователя, и его основание — одна строка на допущение.

## Критерии готовности

1. Критерий
2. Критерий

## Правила

- Пиши конкретно, без воды.
- Критерий — наблюдаемое поведение системы, проверяемое снаружи, без чтения
  кода. Форма: при <условии> система <результат>. Плохо: «удаление работает
  корректно». Хорошо: «при нажатии кнопки удаления система показывает диалог
  подтверждения, и до подтверждения запись остаётся в списке». Слова
  «корректно», «удобно», «быстро», «надёжно» критерием не являются.
- У каждого сценария есть хотя бы один критерий, и каждый критерий относится к
  сценарию.
- У сценария с пользовательским вводом или внешним вызовом есть критерий на
  отказ: что видит пользователь, когда шаг не проходит — пустой ввод, отказ
  внешнего сервиса, недоступные данные. Без такого критерия цикл пишет только
  счастливый путь, а ревью не находит нарушения.
- Критерии нумеруются: план ссылается на них номерами.
- Не описывай, как реализовывать: только что и зачем.

## Проверка перед сохранением

Перечитай «Правила» и проверь документ по каждому пункту, затем проверь то, чего
в правилах нет:

1. Первый сценарий сам по себе даёт работающий продукт.
2. Каждое решение, принятое за пользователя, записано в «Допущения».
3. Новая внешняя зависимость, сервис или модель названа в «Технических
   ограничениях».
4. Открытых вопросов не осталось: вопрос либо задан, либо перенесён в «Не в
   скоупе».

Не начинай реализацию: скилл заканчивается сохранённым документом.
Следующий шаг — команда `/plan-phase docs/prd-<слаг>.md`.
