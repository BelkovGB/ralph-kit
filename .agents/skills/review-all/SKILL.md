# Полное ревью изменений

## Область ревью

Область — коммиты текущей ветки поверх базовой плюс незакоммиченные изменения.
Команды запускай из корня рабочего дерева.

1. Узнай текущую ветку через `git branch --show-current`. В
   `.agents/ralph.config.json` найди фазу по имени `branch` без крайних пробелов.
   Для этой фазы возьми `phase.baseBranch ?? config.baseBranch`. Если подходящей
   фазы нет, возьми `config.baseBranch`.
2. Убери крайние пробелы у имени базы из конфига. Передавай ссылку одним
   аргументом без подстановок оболочки. Проверь локальную ветку командой
   `git rev-parse --verify 'refs/heads/<имя базы>^{commit}'`.
   Если её нет, проверь `git rev-parse --verify 'refs/remotes/origin/<имя базы>^{commit}'`.
   Если имя базы не задано, получи ссылку через
   `git symbolic-ref refs/remotes/origin/HEAD` и проверь её той же командой.
3. Если база недоступна, назови проверенные ссылки, спроси, с чем сравнивать,
   и остановись. В командах инвентаря подставь проверенный SHA вместо `<база>`.

## Инвентарь изменений

Инвентарь — статистика, список изменённых файлов и построчный diff вместе.
До запуска ревьюеров выбери один набор исключений для построчного diff
коммитов и рабочей копии. Например, исключи lock-файлы и сгенерированные файлы.

```
git diff --stat <база>...HEAD
git diff --name-status <база>...HEAD
git diff <база>...HEAD -- . ':(exclude)<lock-файл проекта>'
git status --short --untracked-files=all
git diff --stat HEAD
git diff HEAD -- . ':(exclude)<lock-файл проекта>'
```

Сгенерированные файлы убирай из построчного diff pathspec-ом
`':(exclude)<путь>'`, как lock-файл в примере: он меняется на сотни строк от
одной зависимости и вытесняет из задания продуктовый код. Исключённый файл
остаётся в списке и в статистике, исчезает только его diff.

Файл со статусом `??` неотслеживаемый и виден только в `git status`.
Для таких файлов вне набора исключений вложи в инвентарь полное содержимое.

Инвентарь идёт в задание каждому ревьюеру. Оболочки у ревьюеров нет: `git` они
вызвать не могут и без инвентаря либо угадывают изменения по именам файлов, либо
читают весь проект.

Если инвентарь не влезает в задание, вложи статистику и список файлов целиком, а
построчный diff — по самым крупным изменениям, и скажи ревьюеру, что остальные
файлы он читает сам.

## Правила проекта

Прочитай `.agents/review-rules.md` один раз и вложи правила в задание каждому
ревьюеру. Файла нет — так и напиши в задании: «правил проекта нет». Правила
проекта дополняют перспективу ревьюера, а не заменяют её.

## Три перспективы

1. **Безопасность** — доверие ко вводу, границы файловой системы, запуск внешних
   процессов, выдача данных, секреты и конфигурация.
   Субагент `security-reviewer`, файл `.claude/agents/security-reviewer.md`.
2. **Корректность** — логические ошибки, необработанные отказы, крайние случаи,
   гонки и порядок операций, производительность.
   Субагент `correctness-reviewer`, файл
   `.claude/agents/correctness-reviewer.md`.
3. **Покрытие тестами** — поведение без теста, непроверенные пути отказа, тесты,
   которые не падают.
   Субагент `test-coverage-reviewer`, файл
   `.claude/agents/test-coverage-reviewer.md`.

## Как запускать

Есть у твоего CLI субагенты — вызови каждого по имени из списка выше и запусти
все три параллельно. В задание вложи инвентарь изменений, правила проекта и имя
базовой ветки. Перспективу не пересказывай: её текст агент уже получил вместе с
собой, и копия в задании оплачивается второй раз.

Нет субагентов — пройди перспективы по одной, прочитав перед каждой её файл и
идя по нему как по чек-листу. Находки каждой перспективы выписывай сразу
черновиком в ответе, под именем перспективы, а в отчёт своди только после
третьей: смешанные выводы теряют перспективу, от которой пришла находка.

## Шкала важности

Одна на все три перспективы — `P0`, `P1`, `P2`, `P3` из
`.agents/review.schema.json`, где `P0` самое важное замечание, а `P3` самое
мелкое.

- `P0` — изменение ломает работу или открывает уязвимость.
- `P1` — дефект проявляется на реальном сценарии: отказ, потеря данных,
  неверный результат.
- `P2` — дефект проявляется на редком сценарии или создаёт риск, который пока
  не проявляется.
- `P3` — мелкое замечание, которое чинится по случаю.

Строка находки: важность, `[файл:строка]`, суть, чем грозит, как чинить.

Порог вердикта — поле `reviewSeverityFloor` того же `.agents/ralph.config.json`:
`P1` блокирует P0 и P1, `P3` блокирует любую находку. Поля или файла нет — считай
порог `P3`, как считает прогон. Свой порог не назначай: при чужом ручное ревью
скажет «прошло» там, где прогон вернёт issue на переделку.

## Подтверждение находок

Подтверди сам каждую находку важностью не ниже порога: открой файл, найди
конструкцию, о которой говорит находка, и проверь, что она делает описанное и
что она есть в собранном инвентаре.

Номер строки ревьюер часто берёт из diff, а не из файла. Разошедшийся номер
исправь в отчёте; понижать из-за него находку нельзя.

Поведение оказалось другим или конструкции в изменениях нет — перенеси находку в
«Требует проверки» и назови, что не сошлось.

## Отчёт

Если ревью относится к известному комплекту работы, сохрани отчёт в его
`reports/` по [контракту документов](../init-project/references/project-documents.md).
Предыдущий результат не перезаписывай, если он нужен для истории проверки.
Не создавай комплект работы ради отдельного ревью ветки.

- **Находки** — сгруппированы по `файл:строка`, группы по убыванию важности. В
  группе строка на находку с именем перспективы, важность группы — наибольшая в
  ней. Так одно место чинится один раз, даже когда перспективы назвали в нём три
  разных дефекта.
- **Требует проверки** — то, что подтвердить не удалось.
- **Вердикт** последней строкой: есть находка важностью не ниже порога — «не
  прошло», иначе «прошло».

Скилл заканчивается отчётом: найденное не чини и issues не заводи.
