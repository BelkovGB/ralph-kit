# Источники и проверки подготовки

Читай установленную версию: путь к runtime всегда `scripts/ralph/` внутри
проекта. Не обновляй Kit и не меняй его поведение вместо подготовки запуска.

## Эффективные значения

`ralph-config.mjs`: `prepareConfig` применяет умолчания и валидирует объект.
Она читает журнал, правила и схемы, но не вызывает агента и не пишет конфиг.
`captureControlPlane:false` подходит для просмотра черновика. Для запуска
проектных проверок используй `loadConfig()` с полным снимком control plane:
он также применяет runtime-настройки и выбранный GitHub-аккаунт к процессу.

`ralph-gui-fields.mjs`, если поставлен, экспортирует `fieldGroups`: подписи,
hints, варианты, единицы. Импорт не запускает GUI. В минимальной CLI-копии
этого модуля может не быть: бери подписи из таблицы ниже, значения — из
`prepareConfig`. Программа ниже не зависит от GUI. Умолчания в метаданных формы могут быть
условными: **значение бери из `prepareConfig`, не из `field.default`**.
Например, `supervisor.timeoutMs` наследует `runtime.agentTimeoutMs`, а
`milestoneReview.maxTurns` — `maxTurns`.

Для компактного снимка лимитов выполни из корня следующую JS-программу через
`node --input-type=module` в синтаксисе текущей оболочки. Она не печатает токены,
переменные окружения, тела issues и prompt:

```javascript
import { readFileSync } from 'node:fs';
import { prepareConfig } from './scripts/ralph/ralph-config.mjs';
const raw = JSON.parse(readFileSync('.agents/ralph.config.json', 'utf8'));
const effective = prepareConfig(structuredClone(raw), { captureControlPlane: false });
const get = (object, key) => key.split('.').reduce((value, part) => value?.[part], object);
const keys = ['maxIterations', 'maxTurns', 'maxTestFixAttempts', 'maxReviewFixAttempts'];
for (const group of ['runtime', 'supervisor', 'milestoneReview']) {
  for (const [key, value] of Object.entries(effective[group])) {
    if (typeof value === 'number') keys.push(`${group}.${key}`);
  }
}
for (const key of keys) {
  console.log(JSON.stringify({ key, value: get(effective, key),
    source: get(raw, key) == null ? 'умолчание' : 'файл' }));
}
```

Роли, фазы, команды, `reviewSeverityFloor`, `autoApproveConfiguredIssues`,
`trustedIssueAuthors`, `developmentSkills`, режимы задач и артефакты прочитай
отдельно. Значения секретов в `validationEnvironment` не выводи. Если загрузка
не удалась, покажи ошибку и доступные исходные значения; полный набор
действующих лимитов пока не установлен.

## Что считать лимитами

Показывай фактические числа; этот список объясняет область, а не задаёт их:

| Ключ | Область и поведение |
| --- | --- |
| `maxIterations` | Сессии разработки на фазу, включая повторы; бюджет переживает перезапуск. |
| `maxTurns` | Одна сессия разработки или ревью issue. У Claude шаг — ответ модели, у Codex — элемент сессии, включая команды. |
| `maxTestFixAttempts` | Неудачные проверки задачи до остановки; 1 означает остановку на первой неудаче. |
| `maxReviewFixAttempts` | Отказы ревью подряд; на пределе issue откладывается, включённая Lisa может помочь. |
| `milestoneReview.maxTurns` | Шаги одной сессии ревью фазы. |
| `milestoneReview.maxFindings` | Замечания за круг ревью фазы, а не число кругов. |
| `supervisor.maxInterventions` | Вызовы Lisa на фазу; сохраняются между запусками. |
| `supervisor.maxAdditionalIterations` | Ограниченный резерв Ralph; успешное вмешательство добавляет не больше одной итерации. |
| `supervisor.maxTurns`, `supervisor.timeoutMs` | Шаги и время сессии Lisa, в том числе отдельной проверки ремонта. |
| `runtime.commandTimeoutMs` | Общее время обычной внешней команды. |
| `runtime.validationTimeoutMs` | Время Git-коммита, несмотря на имя поля. |
| `runtime.validationRunTimeoutMs` | Время выбранного набора команд проверок. |
| `runtime.commandIdleTimeoutMs` | Тишина stdout/stderr команды. |
| `runtime.agentTimeoutMs` | Общее время сессии разработки или ревью. |
| `runtime.agentFirstEventTimeoutMs`, `runtime.agentIdleTimeoutMs` | Ожидание первого и следующего события CLI. |
| `runtime.reviewRetryAttempts` | Полные попытки ревью при техническом сбое, включая первую; не исправления замечаний. Общий таймаут и лимит шагов не повторяются. |
| `runtime.networkRetryAttempts`, `runtime.networkRetryBaseDelayMs` | Попытки сетевой команды и базовая пауза повтора. |
| `runtime.maxPages` | Страницы GitHub; превышение останавливает очередь, не обрезает её. |

Смысл остановок сверяй с hints и текущим кодом. Не называй счётчик фазы лимитом
одного запуска. При уменьшении лимита ниже уже использованного покажи,
что следующая попытка не поместится; не обнуляй сохранённые счётчики.

## Окружение и очередь

- Проверь Node.js по требованиям установленного Kit, Git, `gh`, CLI разработки
  и включённой Lisa в PATH. `--check` проверяет CLI разработки через `--version`.
- Вход проверяет `verifyAgentAuthentication(config)` из
  `ralph-agent-backends.mjs`. В отдельном Node-процессе загрузи конфиг через
  `loadConfig()` и вызови её для `config`; при включённой Lisa также для
  `{ ...config, agentCli: config.supervisor.agentCli }`. Это проверка входа,
  не генерация. У Claude проверяется наличие поддерживаемого токена окружения;
  обычный интерактивный вход не заменяет его. Доступ к модели этим не доказан.
- Проверь `gh auth status`, выбранный `githubAccount`, права записи и соответствие
  GitHub-репозитория локальному `origin`. Git push и gh могут иметь разные
  учётные данные. Не проверяй запись созданием тестовой issue/PR или push.
- Получи runtime-путь через `git rev-parse --git-path ralph-loop`. У lock проверь
  живой процесс; из `state.json` читай только фазу, ветку, задачу, этап,
  использованные итерации, вызовы Lisa, резерв, счётчики исправлений
  и `validationPathDirectories`. Последнее поле содержит принятые пути
  инструментов для продолжения после Lisa. Для вызова runner прочитай также
  `approvedIssueSnapshots` внутри процесса, не выводя тела задач в чат.
  Не записывай состояние средствами навыка и не снимай чужую блокировку.
- При сохранённой задаче сверяй её ветку/HEAD и восстановимость по `--check`.
  При любой сохранённой issue не меняй конфиг и HEAD: даже коммит только
  настроек может блокировать продолжение. Для `committed/pushed/reviewing/closing`
  нужен точный HEAD; рабочие этапы и staging также проверяют сохранённые
  коммит и дерево. Действующий запуск проверяй без изменения настроек. Смена настроек требует сначала завершить задачу либо
  отдельно разобрать штатное `--accept-manual-commit` по документации.
  Не применяй его автоматически: оно меняет состояние и сбрасывает результаты
  проверок, а при `active=false` не выполняется.
  Для новой фазы из чистого дерева создай/выбери настроенную ветку от её
  фактической базы. Существующую ветку не сбрасывай. Смена ветки не должна
  унести согласованные настройки. Check ветки не создаёт и не переключает.
- Обнови нужные remote refs через fetch и проверь доступность базы.
  `--check` использует уже имеющиеся refs. Возможный конфликт будущего слияния
  не отмечай проверенным без проверки истории/слияния в изоляции.
- Проверь milestones всех фаз: точные названия, отсутствие дублей, статус,
  доступность базы текущей фазы и порядок зависимых фаз. Будущая база может
  создаваться предыдущей настроенной фазой; не требуй её заранее. Сверь PR,
  чтобы не повторить работу.
- Проверь открытые issues всех фаз, их авторов и режимы. Для автоматического
  одобрения допустимы владелец репозитория и `trustedIssueAuthors`; у организации
  автор-человек не становится доверенным из-за членства. В ручном режиме сверяй
  title/body со снимком штатными правилами `ralph-issue-contract.mjs`.
  Не подменяй снимок и хеш вместо одобрения изменившейся задачи.
- Сравни остаток итераций с очередью: одна задача требует минимум одной итерации
  лишь когда ей нужна разработка; повторы заранее неизвестны. При ручном
  одобрении назови ожидаемую остановку на новых issues ревью фазы.

## Команды проекта

`--check` не выполняет preflight, validation и браузерные проверки. На текущем
CLI exit 0 совместим с предупреждением о недоступной очереди, отсутствии прав
записи или непроверенной базе. Оцени текст результата и отдельные проверки.

Для реальных команд в отдельном Node-процессе:

1. Загрузи конфиг через `loadConfig()` и выбери конфигурацию фактической фазы;
   используй `configForPhase` из `ralph-config.mjs`. Для продолжения объедини
   `state.approvedIssueSnapshots` с `config.approvedIssueSnapshots` в памяти,
   как делает CLI: иначе принятый режим задачи может потеряться.
2. При продолжении прочитай сохранённые `validationPathDirectories` и передай
   их как `options.validationPathDirectories` (без state — пустой список).
   Отдельный процесс не имеет `activeStateStore`, поэтому сам их не подхватит.
   Не копируй весь PATH и не обходи штатную проверку допустимости этих путей.
3. Используй `runConfiguredValidation(config, options)` из
   `ralph-validation-runner.mjs`. Он применяет runtime-окружение, удаляет только
   разрешённые артефакты и сам запускает preflight перед проверками. Не вызывай
   `runPreflight` дополнительно без необходимости повторной подготовки.
4. Всегда передавай правильный `scope` (`issue`, `phase`, `baseSync`),
   даже с обычным `validationScripts`: по нему добавляются браузерные команды.
   Для `validationProfiles` обязателен также `baseCommit` — полный SHA
   реальной базы сравнения. При проверке задачи передай `issueNumber`, чтобы
   учесть её process pack и браузерные команды. До первого запуска используй
   проверенный снимок текущей issue в памяти; не пиши одобрение
   в журнал вместо владельца.
   Найди базу по текущему состоянию и истории, не подставляй HEAD для пустого diff.
   Для ещё не начатой задачи проверка текущей базы доказывает только готовность
   окружения: будущие изменения и их сценарии пока проверить нельзя.
5. Не выдавай один scope за все профили. Проверь применимые команды каждого
   профиля на имеющихся входах; неподготовленные будущие сценарии укажи отдельно.
   Если профиль на пустом diff ничего не запускает, нужна существующая проектная
   smoke/regression-команда для проверки стенда; не придумывай её без договора.
6. До запуска прочитай команды и договор проекта: preflight может менять файлы,
   а уборка удаляет `validationArtifactPaths`. Проверь нужные тестовые сервисы
   и секреты в том же окружении, не направляй подготовку на рабочие данные.
   Если нужен доступ или отдельное разрешение, заверши независимые проверки
   и назови точное препятствие.
7. Сохрани код возврата и короткий итог. Коды 75/76/78/79 означают особые отказы
   из `scripts/ralph/README.md`; не превращай их в успех повтором или отключением
   теста. После команд проверь tracked/untracked файлы и исходники на изменения.

## Полная команда запуска

Подставь проверенный абсолютный путь, без `<проект>` и переменных из чата.
Для PowerShell удваивай апостроф внутри одинарных кавычек. Объедини переход
и запуск в один script block: ошибка перехода должна прервать весь блок:

```powershell
& {
  Set-Location -LiteralPath 'F:\путь к проекту' -ErrorAction Stop
  node .\scripts\ralph\ralph-loop.mjs --run --ui=split
}
```

Для Bash/Zsh используй POSIX quoting; апостроф внутри пути — `'"'"'`:

```sh
cd -- '/полный/путь к проекту' && node scripts/ralph/ralph-loop.mjs --run --ui=split
```

Split UI включается штатным CLI, сервер GUI для этого не нужен. Не добавляй
установку пакетов, смену GitHub-аккаунта, скрытую активацию и коммит в блок запуска.
Все необходимые настройки и фиксация должны быть готовы до передачи команды.
