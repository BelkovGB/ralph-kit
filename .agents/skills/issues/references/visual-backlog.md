# Обзор задач и зависимостей

Сначала покажи задачи по фазам, затем — схему прямых зависимостей, когда она
помогает понять порядок работ. Бери содержание из плана, связанного PRD и кода;
архитектуру учитывай только при её подключении. Таблица аудита задаёт порядок,
а обзор объясняет его, не вводя второй источник требований.
Для нового комплекта показывай фактические пути `active/<слаг>/` и его неизменный
слаг. Перенос не означает выполнения задач. Исторические ссылки по SHA сохраняй.

## Обзор и детали

Покажи все фазы с их результатами и входящими задачами. При выборе задачи
раскрой создаваемый результат, наблюдаемый критерий готовности и прямые
зависимости. Полное тело доступно по запросу. В сухом прогоне полное тело первой
создаваемой issue остаётся обязательным: краткая карточка его не заменяет.
Большой план раскрывай по фазам, не скрывая существование остальных задач
и обнаруженных конфликтов. Для одной задачи достаточно короткой таблицы
или описания без переключателей и графа.

Названия, критерии, контракты и применимые ID архитектуры совпадают с проверенными
документами. Если для обзора нужны временные ID задач, обозначь их как локальные:
это не номера GitHub и не новые поля тела issue. Настоящие номера и ссылки
показывай только по данным GitHub.

## Зависимости и исполнение

Стрелка идёт от поставщика результата к задаче, которая его использует.
Показывай только прямые зависимости; существующую основу отличай от будущей
задачи. Выбор задачи может выделять её входящие связи и раскрывать предпосылки.

Отдельно подпиши основания веток фаз и условие завершения базовой фазы.
Зависимость от одной её задачи не отменяет ожидания всей базовой фазы.
Ralph выполняет фазы в порядке конфига, а issues — по возрастанию номеров;
отсутствие прямой связи не обещает одновременного запуска.
Каждая фаза принимает одну `baseBranch`, содержащую все её основания.
Две фазы от общей базы сами не получают изменения друг друга; схема не
подразумевает объединения веток.

## Что проверено

Различай план, результат аудита и фактическую сверку GitHub. `PASS` означает
прохождение аудита, а не выполненные задачи или пройденные продуктовые тесты.
До сверки GitHub не присваивай статусы «создаётся», «есть» или «пропущена».
В сухом прогоне бери их из полного сопоставления по правилам создания;
после записи показывай проверенные номера, milestones и прямые зависимости.
Учебный пример помечай как учебный, без выдуманной готовности и публикации.

При `FAIL` выдели конкретную задачу, нарушенную связь или пробел требований
и предложи минимальное исправление плана с последствиями. Схема не исправляет
план и не делает его пригодным к созданию issues. Не придумывай сроки,
стоимость или проценты выполнения для заполнения обзора.

## Правки через квиз или чат

Просмотр, выбор узла, раскрытие и сохранённое состояние не принимают решение,
не редактируют документы и не запускают создание или изменение GitHub issues.
Получай правки через явно отправленный ответ на квиз или сообщение в чате.
Квиз нужен для нерешённого продуктового выбора, изменения согласованного объёма
или существенных последствий для владельца: реальные варианты, рекомендация
с последствиями и возможность своего ответа. Уже известное не спрашивай заново;
минимальное техническое исправление зависимости предложи сам.

По прямому поручению изменить план сверь правку с PRD, кодом и подключённой
архитектурой, сохрани только разрешённые изменения и обнови обзор.
При нарушении зависимости или согласованного результата объясни ограничение,
не меняя объём молча. Повтори аудит, а перед записью GitHub — сверку источников
и существующих задач; прежний `PASS` больше не подтверждает изменённый план.
Старый обзор обнови или обозначь как устаревший. Состояние прежнего компонента
не отменяет новую версию документов.

Просмотр и просьба исправить план сами по себе не заменяют прямой вызов
`/issues` с путём к плану. При таком вызове успешный аудит, сверка и сухой прогон
ведут к созданию без нового запроса подтверждения. Визуальные правки не разрешают
обновлять существующие issues: правила совпадения заголовков, тел и SHA остаются
в инструкции создания.

## Формат

Используй доступные средства чата по их документации. Интерактив раскрывает
задачи и связи; для статичного графа достаточно Mermaid. Без интерактива сохрани
тот же порядок и содержание в таблице и текстовой схеме. Устанавливать плагин,
SDK или сервер ради обзора не нужно. Подписи читаются без цвета; выбор и
раскрытие доступны с клавиатуры.
