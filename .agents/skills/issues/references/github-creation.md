# Создай беклог в GitHub

Выполняй эту инструкцию только после `Логическая проверка: PASS`. Таблица аудита
задаёт порядок и прямые зависимости задач.

## Подготовь данные

1. Узнай репозиторий:
   `gh repo view --json nameWithOwner --jq .nameWithOwner`.
2. Прочитай все страницы меток и milestones. Подставь `nameWithOwner` из шага 1.
   Каждая строка вывода содержит одну запись в JSON.

   ```text
   gh api --paginate "repos/<nameWithOwner>/labels?per_page=100" --jq '.[] | .name | @json'
   gh api --paginate "repos/<nameWithOwner>/milestones?state=all&per_page=100" --jq '.[] | {number, title, state} | @json'
   ```

3. Сопоставь milestones с фазами по точному названию среди открытых и закрытых
   записей. Если одному названию соответствуют несколько milestones, остановись
   до записи. Укажи их номера и состояния. Для каждой найденной фазы прочитай
   все страницы задач по `number` её milestone. Для новой фазы этот запрос
   пропусти.

   ```text
   gh api --paginate "repos/<nameWithOwner>/issues?milestone=<number>&state=all&per_page=100" --jq '.[] | select(.pull_request == null) | {number, title, body, labels: [.labels[].name], milestone: .milestone.number} | @json'
   ```

   Если чтение любой страницы завершилось ошибкой, остановись до записи. По
   неполному списку нельзя определить, каких сущностей нет.
4. Убедись, что commit плана запушен, и запомни его SHA. При продолжении
   частично созданного беклога возьми SHA из источников уже созданных задач
   этого плана: новый commit не должен менять их тела. Разные SHA или
   несовпадение документов с проверенным планом — конфликт до записи в GitHub.
   Ссылки должны вести на `/blob/<sha>/<каталог документов>/...`.
5. Проверь план и PRD на этом SHA до изменений GitHub:
   `gh api "repos/<nameWithOwner>/contents/<каталог документов>/plan-<слаг>.md?ref=<sha>" --jq .name`
   `gh api "repos/<nameWithOwner>/contents/<каталог документов>/prd-<слаг>.md?ref=<sha>" --jq .name`
   Если план ссылается на архитектуру, проверь также её:
   `gh api "repos/<nameWithOwner>/contents/<каталог документов>/architecture-<слаг>.md?ref=<sha>" --jq .name`
   Содержимое файлов на SHA должно совпадать с проверенным комплектом.
   При подключённой архитектуре сверь хеши входов плана с документами этого SHA.
   Без неё документ архитектуры и хеши не требуются. Сравнивай текст в UTF-8
   без BOM с переводами строк LF. При несовпадении остановись до записи в GitHub.

## Составь issue

Заголовок — короткое действие в повелительном наклонении.

Тело:

```markdown
## Контекст

**Фаза:** {название фазы}
**Цель фазы:** {цель фазы}
**Затрагивает:** {слои}

## Задача

{текст задачи из плана}

## Зависимости

{заголовки прямых предыдущих задач или «Нет»; для другой фазы укажи её название}

## Критерий готовности

{наблюдаемый результат и способ его увидеть}

## Не входит

{соседние задачи, которые можно принять за часть этой}

## Источник

- [План](https://github.com/{nameWithOwner}/blob/{sha}/<каталог документов>/plan-<слаг>.md)
- [PRD](https://github.com/{nameWithOwner}/blob/{sha}/<каталог документов>/prd-<слаг>.md)
```

Только при подключённой архитектуре добавь перед «Не входит» раздел
«Архитектурные договорённости»: применимые ID решений и нужные задаче контракты,
имена и ограничения. В «Источник» добавь ссылку на документ архитектуры по тому
же SHA. Без архитектуры не добавляй эти раздел и ссылку, даже пустыми:
существующие тела issues должны сохраняться при повторном запуске.

Критерий описывает результат одной задачи, а не готовность фазы. Не используй
«работает корректно», «стало быстрее» и другие непроверяемые оценки. Если
проверка ручная или зависит от внешнего сервиса, укажи это. Если критерий требует
решения, которого нет в плане, PRD, коде или применимой архитектуре, остановись
до изменений GitHub и назови недостающее решение.

Укажи только прямые зависимости. Метки: тип (`enhancement`, `documentation`,
`bug`), слой из плана и слаг фичи. Автор issue должен владеть репозиторием или
входить в `trustedIssueAuthors` Ralph.

## Проведи сухой прогон

До изменений GitHub напечатай:

- `Логическая проверка: PASS` и таблицу аудита;
- каждый milestone с пометкой `создаётся` или `есть`;
- каждую issue в порядке плана с пометкой `создаётся` или `пропущена`;
- полное тело первой создаваемой issue.

Не запрашивай подтверждение после сухого прогона. Проверь, что число issue равно
числу задач плана, критерии не повторяются, а каждая прямая зависимость ведёт на
базовый код или более раннюю задачу.

- В пределах фазы сопоставь задачи по точному заголовку. Пропусти issue только
  при единственном совпадении заголовка и полном совпадении тела. Проверь
  оставшиеся issue со ссылкой на путь проверяемого плана в разделе «Источник»
  независимо от SHA. Несопоставленная issue из этого плана, расхождение тел
  или несколько issue с одним заголовком — конфликт. Остановись до записи.
  Покажи номера и поля, которые различаются. Изменение существующей issue
  требует отдельного поручения. Ralph хранит неизменяемый снимок её тела.
- Если в закрытом milestone все задачи совпали, переиспользуй его с прежним
  статусом. Если в нём не хватает задачи, остановись до записи. Назови milestone
  и недостающую задачу.
- До создания проверь номера найденных задач и их прямых зависимостей. Если
  новую задачу пришлось бы вставить перед уже созданной задачей по порядку
  плана, остановись до записи. Укажи конфликтующие задачи.

## Создай беклог

1. Создай отсутствующие метки. Переиспользуй существующую метку слоя вместо
   синонима:
   `gh label create "<метка>"`
   `gh label create "<слаг>" --description "<название фичи>"`
2. Создай отсутствующие milestones. Дубликат названия остановит Ralph:
   `gh api repos/:owner/:repo/milestones -f title="Фаза N: название"`
3. Создай issue строго по таблице аудита:
   `gh issue create --title "..." --body-file "<файл>" --label "..." --milestone "..."`
   Пиши тела во временный каталог вне репозитория. Не передавай многострочный
   Markdown аргументом оболочки.

При ошибке `gh issue create` остановись и назови задачу. Повторный запуск
пропустит полностью совпавшие сущности и продолжит с неё.

## Проверь результат

Убедись, что номера issue возрастают по плану, а номер каждой зависимости меньше
номера потребителя. Проверь milestone и метку фичи у каждой issue. Напечатай
номера, заголовки и прямые зависимости.

Затем напечатай блок для `.agents/ralph.config.json`:

```json
"phases": [
  {
    "milestone": "Фаза 1: название",
    "branch": "ralph/<слаг>-phase-1"
  },
  {
    "milestone": "Фаза 2: название",
    "branch": "ralph/<слаг>-phase-2",
    "baseBranch": "ralph/<слаг>-phase-1"
  }
]
```

`milestone` повторяет точное название. `baseBranch` — ветка прямой зависимости;
у независимой фазы поле отсутствует.

Заверши вызов отчётом и блоком `phases`. Правка конфига, коммит и запуск Ralph
требуют отдельного поручения.
