# Issues из плана

По указанному плану создай один milestone на фазу и одну issue на задачу. Навык
запускает только прямая команда с путём к плану. Если пути нет, запроси его.

Issue должна быть самодостаточной. Ralph выполняет задачи по возрастанию номеров,
поэтому каждая задача опирается только на базовую ветку, завершённые фазы и более
ранние issue своей фазы.

## Проверь план

1. Прочитай план, связанный PRD, архитектуру и проектные инструкции. Каталог документов по
   умолчанию — `docs`, если проект не задаёт другой.
2. Доступным средством поиска найди в коде названные сущности и тесты. Читай
   только файлы, нужные для проверки предпосылок.
3. Для каждой задачи выпиши фазу, создаваемый результат, нужные сущности, прямые
   зависимости и наблюдаемый критерий готовности.
4. Проверь граф и содержание задач по правилам ниже.
5. Проверь версии входов плана и актуальность архитектуры: требования, значимые
   контракты и зависимости. Отсутствующая архитектура или влияющее на задачи
   расхождение — FAIL с минимальным исправлением; не создавай её и не меняй
   план в режиме issues. Для старого плана сначала нужен solution-architect
   и обновление его ссылок. Редакционное расхождение объясни отдельно,
   предложив актуализацию метаданных без пересмотра всего решения.

План проходит аудит, только если:

1. Каждая зависимость уже есть в базовой ветке или создаётся раньше. В графе нет
   циклов и ссылок вперёд. `baseBranch` зависимой фазы содержит все её базовые
   фазы; Ralph принимает только одну базовую ветку.
2. Каждая issue завершается рабочим изменением и оставляет проходящие проверки.
   Код, его тесты и первая используемая ими зависимость входят в одну issue.
   Точка входа не ждёт поведения из будущей задачи.
3. Потребитель следует после поставщика: структура данных и контракт появляются
   до использующего кода, реализация — до точки входа, сквозная проверка — после
   полной цепочки. Добавляй только применимые звенья.
4. Проверки и операции используют только сущности и возможности, существующие
   на этом шаге. Проверку будущего поведения закрепляй за более поздней задачей.
5. Задачи покрывают требования PRD в обе стороны. Предметные инварианты,
   переходы состояний, ошибки, целостность и конкурентные сценарии закреплены за
   конкретными задачами. Отложенное требование присутствует позже.
6. Задачи не дублируют друг друга и не выполнены текущим кодом. Если поведение
   уже есть, остановись и предложи удалить задачу или описать реальный пробел:
   Ralph не должен угадывать commit для `ALREADY_FIXED`.
7. Критерий готовности наблюдаем через команду, запрос или экран. Раздел
   `Не входит` ему не противоречит, а объём задачи помещается в одну автономную
   сессию. Не создавай отдельные issue на тесты, валидацию или control plane
   Ralph; его пути перечислены в `.agents/RALPH.md`.

8. Задачи покрывают решения архитектуры, используют одинаковые контракты и
   не вводят неописанные сервисы/технологии. Существенное решение не оставлено
   на усмотрение свежей автономной сессии. В теле задачи есть применимые ID
   архитектурных решений и необходимые договорённости, а не только ссылка.

## Заверши аудит

При конфликте напечатай `Логическая проверка: FAIL`. Назови фазу, задачу,
нарушенную зависимость и минимальную правку плана. Не меняй план без прямой
просьбы пользователя и не изменяй GitHub.

При успехе напечатай `Логическая проверка: PASS` и таблицу: задача, прямые
зависимости, создаваемый результат, критерий готовности, решения архитектуры.
Также напечатай `Соответствие архитектуре: PASS`. Таблица задаёт порядок
issue.

Только после `PASS` прочитай целиком
[инструкцию создания в GitHub](references/github-creation.md) и выполни её.
