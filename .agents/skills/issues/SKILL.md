# Генератор issues из плана

Скилл читает план из файла, названного в аргументе команды, и создаёт задачи
только по нему. Запускает его прямая команда: просьба вроде «заведи задачи»
запуском не считается — спроси, какой файл плана брать.

Issue самодостаточна: агент, у которого есть только её тело и ссылки из тела,
делает задачу правильно. Этим разрешается сомнение о любой формулировке ниже.

Одна фаза — один milestone, одна задача — одна issue. Ralph берёт issue
milestone по возрастанию номера, поэтому создавай их строго в порядке плана.

Каталог документов задаёт проект: по умолчанию `docs`, но если файл инструкций
проекта называет другой — бери его.

## Порядок действий

1. Прочитай план.
2. Узнай репозиторий и подставляй его во все ссылки:
   `gh repo view --json nameWithOwner --jq .nameWithOwner`
   Ошибка в ссылке необратима: тело issue после создания не редактируется.
3. Убедись, что коммит с планом запушен, и запомни его SHA. Ссылка на план в теле
   issue делается постоянной — `/blob/<sha>/<каталог документов>/...`: файлы плана
   и PRD удаляются после сдачи фичи, а ссылка на ветку после этого отдаёт 404.
4. Проверь обе ссылки тела issue до того, как создашь что-либо:
   `gh api "repos/<nameWithOwner>/contents/<каталог документов>/plan-<слаг>.md?ref=<sha>" --jq .name`
   `gh api "repos/<nameWithOwner>/contents/<каталог документов>/prd-<слаг>.md?ref=<sha>" --jq .name`
   Команды проверяют репозиторий, SHA и оба пути. Ошибка — останов: незапушенный
   коммит или PRD под другим путём даёт 404 сразу во всех телах issue.
5. Прочитай текущее состояние репозитория, ничего не меняя: метки
   `gh label list`, milestones `gh api repos/:owner/:repo/milestones --jq '.[].title'`,
   заведённые issue каждой фазы
   `gh issue list --milestone "<название>" --state all --json number,title --jq '.[].title'`.
   У milestone, которого в списке нет, issue не спрашивай: команда вернёт ошибку.
6. Напечатай сухой прогон (раздел «Проверка перед созданием»). До этой печати
   GitHub не менялся.
7. Заведи метки, которых нет в списке, включая метку фичи — слаг плана: без них
   первая же команда создания issue упадёт.
   `gh label create "<метка>"`
   `gh label create "<слаг>" --description "<название фичи>"`
   Метку слоя, которая уже есть под другим словом, переиспользуй: иначе синонимы
   `api`, `backend`, `бэкенд` копятся от фичи к фиче.
8. Заведи milestone тех фаз, которых нет в списке:
   `gh api repos/:owner/:repo/milestones -f title="Фаза N: название"`
   Два одноимённых milestone останавливают прогон Ralph: он не может выбрать,
   какой из них взять.
9. Создай issue задач фазы в порядке плана:
   `gh issue create --title "..." --body-file "<файл тела>" --label "..." --milestone "..."`
   Тело идёт файлом, а не строкой: многострочный markdown в аргументе оболочки
   ломается в PowerShell и в bash по-разному, а испорченное тело не исправить.
   Файлы тел пиши во временный каталог вне репозитория: посторонний файл в
   рабочем дереве ломает прогон Ralph.
10. Напечатай блок `phases` для `.agents/ralph.config.json` (см. ниже).

## Формат issue

**Title** — действие задачи в повелительном наклонении, короткой строкой. Не
переноси предложение задачи целиком.

**Body**:

## Контекст

**Фаза:** {название фазы}
**Цель фазы:** {цель фазы}
**Затрагивает:** {слои}

## Задача

{текст задачи из плана}

## Критерий готовности

{наблюдаемый результат этой задачи и способ его увидеть}

## Не входит

{соседние задачи фазы, которые можно принять за часть этой}

## Источник

- [План](https://github.com/{nameWithOwner}/blob/{sha}/<каталог документов>/plan-<слаг>.md)
- [PRD](https://github.com/{nameWithOwner}/blob/{sha}/<каталог документов>/prd-<слаг>.md)

## Правила

- Критерий готовности — наблюдаемый результат, проверяемый снаружи, без чтения
  кода. «Работает корректно», «стало быстрее», «удобно» критериями не считаются.
- Критерий называет способ увидеть результат: команду, запрос, состояние экрана.
  Результат, который виден только человеку или только через внешний сервис,
  назови таким прямо в критерии, иначе агент придумает проверку сам и
  отчитается по ней.
- Критерий готовности выводится из самой задачи. Признак готовности фазы
  («Когда готова») в issue не копируется: изменениями одной задачи он не
  проверяется, и агент либо тянет в неё всю фазу, либо отчитывается о чужом
  результате.
- Останов вместо выдумки: если задача не превращается в критерий без решения,
  которого нет ни в плане, ни в PRD, — не создавай issue, назови человеку задачу
  и недостающее решение. Заглушка в неизменяемом теле дороже паузы.
- Метки: тип (`enhancement`, `documentation`, `bug`), слой и метка фичи. Слои
  называет сам план — своими словами, а не заранее заданным словарём.
- Тело issue после создания не редактируется: Ralph хеширует его в неизменяемый
  снимок и отклоняет issue, разошедшуюся со снимком.
- Автор issue должен быть владельцем репозитория или входить в
  `trustedIssueAuthors` конфигурации Ralph, иначе прогон её отклонит.

## Повторный запуск

- Задачу, чей заголовок уже есть у issue этой фазы (шаг 5), пропусти и напечатай
  «пропущена». Иначе второй запуск удваивает беклог.
- Метку и milestone создавай только когда их нет: иначе повторный запуск падает
  на уже заведённом.
- `gh issue create` вернул ненулевой код — останови цикл и назови задачу, на
  которой он встал. Следующий запуск продолжает с неё.

## Блок настроек прогона

В конце напечатай готовый блок для `.agents/ralph.config.json`, чтобы человек не
переносил названия milestone и ветки руками:

```json
"phases": [
  {
    "milestone": "Фаза 1: название",
    "branch": "ralph/<слаг>-phase-1"
  },
  {
    "milestone": "Фаза 2: название",
    "branch": "ralph/<слаг>-phase-2",
    "baseBranch": "ralph/<слаг>-phase-1"
  }
]
```

`milestone` — точное название milestone. `baseBranch` — ветка фазы из «Зависит от»;
у фазы, не зависящей ни от чего, его не пиши: возьмётся базовая ветка
репозитория.

## Проверка перед созданием

Напечатай план действий: по каждой фазе — название milestone с пометкой
«создаётся» или «есть», под ним заголовки issue в порядке плана с пометкой
«создаётся» или «пропущена», а после списка — полное тело первой создаваемой
issue. Печать ответа не ждёт. Затем проверь:

1. Число строк «создаётся» и «пропущена» вместе равно числу задач плана.
2. Ни у одной пары issue не совпадает критерий готовности.
3. Нет issue «прогнать валидацию» и issue «написать тесты».
4. Ни одна issue не требует менять control plane Ralph — файлы, которые задают
   поведение будущей сессии агента. Их список лежит в `.agents/RALPH.md`; здесь
   он не повторяется, потому что второй список путей разойдётся с первым при
   первом же изменении.

## Проверка после создания

1. Номера issue возрастают в порядке задач плана.
2. У каждой созданной issue есть milestone и метка фичи.
3. Напечатай номера с заголовками в порядке создания, чтобы порядок проверялся
   одним взглядом.

Следующий шаг: перенеси напечатанный блок `phases` в `.agents/ralph.config.json`
и закоммитить конфиг — на грязном рабочем дереве прогон не стартует. Затем проверь
настройку командой `node scripts/ralph/ralph-loop.mjs --check` и запусти прогон
командой `node scripts/ralph/ralph-loop.mjs --run`.
