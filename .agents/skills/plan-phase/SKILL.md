# Plan генератор

Прочитай PRD из файла, названного в аргументе команды, и составь план
реализации.

## Куда сохранить

`docs/plan-<слаг>.md`, где `<слаг>` — часть имени файла PRD после `prd-`. PRD
`docs/prd-user-profile.md` даёт план `docs/plan-user-profile.md`.

Каталог документов задаёт проект: по умолчанию `docs`, но если файл инструкций
проекта называет другой — бери его.

## Структура плана

# Plan: {Название}

**PRD**: [prd-<слаг>.md](prd-<слаг>.md)
**Дата**: {текущая дата}

## Фазы реализации

### Фаза 1: {название}

**Цель** Что получает пользователь после этой фазы.

**Зависит от** Фаза N, либо «ничего».

**Затрагивает** {слои, которые меняет фаза}

**Критерии PRD** Номера критериев готовности PRD, которые закрывает фаза.

**Задачи**

- [ ] Задача
- [ ] Задача

**Когда готова** Критерий готовности фазы.

## Что такое фаза

- Фаза даёт результат, который увидит пользователь. После любой фазы можно
  остановиться, и продукт остаётся рабочим.
- Слой — граница задачи, а не фазы. Backend-половина без своей frontend-половины
  не меняет для пользователя ничего, поэтому обе половины лежат в одной фазе, а
  backend-задачи идут раньше frontend-задач.
- Первая фаза — минимальный сквозной путь (Tracer Bullet).
- Фаз «документация» и «валидация» не бывает: документация принадлежит фазе,
  которая меняет контракт, а полный набор проверок репозитория выполняет
  прогон Ralph после каждой задачи.
- Если внутри фазы два результата, которые пользователь получит по отдельности,
  это две фазы.
- Порядок фаз — это порядок веток прогона: **Зависит от** называет фазу, на
  ветке которой строится следующая.

## Критерий готовности

**Когда готова** называет наблюдаемый результат, который проверяют снаружи, без
чтения кода: при <условии> система <результат>. «Работает корректно», «стало
быстрее», «удобно» — не критерии: снаружи их никто не проверит.

## Если фаза режется только по слоям

Фича кажется неделимой, пока её режут по слоям. Пройди оси разреза по порядку и
возьми первую, которая даёт пользователю результат:

- **Сценарий** — какой сценарий PRD полезен сам по себе, без остальных.
- **Тип данных** — на каком подмножестве данных фича уже полезна: один формат
  файла, одна роль, одна запись вместо списка.
- **Правило обработки** — какие проверки, права и особые случаи откладываются,
  не ломая основной сценарий.
- **Интерфейс ввода** — через какую одну точку входа поведение видно первым:
  форма, команда чата, ссылка.

Ни одна ось не даёт результата пользователю — фича описана слишком узко.
Остановись и спроси, а не выдумывай фазу.

## Что такое задача

- Одно предложение без союза «и». Два действия — две задачи.
- Тест задачи пишется внутри неё и должен быть написуем из кода этой задачи и
  предыдущих. Если тест требует кода следующей задачи, порядок неверный.
- Отдельной задачи «написать тесты» не бывает.
- Новая внешняя зависимость, сервис или модель — отдельная задача, и она первая
  в фазе.
- Задача расширяет предыдущую, но не переписывает её. Две задачи, меняющие одну
  функцию по разным причинам, склеиваются в одну.
- Задача называет имена, которые вводит: функцию, поле, эндпоинт, ключ
  конфигурации. Ralph выполняет каждую issue в свежей сессии и соседние не
  видит, поэтому имя, придуманное на ходу, разойдётся с тем, которого ждёт
  следующая задача.

## Сквозное переименование и смена формата

Переименование общего типа или смена формата ломает все вызовы разом. Одной
задачей такое изменение не сдать: пока вызовы переведены не все, валидация не
проходит, а прогон Ralph гоняет её после каждой задачи. Режь на три задачи:

1. Новая форма заводится рядом со старой, старая продолжает работать.
2. Вызовы переводятся на новую форму.
3. Старая форма удаляется.

Старая форма живёт до третьей задачи, поэтому каждая проходит валидацию. Здесь
правило о склейке задач не действует: три задачи меняют один код и третья
переписывает результат первой, но только так валидация проходит после каждой
из них.

## Правила

- План покрывает все критерии готовности PRD: каждый номер встречается хотя бы
  в одной фазе.
- Не расширяй объём за пределы PRD: каждая задача приближает хотя бы один
  пронумерованный критерий готовности.
- Решение, которого нет в PRD, не выдумывай: остановись и спроси.

## Проверка перед сохранением

Перечитай разделы «Что такое фаза», «Что такое задача» и «Правила» и проверь
план по каждому их пункту, затем проверь то, чего в них нет:

1. Каждое **Когда готова** проверяется снаружи, без чтения кода.
2. Имя, которое одна задача вводит, а другая использует, записано в обеих
   одинаково.

Не начинай реализацию. `/issues` ставит в тела issue ссылки по SHA коммита и
падает на незапушенном плане, поэтому следующий шаг — закоммитить и запушить план
и PRD, затем выполнить `/issues docs/plan-<слаг>.md`.
