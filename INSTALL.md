# Установка Ralph Kit в проект

Единый порядок установки для агента и принимающего её человека. Устройство
набора — в [README.md](README.md), договор проверок — в
[scripts/ralph/README.md](scripts/ralph/README.md). Все пути ниже — от корня
проекта-потребителя. После каждого шага проверьте указанный результат.

## 1. Определить рабочую папку и границы подготовки

Просьба «установить», «обновить» или «подготовить» не разрешает запуск автономного
цикла. До указания на запуск оставляйте `active=false`. Не создавайте второй
Ralph и не меняйте контрольные файлы во время действующего прогона.

Штатный способ — файлы Kit внутри проекта, с версией и конфигом в Git. Каталог
runtime обязан называться `scripts/ralph/`: модули вычисляют корень как два уровня
выше себя и выполняют там команды Git и GitHub. Общая установка вне проекта и
невидимая для Git локальная накладка сейчас не поддерживаются.

Работайте в выбранной пользователем копии. Отдельный clone или worktree допустим
для изоляции, но не является требованием Ralph: объясните причину и запишите
путь, исходный commit и способ переноса нужных незакоммиченных изменений.
Не применяйте `skip-worktree`, `assume-unchanged`, исключения отслеживаемых файлов
или пустые коммиты, чтобы представить незавершённую установку чистой.

Проверьте `git status --short` и `git ls-files -v`. При посторонних изменениях
сохраните их: не делайте reset/clean и не включайте их в коммит Kit. Используйте
согласованную изолированную копию либо дождитесь фиксации работы владельцем.
Запрос «Kit только локально» требует решения о хранении: гайд не обещает такой
режим и не разрешает обходить его отсутствие флагами Git.

**Результат:** известны абсолютный путь, ветка, HEAD, способ хранения и исходные
изменения. Установщик не запустил цикл и не спрятал изменения.

## 2. Проверить инструменты и доступ

- Проект — Git-репозиторий с remote на GitHub; `git --version` работает.
- `node --version` — 22 или новее; набор проверяется на Node.js 24.
- `gh --version` и `gh auth status` успешны, у выбранного аккаунта есть запись
  в репозиторий. При нескольких аккаунтах заполните `githubAccount`.
- CLI из `agentCli` доступен в PATH этого терминала: `codex --version` или
  `claude --version`. Codex требует `codex login`; Claude — поддерживаемый токен
  окружения из README. Не записывайте токены в конфиг или отчёт.
- Зависимости и тестовые сервисы проекта известны; их подготовка описана в шаге 5.

**Результат:** инструменты доступны процессу, который будет запускать Ralph.
Установка CLI и доступность модели — разные проверки: `--check` не выполняет
сессию модели и не доказывает её доступность.

## 3. Скопировать файлы и зафиксировать источник

Запишите версию Kit и SHA источника. Не смешивайте файлы разных версий.

| Путь в проекте | Владелец | При обновлении |
| --- | --- | --- |
| `scripts/ralph/**` | набор | заменить файлы поставки, сохранив файлы проекта |
| `.agents/RALPH.md`, `.agents/ralph-rules.md`, `.agents/review.schema.json` | набор | заменить |
| `.agents/skills/**` | набор и проект | заменить только навыки поставки |
| `.claude/skills/**`, `.claude/agents/**` | набор и проект | заменить только файлы поставки |
| `LICENSE` рядом с копией, например `scripts/ralph/LICENSE` | набор | заменить |
| `.agents/ralph.config.json` | проект | сохранить; при первой установке взять образец |
| `.agents/approved-issues.json` или существующий журнал | проект | сохранить содержимое и сверить хеш |
| собственные навыки, скрипты и обёртки проверок | проект | сохранить, даже внутри каталогов выше |
| `AGENTS.md`, `CLAUDE.md` в корне и вложенных каталогах | проект | сохранить; дополнить по необходимости |
| строки `.gitattributes` и `.gitignore` | проект | сверить с шагом 4 |

Граница владения — перечень файлов поставки конкретной версии, а не название
каталога. При совпадении пути с файлом проекта разберите различия до замены.
Копируйте `.agents/skills/**` и `.claude/skills/**` вместе: первый содержит
тексты, второй — оболочки команд Claude. Ревьюерам нужны `.claude/agents/**`;
глобальная установка навыков их не заменяет.

В проект не копируют корневые `README.md`, `CHANGELOG.md`, `INSTALL.md`,
`eslint.config.mjs`, каталоги `docs/`, `templates/` и `.github/` набора.
Если проектных инструкций ещё нет, возьмите `templates/AGENTS.md` и
`templates/CLAUDE.md` как начальные `AGENTS.md` и `CLAUDE.md`. Существующие файлы
не заменяйте: добавьте недостающие сведения о стеке и командах.

**Результат:** runtime, навыки и инструкции на месте, версия источника известна,
проектные дополнения сохранены. Установка видна в diff и воспроизводима из Git.

## 4. Подготовить журнал и служебные пути

Для новой установки рекомендуемый журнал — `.agents/approved-issues.json`.
Создайте UTF-8 файл с содержимым `{}`. При обновлении перенесите существующий
журнал целиком, не заменяя пустым. Укажите путь в `approvedIssueSnapshotsFile`.
Историческое значение образца `scripts/ralph/approved-issues.json` допустимо,
но попадает в каталог обновления: диагностика предупредит об этом.

Добавьте в существующий `.gitattributes`:

```text
scripts/ralph/** text eol=lf
.agents/approved-issues.json text eol=lf
```

Для другого пути журнала добавьте правило LF именно для него. Правило не меняет
существующие байты: сохраните журнал с LF до вычисления хеша. CRLF после клона
на Windows иначе изменит хеш и остановит загрузку конфига. Из корня вычислите
SHA-256 точных байтов файла:

```bash
node --input-type=module -e "import{readFileSync}from'node:fs';import{createHash}from'node:crypto';console.log(createHash('sha256').update(readFileSync('.agents/approved-issues.json')).digest('hex'))"
```

Запишите результат в `approvedIssueSnapshotsHash`. Не используйте ошибку
`--check` как калькулятор хеша. Не перенормировывайте посторонние файлы.
В существующий `.gitignore` добавьте пять строк:

```text
.agents/last-review.json
.agents/last-milestone-review.json
.agents/.ralph.config.json.*.tmp
.claude/settings.local.json
.claude/scheduled_tasks.lock
```

**Результат:** путь и хеш согласованы, LF закреплён для фактического журнала,
служебные результаты не делают дерево грязным. Сам журнал не игнорируется.

## 5. Подключить проверки проекта

Настройте `.agents/ralph.config.json` в редакторе или через пульт:

```bash
node scripts/ralph/ralph-gui.mjs
```

| Поле | Назначение | Условие |
| --- | --- | --- |
| `preflightScripts` | зависимости, подготовка стенда, генерация | может менять файлы по договору проекта |
| `validationScripts` | тесты, lint, проверка актуальности генерации | не меняет отслеживаемые файлы и не оставляет новые исходники |
| `validationEnvironment` | строки `NAME=value` для проверок | только нужные настройки; секреты — по файловому договору проекта, не в конфиге |
| `validationArtifactPaths` | отчёты, покрытие, трассы | только удаляемые результаты; Ralph очищает эти пути |

Команды запускаются из корня проекта; переход в другой каталог должен быть
частью команды или обёртки. Генератор отслеживаемых файлов нельзя включать
в validation: Ralph остановится с `RALPH_VALIDATION_MUTATED`. Обёртка не
должна скрыто отключать обязательные тесты.

До передачи агенту выполните команды в порядке конфигурации и в описанном
Ralph окружении проверок. Успех в другом терминале не доказывает работу обёртки.
Сопоставьте требования фазы с выполненными сценариями: обязательные тесты
с SKIP остаются непроверенными. При необходимости подготовьте изолированную
тестовую БД по правилам проекта; не направляйте миграции в рабочие данные.

**Результат:** записаны команды, окружение, тестовые сервисы, результаты и
пропуски. Validation не меняет исходники. `--check` показывает команды, но
не выполняет их; отдельного универсального режима проверки команд пока нет.
Рецепты стека остаются в проекте или [docs/tips.md](docs/tips.md).

## 6. Выбрать очередь, модели и режим

Одна фаза — нативный milestone репозитория и ветка из `phases`. Название
milestone копируется точно. GitHub Project может быть доской статусов, но не
источником очереди. Assignee не является техническим требованием Ralph;
добавляйте его только по действующим правилам проекта.

Планирование: PRD → `plan-phase` → `issues`. `solution-architect` —
необязательный разбор сложных интеграций и контрактов перед планированием.
Согласуйте базовую ветку и убедитесь, что она содержит нужные документы и
инструкции. Модели/effort разработки, ревью issue и milestone, порог
`reviewSeverityFloor` задаются в конфиге, а не дублируются в правилах сессии.
`P3` блокирует дефекты P0–P3; лимиты исправлений при этом сохраняются.

| Настройка | Пробная задача | Полная фаза |
| --- | --- | --- |
| `active` при подготовке | `false` | `false` |
| `stopAfterFirstIssue` | `true` | `false` |
| `maxIterations` | бюджет задачи с повторами; `1` — одна попытка | бюджет исходных задач, повторов и новых задач ревью |
| `autoApproveConfiguredIssues=true` | подхватывает допустимые задачи | позволяет подхватывать новые задачи ревью без ручного снимка |
| `autoApproveConfiguredIssues=false` | заранее одобрить точный текст задачи | каждую новую review-issue оператор одобряет вручную |
| `trustedIssueAuthors` | доверенные авторы | доверенные авторы, включая автора задач ревью |

Автоодобрение не отключает ограничения milestone, доверенных авторов и проверки
снимка. Ручное одобрение допустимо, но останавливает непрерывное автоисправление.
Пробный прогон заканчивается после первой выполненной issue без PR и ревью
фазы. Бюджет итераций хранится между перезапусками: не удаляйте state ради
сброса. Переход к полной фазе требует изменения режима и лимитов.

**Результат:** режим назван, очередь и база проверены, поведение при новых
дефектах понятно. Одна попытка не представлена как готовность всей фазы.

## 7. Проверить и принять установку

Оставьте `active=false` и выполните:

```bash
node scripts/ralph/ralph-loop.mjs --check
```

Диагностика работает и при выключенном цикле. Она проверяет инструменты,
GitHub, конфиг и состояние продолжения; печатает версию, фазу, ветку, очередь,
бюджет, команды и предупреждения. Сессии модели, проверки проекта, push,
закрытие issues и PR не выполняются. Диагностика пишет локальный лог, берёт
блокировку и может обновить ссылки origin через fetch; не запускайте её
параллельно действующему Ralph.

В старых версиях `active=false` давал строку «Ralph Loop выключен» и exit 0
без диагностики. Не принимайте это как проверенную установку. Не включайте
автономный цикл ради этой проверки; сначала обновите Kit.

Self-tests запускают последовательно и только вне действующего цикла:

```bash
node --test --test-concurrency=1 "scripts/ralph/*.test.mjs"
```

Тесты временно меняют контрольные файлы и восстанавливают их. Не меняйте модели
проекта ради зелёных self-tests. До коммита диагностика может сообщить грязное
дерево без отказа, если нет сохранённой задачи; `--run` требует чистое дерево.
Проверьте diff и зафиксируйте только установку и её конфиг, затем повторите
диагностику. Все предупреждения должны быть исправлены или объяснены.

**Результат — паспорт установки:** абсолютная папка; версия/SHA Kit; HEAD,
ветка и база; аккаунт без секретов; milestone; модели/effort и порог; режим,
лимиты и способ одобрения; команды проверок; результаты, SKIP и препятствия;
точная команда запуска. Разделяйте «установка проверена», «пробный прогон
проверен» и «фаза завершена». Если запуск не разрешён, паспорт заканчивается
готовностью к запуску с `active=false`, а не запуском.

## 8. Запустить после разрешения

Перед запуском включите `active=true`, зафиксируйте конфиг и выполните
диагностику на чистом дереве. Три команды решают разные задачи:

| Команда | Назначение |
| --- | --- |
| `node scripts/ralph/ralph-loop.mjs --check` | диагностика без агента |
| `node scripts/ralph/ralph-loop.mjs --run --ui=split` | цикл с разделённым экраном терминала |
| `node scripts/ralph/ralph-gui.mjs` | браузерные настройки и наблюдение; не запускает и не останавливает цикл |

Split требует интерактивного TTY: Tab переключает журнал, Ctrl+C останавливает
цикл. Для перенаправления вывода используйте `--run` без `--ui=split`.
После пробной задачи проверьте изменения, тесты, ревью и состояние issue,
прежде чем переключать конфиг на полную фазу. Ralph не сливает PR автоматически.

## Обновление

1. Убедитесь, что цикл остановлен. Запишите версии и SHA до/после, прочитайте
   соответствующие записи CHANGELOG. Старший номер означает несовместимость.
2. Сохраните конфиг, журнал, инструкции, проектные дополнения и состояние из
   пути `git rev-parse --git-path ralph-loop`. Не публикуйте runtime-логи.
3. Сравните перечни файлов старой и новой поставки. Замените принадлежащие
   набору файлы из шага 3. Не очищайте общие каталоги целиком; сохраните
   проектные навыки и обёртки. Покажите список заменённых и сохранённых файлов.
4. Удаляйте только устаревшие файлы поставки. При переходе через 2.0.0 это
   `scripts/ralph/Dockerfile.validation`, `ralph-validation-entrypoint.sh`,
   `ralph-validation-docker-shim.sh`; из конфига удаляются `validationMode`,
   `validationContainer`, `validationDependencyPaths`. Файлы проекта не удаляйте.
5. Сверьте LF, ignore, путь и хеш журнала. Повторите проверки шага 7,
   просмотрите diff, закоммитьте обновление отдельно от продуктовой работы.
6. При незавершённой issue сохраните state и следуйте
   [порядку восстановления](scripts/ralph/README.md#продолжение-после-ручного-исправления).
   Обновление не означает разрешение на возобновление цикла.

## Удаление

Остановите цикл. По перечню установленной версии удалите файлы Kit из
`scripts/ralph/**`, `.agents/skills/**`, `.claude/skills/**`, `.claude/agents/**`,
а также `.agents/RALPH.md`, `.agents/ralph-rules.md`, `.agents/review.schema.json`
и `.agents/ralph.config.json`. Сохраните собственные навыки и обёртки проекта.
Журнал и runtime-состояние сохраните, если они нужны для аудита; runtime-путь
показывает `git rev-parse --git-path ralph-loop`. Уберите только служебные строки
ignore/attributes, которые больше не нужны. Проектные `AGENTS.md` и `CLAUDE.md`
остаются на месте.
