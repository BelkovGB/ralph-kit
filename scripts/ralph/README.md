# Проверки Ralph

## Область проверки

`validationProfiles` задаёт три команды или набора команд: `issue` после работы
над задачей, `phase` перед pull request и `baseSync` после слияния базы.
Все три профиля обязательны, если включён выборочный режим. Ralph передаёт
каждой команде `RALPH_VALIDATION_SCOPE` и полный SHA
`RALPH_VALIDATION_BASE_COMMIT`. Проектная команда сравнивает итоговое дерево с
этой базой и выбирает проверки по графу зависимостей.

После исправления проектная команда повторяет тест найденного дефекта и все
проверки, чьи входы изменились. Ранее успешный результат можно сохранить только
при неизменных коде, зависимостях, настройках и нужных сервисах. Команда должна
записывать охват, отпечаток входов, время и причину каждого повтора. Если
область влияния неизвестна, она завершает работу с кодом 79; Ralph останавливает
задачу для отдельного регресса. Полный регресс проекта запускается вне Ralph.

Код 75 означает сбой окружения, 76 — нестабильную проверку, 78 — существующую проблему проекта. Эти
результаты не создают новую попытку разработки. После разрыва соединения Ralph
может повторить упавшую команду для диагностики один раз. Успешный повтор
оставляет статус `RALPH_VALIDATION_UNSTABLE` и исходную ошибку.

Без `validationProfiles` Ralph сохраняет прежнее поведение `validationScripts`.

## Контроль зависших команд

`runtime.commandIdleTimeoutMs` ограничивает время без вывода в stdout или stderr
для внешних команд любого языка: тестов, сборок, Git и утилит. По умолчанию —
600000 мс (10 минут); настройка доступна в UI в разделе «Таймауты».
На пределе Ralph останавливает дерево команды, сохраняет её вывод и выдаёт
`RALPH_COMMAND_IDLE_TIMEOUT`. Включённая Лиза получает эту ошибку в пределах
своего бюджета. Изменения проекта сохраняются, успешной проверка не считается.

Тишина означает возможное зависание, а не доказанный deadlock. Команды с долгими
вычислениями без вывода требуют большего лимита или вывода реального прогресса.
Буферизация программы может скрывать прогресс. CPU и существование процесса
не считаются доказательством полезной работы. Общий таймаут остаётся обязательным,
даже если команда постоянно печатает сообщения. Для CLI агента отдельно действуют
`agentFirstEventTimeoutMs` и `agentIdleTimeoutMs` по событиям сессии.

## Продолжение после ручного исправления

`--check` проверяет возможность продолжить сохранённую задачу по тем же правилам,
что и `--run`: ветку, HEAD, рабочее дерево и этап восстановления. Он не меняет
Git-ветку и сохранённое состояние. Диагностика выполняется при `active=false`,
не вызывая агента и команды проекта. Она берёт блокировку, пишет локальный лог
и может обновить remote refs через fetch. Её успех не заменяет проверки проекта.

Если после остановки вы исправили задачу и создали коммит, добавьте ему trailer
`Ralph-Issue: #<номер задачи>`. Из чистой ветки задачи выполните:

```text
node scripts/ralph/ralph-loop.mjs --accept-manual-commit <полный SHA коммита задачи>
node scripts/ralph/ralph-loop.mjs --check
node scripts/ralph/ralph-loop.mjs --run
```

Первая команда только принимает коммит в сохранённую задачу. Она не запускает
агента, не отправляет ветку и не закрывает задачу. Следующий запуск повторит
все настроенные проверки и ревью. Счётчики попыток и замечания сохраняются,
прежний PASS и результаты проверок сбрасываются.

Если повторная проверка сохранённого коммита завершается `RALPH_VALIDATION_FAILED`
или `RALPH_COMMAND_IDLE_TIMEOUT`,
Ralph сохраняет HEAD как базу исправления и возвращает задачу в `working-tree`.
Включённая Лиза может исправить файлы, после чего Ralph повторяет разработку,
проверки и ревью. Старые результаты ревью сбрасываются; счётчики сохраняются.
Ошибки авторизации, границ рабочего дерева и изменения файлов самой проверкой
этот переход не разрешают.

При восстановлении сохранённой задачи Ralph не сливает базовую ветку: сначала
завершает работу на проверяемом HEAD. Синхронизация базы выполняется при запуске
без сохранённой задачи.

Ralph проверяет локальный HEAD отдельной сессией до push. `issue.reviewReceipt`
хранит SHA проверенного HEAD и вердикт отдельно от стадии публикации. При
повторном закрытии Ralph сверяет опубликованный SHA, сохраняя `PASS` для того
же HEAD. Если сессия вернула `FAIL`, Ralph сохраняет замечания до обращения к
GitHub. Неопубликованный коммит на лимите отказов блокирует публикацию ветки
до исправления issue. Сбой повторной проверки и переход к Lisa сохраняют
блокировку, пока Ralph не подтвердит отправку проверенного HEAD.

Коммит должен продолжать сохранённую базу. Все продуктовые коммиты после неё
должны относиться к той же задаче и входить в указанный коммит. После него
допускаются только изменения файлов самого Ralph. Слияния, посторонние правки,
чужая ветка и грязное дерево требуют отдельного разбора. Этапы `staging` и
`validation-mutated` восстанавливаются по прежним строгим правилам; ручное
принятие не обходит проверку сохранённого дерева.
После отклонённого ревью коммит должен менять файлы проекта относительно
отклонённого состояния. Пустой коммит и правка только файлов Ralph не подходят.

Не удаляйте `state.json` для обхода ошибки: вместе с ним теряется контекст
задачи. Для обычного продолжения без ручного коммита достаточно `--run`:
при чистом дереве он вернётся на ветку сохранённой задачи. `--check` и
`--accept-manual-commit` ветку не переключают.

Границу control plane и список файлов, которые сверяет проверка подделки,
описывает `.agents/RALPH.md`. Здесь — журнал одобренных issues, договор о
командах проверок и порядок их запуска.

## Разделённый экран CLI

В сессии Codex Ralph подписывает шаги по событиям CLI: поиск, чтение и изменение
файлов, тесты, работу в браузере и вызовы инструментов. Для знакомой команды он
показывает действие, например `git diff` → «Смотрит изменения». Неизвестную или
составную команду показывает с концом её строки, сокращая начало. Подпись
занимает не более 64 символов; полный вывод команды остаётся в журнале.
Подписи формируются локально, без запроса к модели; счётчик шагов и лимиты
сессии не меняются.

После `--run` в терминале остаётся итог прогона: успех, остановка до окончания
фаз или ошибка, длительность и путь к логу. Пульт закрывается автоматически
и освобождает клавиатуру; нажимать Ctrl+C после завершения не нужно.

Запустите `node scripts/ralph/ralph-loop.mjs --run`: разделённый экран включается
автоматически. Слева три раздела: «Прогон», «Задача и проверки», «Сессия и время».
Между разделами — пустая строка. Над обеими колонками стоит «СЕЙЧАС» с главным
этапом работы. Команда Git или ожидание ответа показаны ниже и не заменяют этап.
Экран один; меняются его данные:

| Работа | Главная строка |
| --- | --- |
| Задача | `Задача #… · Реализация`, `Проверки`, `Ревью` и другие этапы задачи |
| Между задачами | Обновление очереди, подготовка ветки или следующей задачи |
| Работа с фазой | Подготовка PR, ревью фазы, создание задач по замечаниям, переход фазы |
| Вмешательство Lisa | `Lisa: восстановление работы` |
| Завершение | `Прогон завершён` или `Прогон остановлен с ошибкой` |

В блоках — фаза, milestone, задача и счётчики «использовано / предел»:
итерации фазы, исправления тестов, отказы ревью, шаги агента и время сессии.
Во время ожидания показаны время без событий и предел остановки; до первого
ответа действует отдельный предел. Время команды сравнивается с её фактическим
таймаутом. Число ответов инструментов показано без предела: такого лимита нет.
Справа — короткие события Ralph, без подробного вывода агента.
При вызове Lisa слева появляются её имя, номер вызова и счётчик шагов; справа —
события и короткие сообщения её сессии. По Tab подробные сообщения Lisa
помечены `[Lisa]`.
«Вызовы Lisa за прогон» считает вызовы с текущего запуска `--run`, включая
предыдущие фазы. «Вызовы Lisa в фазе» показывает использованный бюджет и лимит
`supervisor.maxInterventions`; этот счётчик сохраняется между перезапусками
и сбрасывается при переходе к следующей фазе. При выключенном супервизоре
показано «Lisa: выключена».

Между задачами вместо пустой задачи показана текущая операция: обновление
очереди, подготовка PR, ревью фазы с номером PR, создание задач по замечаниям
или переход к следующей фазе. Слева видны текущая команда и время этапа.
Служебные сообщения о запуске и завершении команд остаются в логе по Tab.

Во время сессии пульт различает ожидание первого события, первого рабочего
шага после служебных событий и следующего события агента. «До остановки» —
время до ближайшего лимита сессии или отсутствия событий. Если CLI молчит,
прогресс работы провайдера неизвестен; на экране остаются последние факты.

«Сеть» и «Запуск ревью» показывают номер попытки из разрешённых, включая
первую. `2/3` означает один повтор и ещё одну разрешённую попытку. Завершённая
сетевая операция помечена «последняя». Это не счётчик разрывов соединения.
«Сделано в прогоне фазы» считает задачи, завершённые этим прогоном в текущей фазе;
«В очереди» — оставшиеся известные задачи. Отложенные после отказов ревью
показаны отдельно. Это не общая статистика milestone за всё время.

`Tab` переключает пульт и подробный лог текущей задачи на всю ширину окна.
В логе `PgUp`/`PgDn` листают историю, `End` возвращает слежение. Новые строки
не сдвигают просмотр старых. История начинается до нажатия Tab; при переходе
к следующей задаче она очищается. В памяти — последние 2000 строк до 2000
символов каждая. Длинные строки переносятся по ширине окна.
При перегрузке экран сообщает о пропущенных подробностях; они остаются в журнале.
Состояние этапа передаётся отдельно и не ждёт обработки накопленного лога.
Полный вывод агента и команд остаётся в журнале; путь найдёт команда
`git rev-parse --git-path ralph-loop/run.log`.

При ширине меньше 90 колонок или высоте меньше 16 строк сводка стоит над
событиями. Без TTY на stdout/stderr и при `TERM=dumb` работает обычный вывод.
При нехватке высоты шаги агента и ответы инструментов объединяются в строку.
Строки, которые всё равно не помещаются, обрезаются снизу.
`--ui=plain` явно выбирает обычный режим. `--ui=split` остаётся явным выбором
разделённого экрана для `--run`. Другие команды используют обычный вывод.

Экран работает в отдельном процессе и обновляется раз в секунду и при
сообщениях. Таймер, Tab и прокрутка работают во время синхронных команд
Git и проверок. Вывод таких команд появляется после их завершения.
Время сессии считается
с её начала в этом процессе; прошлые попытки в него не входят. Пропуски
показаны прочерком. Истории замечаний и общего процента готовности здесь нет.

`Ctrl+C` останавливает прогон в обоих режимах. После выхода возвращаются
прежний экран, курсор и режим клавиатуры, а последние три события остаются
в терминале. Для клавиш нужен TTY на stdin. Ctrl+C сразу показывает запрос
остановки; сам цикл обрабатывает его после синхронного участка. Мыши и
управления задачами нет. Если процесс экрана завершился с ошибкой, Ralph
продолжает работать с обычным выводом событий; подробности остаются в run.log.
Символы вне латиницы, кириллицы и базовой пунктуации
заменяются на `?`, чтобы ширина строк не зависела от терминала; в журнале
исходный текст сохраняется.

### Отчёт об остановке после ревью

Когда `--run` завершается с `needs-human` после парковки задач из-за отказов
ревью, Ralph сохраняет Markdown в отдельном каталоге. Его путь показывает
`git rev-parse --git-path ralph-loop/run-stop-reports`.
Путь к файлу виден в терминале после выхода и в шапке пульта. Отчёт показывает
отказы по попыткам, итог ремонта Lisa и сохранённые коммиты. Исход процесса
`needs-human` указан отдельно от сохранённого `state.status`.
Расход текущего запуска указан отдельно от накопленных счётчиков фазы.

Каждый такой запуск создаёт свой файл, даже если Ralph продолжил с тем же
`runId`. В отчёт попадают только служебные поля, числа и идентификаторы.
Тела задач, вывод агентов и подробности ошибок остаются в локальных артефактах.
Если файл записать не удалось, терминал показывает ошибку записи и причину
остановки прогона.

## Аккаунт GitHub

`githubAccount` содержит login аккаунта из `gh auth status`. Ralph читает токен
этого аккаунта командой `gh auth token --user`. Ralph добавляет токен только в
окружение своих процессов `gh` и сетевых команд Git: `fetch`, `push` и
`ls-remote`. Настройка не вызывает `gh auth switch`, не меняет глобальный active
account и не переписывает Git Credential Manager. Токен не хранится в конфиге,
аргументах команд и логах. Агент и проверки его не получают.

При заданном аккаунте `origin` должен иметь вид
`https://github.com/owner/repository.git`. SSH-origin использовал бы ключ
машины, а не выбранный аккаунт, поэтому Ralph отклоняет его. Для сетевых команд
Git Ralph закрепляет проверенный URL в памяти и передаёт его явно вместо
изменяемого `origin`. Поэтому последующая правка `pushurl` не меняет адрес
отправки. Ralph отключает hooks через отдельный пустой каталог; `push` также
получает `--no-verify`. Репозиторий не может прочитать токен через `pre-push`
или `reference-transaction`.

Если поле удалить, Ralph использует аккаунт, активный в GitHub CLI. Если login
не авторизован, `--check` останавливается до запуска агента.

## Журнал одобренных issues

`approved-issues.json` хранит запомненный текст issues, одобренных вручную. При
`autoApproveConfiguredIssues: true` — это умолчание — одобрением служит сам
закоммиченный план `phases`: Ralph берёт текущие заголовок и тело issues этих
milestone, если автор issue доверенный. Перед стартом агента Ralph замораживает
точный текст в состоянии прогона, поэтому правка issue в GitHub после старта
останавливает прогон. Issues с замечаниями ревью, которые Ralph заводит сам,
замораживаются тем же механизмом, и круг исправлений milestone идёт без
человека. Поставьте `false`, когда каждую issue нужно вносить в журнал руками.

В prompt сессии тело issue идёт из этого замороженного текста, а не из живого
тела на GitHub. Разница видна на блоке замечаний ревью: Ralph дописывает его в
тело issue сам, поэтому в замороженный текст блок не входит — иначе прогон
останавливался бы на собственной записи. Значит правку блока сверка не ловит, и
живое тело в prompt пускать нельзя: любой, кто вправе редактировать issue,
диктовал бы через него сессии. Замечания следующая сессия получает из состояния
прогона в служебном каталоге Git, а блок в теле остаётся для человека.
Отложенная issue состояние теряет вместе с прогоном: замечания к ней разбирает
человек, и следующий прогон начинает её по одному тексту автора. Путь к состоянию
показывает `git rev-parse --git-path ralph-loop`: в linked worktree он следует
указателю из файла `.git`.

Журнал защищён контрольной суммой: эталон лежит ключом
`approvedIssueSnapshotsHash` в `.agents/ralph.config.json`. Впишите новую сумму
тем же коммитом, которым добавляете запись, иначе прогон останавливается на
сверке. Команда вычисления SHA-256 приведена в INSTALL.md набора. Рекомендуемый
путь журнала — `.agents/approved-issues.json`, с отдельным правилом LF.
Обновление сохраняет конфиг и журнал независимо от расположения; собственные
обёртки и навыки проекта тоже не входят в перечень заменяемых файлов поставки.

## Договор о командах

Если Lisa нашла утилиту вне `PATH` проверок или поставила недостающую в свой
каталог кэша, она может вернуть `validationPathDirectories` в JSON-ответе.
Ralph принимает не более пяти существующих абсолютных каталогов вне проекта,
добавляет их в конец `PATH` команд подготовки и проверок и сохраняет в
`state.json` до конца фазы.
При остановке сохранённой issue Lisa может исправить скрипты самого Ralph. Исходные
требования остаются в управляющем процессе; независимое ревью проверяет ремонт,
штатная валидация подтверждает результат без изменения дерева. Принятый код
загружается новым процессом с той же issue, общим журналом и прежним бюджетом.
В конфиге Lisa может исправить команды `preflightScripts`, `validationScripts`
и существующих `validationProfiles`, сохранив обязательные проверки. Она может
исправить ошибочную команду или противоречие в инструкциях. Остальные настройки,
права, лимиты, критерии задачи и механизм передачи управления остаются неизменными.
Ревью запускается вне изменённого проекта с исходной политикой и полным diff,
включая инструкции, которые Git игнорирует. Исправленный конфиг загружается заново;
штатные проверки подготовки и валидации повторяются до продолжения задачи.
Это проверка целостности и ревью, а не изоляция от произвольного процесса с правами
того же пользователя. Скрипты проверки проекта по-прежнему исполняются на машине.
Ремонт доступен также на этапах `committed`, `pushed`, `reviewing`, `closing`.
Принятый diff текущей issue проходит валидацию, commit, push и ревью без новой
сессии разработки. Ранее опубликованная история сохраняется. Если issue уже
закрыта, этот же путь завершает ремонт без повторного закрытия; без принятого
ремонта грязное дерево закрытой issue по-прежнему требует оператора.
После потерянного ответа создания PR или закрытия issue Ralph перечитывает
состояние GitHub. Недоступное подтверждение не считается успехом.
Lisa не меняет индекс Git. Изменение индекса между снимком и продолжением
блокирует приёмку. Уже находящиеся в индексе чужие изменения сохраняются;
Ralph останавливается до commit ремонта, чтобы не включить их в него.
В пульте видны этап ремонта, файлы и причина отказа. Stop не запускает Lisa повторно.
Незавершённый `lisaRepair` блокирует ручной перезапуск до разбора оператором;
порядок снятия записи описан в `.agents/RALPH.md`, разделе о Lisa.
Если Lisa ошибочно вернула каталог внутри проекта, Ralph пропускает только этот
необязательный путь и продолжает штатные проверки. Проверки сами сообщат, если
утилиты не хватает; путь внутри проекта в `PATH` Ralph не добавляет.
При переходе к следующей фазе список очищается. Добавление каталогов в PATH
не меняет конфиг или постоянное окружение. Каталог кэша Lisa:
`<hostHomeDirectory>/lisa-tools`; точный путь
Ralph передаёт ей в prompt.

`preflightScripts`, `validationScripts` и `browserValidationScripts` содержат
команды оболочки. Каждая выполняется из корня репозитория: `npm run lint`,
`ruff check .`, `uv run pytest`. Команда обязана быть непустой, укладываться в
предел длины и обходиться без переводов строки. Своей команды автономная сессия
в набор не добавит: файл настроек лежит в control plane. Но control plane
закрепляет только строку команды, а не то, что она запускает: тело `npm run
lint` лежит в `package.json`, тело `make check` — в `Makefile`, и эти файлы
принадлежат проекту, то есть сессия правит их свободно. Значит, написанный
сессией код выполняется на вашей машине раньше, чем его увидит ревью.

## Как идут проверки

Ralph запускает команды в рабочей папке проекта. Он
передаёт им системные пути и значения из `validationEnvironment`, но убирает
пользовательские каталоги конфигурации и credentials агента. Вместо домашнего
каталога оператора команды получают свой в каталоге кэша пользователя, свой на
каждый проект. Без `HOME` инструменты Go, Rust, JVM и npm останавливаются на
поиске кэша ещё до первой команды проекта, а профиль оператора отдавать нельзя.
Каталог переживает прогоны вместе с кэшами и не попадает внутрь рабочей папки:
внутри её находят инструменты, которые ищут корень проекта вверх по дереву.
Там же Ralph задаёт `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `XDG_CONFIG_HOME`
и `XDG_CACHE_HOME`. Любой из этих путей задаётся строкой в
`validationEnvironment`; путь обязан быть абсолютным и лежать вне рабочей папки,
иначе созданные в нём файлы попадут в отпечаток дерева.

Отпечаток дерева Ralph берёт после команд подготовки и после набора проверок.
Подготовка вправе менять дерево — миграции и генерация кода для того и нужны;
проверки не вправе. Изменившая исходники проверка останавливает цикл, и
сообщение называет изменённые файлы.

Отпечаток собирается из того, что git показывает изменённым относительно
коммита, плюс новые файлы вне `.gitignore`; читаются и хешируются только они.
Неизменённые файлы git отбирает по размеру и времени правки из своего кэша
состояния, поэтому запись, вернувшая прежние размер и время, отпечаток не
изменит: от случайной правки форматтером или генератором это защищает
полностью, от подделки времени — нет. Следующий запуск продолжит задачу
только после того, как оператор вернёт точный diff, который был до проверки.

Один элемент списка содержит одну команду. Управляющие операторы
`;`, `&`, `|` и обратная кавычка запрещены. Цепочку запишите несколькими
элементами: так Windows останавливает набор после первого native exit code.

Проверки используют зависимости и сервисы, установленные на машине оператора,
и от его файлов не изолированы. Набор рассчитан на проект, которому оператор
доверяет; недоверенный репозиторий запускайте на отдельной машине.

`validationEnvironment` содержит строки `NAME=value`. Не записывайте туда
production-секреты.

## Адаптеры ревью

Ревью задачи и milestone использует `agentCli`. Предложение ремонта Lisa и
независимое ревью ремонта используют `supervisor.agentCli`, даже если разработку
ведёт другой CLI. Предложение приходит последней текстовой репликой сессии.
Для независимого ревью Ralph передаёт отдельную схему ремонта.

| CLI | Доступ ревьюера | Канал вердикта |
| --- | --- | --- |
| Codex | Оболочка в профиле только для чтения | Файл `--output-last-message` со схемой `--output-schema` |
| Claude Code | `Read`, `Glob`, `Grep` и строгая пустая MCP-конфигурация | `structured_output` итогового события `result` со схемой `--json-schema` |

Оба адаптера передают события сессии в общий журнал и предоставляют свежий
JSON-объект ревью. Ralph удаляет артефакт предыдущей попытки перед стартом.
Отсутствующий или некорректный результат завершает попытку с ошибкой.
Независимый вердикт по ремонту допускает `pass` или `human` с непустым `reason`.
Только `pass` передаёт ремонт на проверки перед перезапуском worker.

## Режимы задач

Поместите маркер в первую непустую строку тела GitHub issue перед тем, как
Ralph снимет одобренный snapshot. Для журнала с ручным одобрением включите
маркер в `body` записи. `--check` показывает выбранные режимы и сообщает,
если для них не хватает настроек.

```markdown
<!-- ralph-process: ui-change -->

В форме входа покажите ошибку под полем. Проверьте отправку пустой формы.
```

| Режим | Что Ralph проверяет |
| --- | --- |
| `bugfix` | Выполняет `validationProfiles.issue` или `validationScripts`. Ревьюер проверяет, что регрессионный тест воспроизводит исходный дефект. |
| `feature` | Выполняет те же команды. Ревьюер сверяет проверки с критериями нового поведения. |
| `ui-change` | После обычных проверок выполняет `browserValidationScripts`. Ревьюер сверяет браузерный сценарий с критериями задачи. |
| `research` | Проверяет отчёт с источниками, сравнением и выводом. |
| `review` | Проверяет отчёт с идентификатором проверенного изменения, находками и основаниями для них. |

Явный режим требует `review.enabled: true`. Ralph использует режим из
одобренного тела issue. Задача без маркера идёт обычным циклом.

`browserValidationScripts` — необязательный список команд из конфига или поля
«Браузерные проверки» в пульте. Для `ui-change` список должен быть непустым.
Если список заполнен, Ralph выполняет его также в конце каждой фазы перед
созданием или обновлением PR. Ralph отправляет тот SHA, на котором прошла
проверка фазы. Команды используют то же окружение, лимит и защиту дерева, что
обычные проверки. После возобновления Ralph снова проверяет задачу или фазу,
на которой остановился.

`research` и `review` добавляют или обновляют только
`docs/ralph-reports/issue-<номер>.md`. Ralph проверяет в Git непустой текстовый
файл и состав изменений до коммита и push. При лишних правках в рабочем дереве
Ralph сохраняет их и передаёт ошибку в следующую итерацию. Если лишние правки
уже попали в заявленный коммит, Ralph останавливается до push. Содержание
отчёта проверяет независимая сессия ревью. Если Lisa исправила доверенные файлы
Ralph, в commit могут войти эти проверенные правки ремонта и сам отчёт.
Уже сохранённый отчёт остаётся в ветке после ремонта.

## Тайм-ауты агента

`runtime.agentTimeoutMs` ограничивает полную длительность одной сессии.
Дополнительно Ralph следит за JSON-потоком CLI: ждёт первое событие не дольше
`runtime.agentFirstEventTimeoutMs`, затем ждёт каждое следующее событие не дольше
`runtime.agentIdleTimeoutMs`. По умолчанию это 300000 и 600000 мс.

При нарушении любого из этих двух пределов Ralph завершает дерево процессов с
кодом `RALPH_AGENT_IDLE_TIMEOUT`. Независимое и итоговое ревью считаются
временно оборванными и повторяются в пределах `runtime.reviewRetryAttempts`.
Общий тайм-аут сессии и лимит шагов не повторяются.

## Приёмка

Команда чата `/acceptance` копит кейсы приёмки по модулям и хранит прогоны в
каталоге документов проекта, по умолчанию `docs/acceptance/`. Скрипт
`ralph-acceptance.mjs` читает эти файлы и ничего, кроме `status.md`, не пишет:

```
node scripts/ralph/ralph-acceptance.mjs status [--dir docs/acceptance]
node scripts/ralph/ralph-acceptance.mjs impact <база>...<ветка> [--dir docs/acceptance]
```

`status` собирает `status.md`: по каждому живому кейсу последний статус, файл
прогона и до пяти последних результатов буквами `P F B S`, свежий справа. Модуль
без файла кейсов и модуль, где все кейсы сняты, названы в сводке разными
строками: снятие последнего кейса — не то же самое, что ненаписанные кейсы.
В сводке есть вердикт каждого прогона по его таблице: любой `FAIL` означает
«не принято»; без `FAIL`, но с `BLOCKED` или `SKIPPED` — «не завершено»;
только `PASS` — «принято». В консоли показан вердикт последнего прогона.
Непройденные кейсы других фаз не меняют вердикт этого прогона. Состав назначенных
кейсов сверяет исполнитель: скрипт не находит кейсы, забытые в таблице.
Нулевой код `status` означает запись сводки, а не принятие продукта.
`impact` берёт `git diff --name-only` по диапазону и печатает задетые модули с
кейсами, задетые без кейсов и изменённые пути, не попавшие ни в один модуль.
Без `modules.md` обе команды останавливаются; кривой заголовок кейса или строка
таблицы прогона останавливают с файлом и строкой — молчаливый пропуск в сводке
выглядел бы как «не гонялся».

Строка прогона со ссылкой на ID кейса, которого нет ни в одном файле кейсов, —
исключение: `status` не останавливается, а печатает предупреждение в поток
ошибок и исключает запись из сводки, `status.md` пишется как обычно с нулевым
кодом возврата. Это не порча формата — кейс обычно удалили из файла кейсов
вместо пометки «снят», и это правка человека, а не искажённый файл. Но кейс
пропадает из сводки совсем, без строки «не гонялся»: предупреждение видно
только в выводе команды, в `status.md` его не остаётся.

Три файла правит проект, поэтому их форматы здесь. Шапку таблицы скрипт узнаёт
по строке-разделителю под ней: без разделителя первая строка читается как
данные, а не пропадает.

**`modules.md`** — таблица: имя модуля (латиница в нижнем регистре, цифры,
дефис), файл кейсов относительно каталога приёмки, пути в коде через запятую.
`**` — любая глубина, `**/` — ноль и более каталогов, `*` — внутри сегмента.
Файл кейсов, который уходит за пределы репозитория, останавливает обе команды.

```
| Модуль | Кейсы | Пути |
| ------ | ----- | ---- |
| cart | cases/cart.md | src/cart/**, src/api/cart/** |
```

**`cases/<модуль>.md`** — каждый заголовок второго уровня есть кейс:
`## CART-012. Название`. ID — имя модуля в верхнем регистре и номер из трёх и
более цифр; номер растёт и не переиспользуется. Строка
`**Снят** <дата> — <причина>` в блоке кейса выводит его из сводки и прогонов,
не удаляя историю. Остальной текст блока скрипт не читает.

**`runs/<дата>-<тип>[-<модуль>].md`** — скрипт читает первую таблицу после
заголовка `## Результаты`: строка — ID кейса, статус из `PASS`, `FAIL`,
`BLOCKED`, `SKIPPED`, комментарий. Прогоны упорядочиваются по имени файла, дата
идёт первой. Если в отчёте есть строка `Вердикт: принято.` (точка необязательна),
все строки таблицы должны иметь `PASS`; иначе обе команды останавливаются с
именем файла. Исправьте ошибочный итог, сохранив результаты. Отчёты без строки
вердикта читаются как раньше. Остальная шапка и разбор отказов — для человека.
Хвост `-<число>` на конце
имени скрипт читает как номер повтора, поэтому самостоятельное имя, которое им
заканчивается, объединится по истории с соседним прогоном той же основы.
