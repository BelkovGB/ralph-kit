# Проверки Ralph

Границу control plane и список файлов, которые сверяет проверка подделки,
описывает `.agents/RALPH.md`. Здесь — журнал одобренных issues, договор о
командах проверок и два режима их запуска.

## Аккаунт GitHub

`githubAccount` содержит login аккаунта из `gh auth status`. Ralph читает токен
этого аккаунта командой `gh auth token --user`. Ralph добавляет токен только в
окружение своих процессов `gh` и сетевых команд Git: `fetch`, `push` и
`ls-remote`. Настройка не вызывает `gh auth switch`, не меняет глобальный active
account и не переписывает Git Credential Manager. Токен не хранится в конфиге,
аргументах команд и логах. Агент и проверки его не получают.

При заданном аккаунте `origin` должен иметь вид
`https://github.com/owner/repository.git`. SSH-origin использовал бы ключ
машины, а не выбранный аккаунт, поэтому Ralph отклоняет его. Для сетевых команд
Git Ralph закрепляет проверенный URL в памяти и передаёт его явно вместо
изменяемого `origin`. Поэтому последующая правка `pushurl` не меняет адрес
отправки. Ralph отключает hooks через отдельный пустой каталог; `push` также
получает `--no-verify`. Репозиторий не может прочитать токен через `pre-push`
или `reference-transaction`.

Если поле удалить, Ralph использует аккаунт, активный в GitHub CLI. Если login
не авторизован, `--check` останавливается до запуска агента.

## Журнал одобренных issues

`approved-issues.json` хранит запомненный текст issues, одобренных вручную. При
`autoApproveConfiguredIssues: true` — это умолчание — одобрением служит сам
закоммиченный план `phases`: Ralph берёт текущие заголовок и тело issues этих
milestone, если автор issue доверенный. Перед стартом агента Ralph замораживает
точный текст в состоянии прогона, поэтому правка issue в GitHub после старта
останавливает прогон. Issues с замечаниями ревью, которые Ralph заводит сам,
замораживаются тем же механизмом, и круг исправлений milestone идёт без
человека. Поставьте `false`, когда каждую issue нужно вносить в журнал руками.

Журнал защищён контрольной суммой: эталон лежит ключом
`approvedIssueSnapshotsHash` в `.agents/ralph.config.json`. Впишите новую сумму
тем же коммитом, которым добавляете запись, иначе прогон останавливается на
сверке; сумму называет само сообщение об остановке. Эталон стоит в конфиге,
потому что обновление набора перезаписывает `scripts/ralph/**` целиком, а конфиг
не трогает: вписанная сумма остаётся на месте вместе с журналом проекта.

## Договор о командах

`preflightScripts` и `validationScripts` держат команды оболочки, а не имена
скриптов. Каждая выполняется как написана из корня репозитория: `npm run lint`,
`ruff check .`, `uv run pytest`. Команда обязана быть непустой, укладываться в
предел длины и обходиться без переводов строки. Своей команды автономная сессия
в набор не добавит: файл настроек лежит в control plane. Но control plane
закрепляет только строку команды, а не то, что она запускает: тело `npm run
lint` лежит в `package.json`, тело `make check` — в `Makefile`, и эти файлы
принадлежат проекту, то есть сессия правит их свободно. В контейнерном режиме
это безопасно — код выполняется в изолированном контейнере без сети. В
host-режиме это значит, что написанный сессией код выполняется на вашей машине
раньше, чем его увидит ревью.

## Host-режим

`validationMode: "host"` запускает команды в рабочей папке проекта. Ralph
передаёт им системные пути и значения из `validationEnvironment`, но убирает
пользовательские каталоги конфигурации и credentials агента. Вместо домашнего
каталога оператора команды получают свой — `.git/ralph-loop/host-home`: без
`HOME` инструменты Go, Rust, JVM и npm останавливаются на поиске кэша ещё до
первой команды проекта, а профиль оператора отдавать нельзя. Каталог переживает
прогоны вместе с кэшами; свой путь задаётся строкой `HOME=...` в
`validationEnvironment`.

Отпечаток дерева Ralph берёт после команд подготовки и после набора проверок.
Подготовка вправе менять дерево — миграции и генерация кода для того и нужны;
проверки не вправе. Изменившая исходники проверка останавливает цикл, и
сообщение называет изменённые файлы.

Отпечаток собирается из того, что git показывает изменённым относительно
коммита, плюс новые файлы вне `.gitignore`; читаются и хешируются только они.
Неизменённые файлы git отбирает по размеру и времени правки из своего кэша
состояния, поэтому запись, вернувшая прежние размер и время, отпечаток не
изменит: от случайной правки форматтером или генератором это защищает
полностью, от подделки времени — нет. Следующий запуск продолжит задачу
только после того, как оператор вернёт точный diff, который был до проверки.

В host-режиме один элемент списка содержит одну команду. Управляющие операторы
`;`, `&`, `|` и обратная кавычка запрещены. Цепочку запишите несколькими
элементами: так Windows останавливает набор после первого native exit code.

Host-режим использует установленные зависимости и доступные с хоста сервисы.
Он подходит доверенному локальному проекту, но не изолирует команды от файлов
пользователя. Attestation в этом режиме не переиспользуется: внешняя база или
другой сервис могут измениться без изменения Git-дерева.

`validationEnvironment` содержит строки `NAME=value`. Не записывайте туда
production-секреты.

## Контейнерный режим

`validationMode: "container"` сохраняет прежнюю изоляцию. Перед первой командой
Ralph собирает образ по `Dockerfile.validation`. Набор
команд идёт в свежем непривилегированном контейнере: сети нет, сокета Docker
нет, корневая файловая система только на чтение, а снимок рабочего дерева
приезжает bind-монтированием — в снимке лежат все файлы, которых не исключает
`.gitignore`. Entrypoint копирует снимок в рабочий каталог с правом записи и
заводит там одноразовый репозиторий Git, поэтому Git-метаданные хоста и его
хранилища паролей контейнеру недоступны.

Контекст сборки — не корень репозитория. В нём только пути из
`validationDependencyPaths` и скрипты проверок Ralph, и берутся они из HEAD, а
не из рабочего дерева: `COPY` любого другого файла падает, а незакоммиченная
правка манифеста останавливает прогон.

Образ не ставит ничего проектного. Свои зависимости — и всё, что команде нужно
во время работы, например базу данных или браузер, — проект добавляет в свой
`Dockerfile.validation`, где сеть ещё есть.

`validationContainer.writableVolumes` добавляет анонимные Docker volumes в
каталоги, куда инструменты должны писать при read-only root filesystem.
Укажите абсолютные POSIX-пути. Docker создаёт volume из содержимого образа и
удаляет его после проверки вместе с `--rm`. Примеры для конкретных пакетных
менеджеров — в `docs/tips.md` репозитория набора.
